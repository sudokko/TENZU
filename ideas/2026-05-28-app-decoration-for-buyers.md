# App 装飾・再印刷機能の購入者解放

## 着想

[acquisition/funnel.md §14](../acquisition/funnel.md) サンクスページ設計の検討中に浮上。

従来の App 設計は「親が 5×5 グリッドに自由に点・線を描いて模写問題 PDF を出力する無料ツール」。この設計では「やる気ある親が 12 枚自作して ¥200 セット代わりにする」カニバリリスクがあった。

機能を削るとユーザーが「使えない」と感じる懸念、機能を残すと自己カニバリ。この袋小路を **App の位置づけ自体を反転** することで突破するアイデア。

## 案の中身

App を **無料ファネル玩具＋購入者特典の二層構造** にする。

### 機能階段（叩き台）

**🟢 無料層（Phase 0 から提供）**
- 5×5 模写問題ジェネレータ（ゼロから自作）
- 透かし入り PDF 出力（フッターに業態識別句＋商品誘導）
- セッション完結（保存なし）
- 1 PDF = 最大 6 問

**🔴 購入者解放層（Phase 1〜段階的）**
- 購入 SKU のインポート（140 SKU から自分が買った分だけ呼び出せる）
- 装飾レイヤー: 子の名前・日付・フレーム・色・メッセージ追加
- 6×6 以上のグリッド対応（Lv.3-5 相当）
- 透かしなし出力
- 作品ライブラリ保存（再印刷可能）
- 限定テンプレ（季節・キャラクター調イラスト枠など）

### 段階導入

| Phase | 内容 |
|---|---|
| **Phase 0**（既定路線維持） | 無料創作ツール公開・透かし＋業態識別句フッター |
| **Phase 1**（モニター期） | 購入者向け SKU インポート機能 β 公開（モニターからフィードバック取得） |
| **Phase 2** | 装飾レイヤー本格実装・春LPバンドルの目玉に |
| **Phase 3** | 高度テンプレ追加・UGC ギャラリー連携 |

## 効くポイント

1. **カニバリ問題を構造的に解消**: 「App だけで充分」→「買えば App がもっと使える」へ反転
2. **¥200 知覚価値の跳ね上がり**: 紙12枚＋App装飾権で「お得感」が立つ。¥1,000-2,000 バンドル SKU（[pack-commerce.md §24](../product/pack-commerce.md)）の核に
3. **Pillar P5（継続・親が子に寄り添う）と完全直結**: 「お子さんの名前入れた点描写を、お子さんが解く」体験は親リテンションの本丸
4. **完成後の達成感**: 子が解いた紙に親が装飾して飾る → 「やり遂げた」が形になる → 続く
5. **UGC が自然発生**: 装飾した作品は SNS にあげたくなる素材になる（IG 主導線と相性最高）
6. **競合堀**: 公文・天才ドリル・ピグマリオンは紙単体勝負。装飾レイヤーは差別化堀

## 課題・落とし穴

| 項目 | 重さ | コメント |
|---|---|---|
| 認証システム | 中 | Stripe Customer Portal ＋ magic link で MVP は組める |
| SKU データ配信 | 軽 | 140 SKU は SVG/JSON で静的配信可能 |
| 購入 ↔ App 権限同期 | 中 | Stripe webhook ＋ DB or JWT で対応 |
| PDF 生成 | 軽 | クライアント完結可能（既定方針） |
| 海賊版対策 | 軽 | 透かし＋認証で実用上OK・完全防御不要 |
| サポート負荷 | 中 | デバイス移行・ログイン問題への対応想定 |
| 開発工数 | **重** | Phase 0 で全部やろうとすると遅延必至 |

### ブランド側の最大の落とし穴

「装飾」が前面に出すぎると「点描写＝空間認知の土台」というブランドの本質がぼやける危険。装飾は **親側のリテンション機能** であって、**子の体験は紙で点を写すこと** は変わらない、を Voice レイヤーで縛る必要あり。

例: 「装飾」ではなく「仕上げ」「お子さんの一冊にする」などのコピー設計で、主役は子の練習・装飾は親の関わり方の一形態と位置づける。

## 判断保留の理由

1. **開発工数の重さ**: Phase 0 公開を遅らせると acquisition の死の谷対策（[decisions.md §3.32](../decisions.md)）が崩れる
2. **収益モデル未決**: 「商品購入で恒久解放」か「サブスクで継続解放」か。前者はブランド整合的、後者は LTV 出る。判断材料不足
3. **App の位置づけ確定が必要**: 無料ファネル単独 → 「無料＋購入者特典」二層構造への反転は SSOT 多箇所改訂を伴う

## 次の判定タイミング

以下のいずれかをトリガーとして再評価:

1. **Phase 0 公開後のモニターフィードバック取得時**: 無料 App だけで「使えない」と感じるか、満足するかの実データを確認
2. **春LPバンドルSKU設計時**（[pack-commerce.md §24](../product/pack-commerce.md)）: ¥1,000-2,000 バンドルの中身検討で「App 装飾権」を組み込むか判断
3. **Phase 1 モニター後の収益・リテンション分析時**: 商品単体の継続率データを見て、App 装飾レイヤー投入の ROI 試算

## 議論メモ（2026-05-28 追記）

装飾解放アイデアを掘り下げる中で見えた3つの技術・運用課題と、それぞれの解決方針案。

### 課題①: 模写以外の8タスクが作りにくい

9 タスクのうち、ツール実装の難度は以下の通り:

| # | タスク | 作る難度 | 理由 |
|---|---|---|---|
| 1 | 模写 | 🟢 軽 | 元図形をそのまま出力 |
| 2 | 欠け補完 | 🟢 軽 | 元図形作って一部消すだけ |
| 3 | 線対称 | 🟢 軽 | 元図形＋対称軸選択 |
| 4 | 回転 | 🟢 軽 | 元図形＋角度選択 |
| 5 | かさね | 🟡 中 | 2図形作って重ねる |
| 6 | **分解** | 🔴 重 | **正解パターン管理必要** |
| 7 | 移動 | 🟢 軽 | 元図形＋移動ベクトル |
| 8 | 拡大縮小 | 🟢 軽 | 元図形＋倍率 |
| 9 | **立体模写** | 🔴 重 | **等角投影UI＋立体描画必要** |

**解決方針**: 「元図形を 1 つ描く UI」さえ作れば、#1-#5, #7, #8 の 7 タスクはタスク選択式で自動変換できる。#6 分解・#9 立体は永久に商品 PDF 専用（実装コスト的にも自然な堀になる）。

### 課題②: 解放範囲を広げると全部自作されてしまう

7×7 まで・透かしなしで解放すると、購入者が「自作で全 SKU 代替できてしまう」リスク。

**解決方針**: App を **2 モードに分離**し、購入者解放を「インポート＋装飾モード」に絞る:

| モード | 無料層 | 購入者層 |
|---|---|---|
| **ゼロから自作モード** | 5×5・透かしあり・#1模写のみ | **据え置き**（5×5・透かしあり・#1模写のみ） |
| **インポート＋装飾モード** | 利用不可 | **解放**（購入 SKU を取り込んで派生作成・7×7まで・透かしなし） |

→ 購入者でも「ゼロから 7×7 で自作セット組む」は永久に不可能。買った SKU を元にしか改変できない。**カニバリ最終ラインを死守**。

**永久に商品 PDF 専用（堀の本丸）**:
1. #6 分解・#9 立体（実装重い＝自然な堀）
2. **年齢別カリキュラム編成**（9種×5段＝140 SKU の体系設計）
3. 難易度メタ厳選公開
4. 解説書・進捗シート・親向けガイド同梱

根本論: App は **末端の問題生成**は奪えるけど、**カリキュラム設計（Pillar P1 体系）**は奪えない。これが真の堀。

### 課題③: PDF 即DL派と App 装飾派の両ケア負荷

買った人は2タイプ（仮説）:
- **X. PDF即DL派**（7-8割）: 買って即DLして印刷したい
- **Y. App装飾派**（2-3割）: 子の名前入れて装飾したい

両方ケアすると工数倍に見えるが、**SKU データの SSOT 化**で大幅軽減可能。

**解決方針**: データを SVG/JSON で 1 ソース化し、出力経路を 2 つに分ける:

```
マスター: SVG/JSON データ（SKU ごと）
  ├─ 出力①: 静的 PDF（ビルド時プリレンダリング）→ 即DL配信（X派主導線）
  └─ 出力②: App 経由 PDF（クライアント生成・装飾レイヤー追加）→ Y派が任意利用
```

**オペレーション**:
- 購入完了 → Stripe webhook → 購入確認メール
- メール本文に 2 リンク併記:
  - 「📄 PDFを今すぐダウンロード」（X派の95%はここで完了）
  - 「✨ Appで装飾してから印刷」（任意・Y派が利用）

→ X 派は App を一切意識せず完結。CV 摩擦ゼロ。

**SVG/JSON SSOT 化の追加メリット**: 装飾 App やる/やらないに関わらず、PDF差替え・将来の動的生成・LLMO 連携すべての基盤投資として正当化できる。

### 結論: Phase 0 では準備不要

3 課題ともに解決方針は見えたが、**今すぐ全部実装する必要はない**。

**Phase 0 段取り**:
- 静的 PDF 即DL運用のみ（既定路線）
- App は無料創作版のみ（装飾なし）
- SVG/JSON SSOT 化は **やってもいいが Phase 0 必須ではない**（様子見）

**Phase 1 で判断材料を収集**:
- モニターから装飾ニーズを実データで確認
- 装飾 App 投入の ROI を試算
- そこで「やる/やらない」を確定

→ いま結論出さない。**アイデアは alive のまま、判断は Phase 1 モニター FB 後に持ち越し**。
