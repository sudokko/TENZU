# サービスブループリント

## サマリ

- **構造**: 7フェーズ（①認知→②検討→③購入→④配布→⑤利用→⑥補填→⑦リピート）× 4レイヤー（顧客行動／フロントステージ／バックステージ／サポーティング）
- **既決の骨格**: 認知（GTM完了）／検討（無料サンプル3層）／購入（Stripe ¥200一律＋初回¥100OFF＋カート要）／配布（4経路）／利用（紙PDF＋WEB解答**公開**）／補填（3要素照合）
- **配布の核**: ①Thank You即DL／②Stripeメール／③**ダウンロードページ（自前マジックリンク認証）**／④補填フォーム
- **マイページ廃止**: 機能最小の「ダウンロードページ」に格下げ（会員登録なし哲学を堅持）
- **PDF は DL 時その場生成**（クライアントサイド pdf-lib・SKU＝12問の問題データ。事前生成ファイルなし・S3 PDF 保管なし）
- **認証は自前マジックリンク**（Lambda 2個＋DynamoDB tokenテーブル・Cognito 不採用）
- **ウォーターマーク不採用**（方針維持。その場生成で技術的には可能になったが採用しない）
- **解答・解説ページは公開**（未購入者も閲覧可、購入導線 CTA 設置）
- **レイアウト選択**: カートは SKU のみ（¥200）。紙サイズ×1ページ問数は**ダウンロード時に自由・何度でも変更可**（商品ページのセレクタ＋プレビューは体験デモ）

## 2. フェーズ別の流れ（時系列）

### ①認知

**顧客行動**: 「点描写 プリント 無料」「点描写 解答 〇〇」等で検索、SNSやブロガー記事から流入、または広告クリック。**解答ページが公開されたことで「点描写 解答」系のロングテール流入が新規追加**。

**既決ポイント**: 集客チャネル・KPIはGTM設計（A工程）で確定済み。

### ②検討/体験

**顧客行動**: 記事を読む／記事内サンプル問題を試す／WEBで問題プレビューを見る／**解答ページを覗いて質を確認**／アプリで点描写を実際に作って体験。

**既決ポイント**:
- 無料サンプルは3層のみ（独立サンプルPDFは廃止）
- 各タスク紹介記事＋サンプル問題はローンチ必須要件（pack-design.md §14.6.2）
- **解答ページは公開**（CTA設置で購入導線として機能）

**既決ポイント（追加）**:
- **アプリの2モード設計**（2026-04-27 ❓7クローズ）:
  - **モード①インフルエンサーフック**: 商品CTAは置かない（紹介価値を保つ・広告色排除）
  - **モード②流入ユーザー受け皿**: 商品ページ直送せず、記事ページ（ノウハウ系）へ振る
- **CTA動線 = 3段階階段モデル**: アプリ → 記事（価値訴求）→ 商品ページ
- **誘導タイミング**: A+B併用
  - A: 問題作成完了画面（満足度ピーク時の振り向き）
  - B: アプリのフッター常設「点描写についてもっと知る」リンク
- **商品リンク強度**: About画面のみ控えめに掲載（メイン体験を阻害しない）
- **アプリのドメイン**: **別ドメイン**（例: `tenzu-app.jp` 等、具体は別途検討）。インフルエンサーフックとしての独立性を強化、「無料アプリ」感を出す
- アプリ→記事誘導用の優先記事ジャンルは §7 で B-2へ申し送り

**既決ポイント（追加・2026-04-28 ❓8クローズ）**:
- **記事は5系統に整理**: ①Pillar（3〜5本・エンティティ権威化）／②Cluster ノウハウ／③Cluster 比較・選び方／④Cluster 課題解決／⑤商品ファミリー（タスク紹介＋解答ページ・既決）
- **LLMO最適化**を全記事の前提とする（チャンク引用・エンティティ強化・独自データ権威化・Schema.org・自然言語見出し・E-E-A-T）
- **CTAはテンプレートスロット化**＋ `target_skus` メタからの自動展開で量産対応
- 詳細は §4 論点8参照

### ③購入

**顧客行動**: 商品詳細ページで内容確認・**紙サイズ×1ページ問数のプレビューで仕上がりを試す** → カート（SKU のみ）→ Stripe Checkoutにメアド入力 → カードまたはPayPayで決済。

**既決ポイント**:
- ¥200一律／1 SKU=12問（**SKU＝問題データ。PDF はレイアウトを当てて生成するビュー**）
- **カート画面あり**（自前実装、Stripe Checkout に line_items 渡す方式）
- **カートに入るのは SKU のみ**。紙サイズ（A4/B4/A3・縦横）×1ページ問数はダウンロード時に自由・何度でも変更可（「印刷自由・兄妹再利用可」「家庭の印刷機に合わせられる」と整合）。商品ページのセレクタ＋連動プレビューは購入前の体験デモ
- 初回¥100OFF（≥¥500、Stripe `first_time_transaction`）

**未決**: 法務ページ配置（❓9）／カート放棄リカバリ（❓11）／アップセル位置（❓6,7,8と関連）。

### ④配布/受領

**顧客行動**: Thank You即DL → 後でStripeメールのリンクからもDL可能 → 再DLしたければダウンロードページにメアド入力（マジックリンク受信→クリック認証）。

**既決ポイント（4経路）**:

| 経路 | タイミング | メアド依存 | 認証 |
|---|---|---|---|
| ① Thank You DL | 決済直後（セッション中） | 不要 | Stripe Session ID |
| ② Stripeメール | 決済直後・自動送信 | 依存 | メール内リンク |
| ③ **ダウンロードページ（自前マジックリンク）** | 再DL時 | 依存 | 自前token（15分期限・1回使い切り） |
| ④ 補填フォーム | メール未達時 | **非依存** | 3要素照合 |

**ダウンロードページUX**:
- 購入 SKU を一覧表示 → SKU ごとに紙サイズ（A4/B4/A3・縦横）×1ページ問数を選択 → 「PDF をダウンロード」で**その場生成・即保存**（ファイル名 `{sku}_{紙}_{問数}.pdf`）
- レイアウトは何度でも変更して再ダウンロード可（事前生成パターン・一括 ZIP は廃止＝不要）

**バックエンド**:
- Stripe Webhook → Lambda が DynamoDB書込（email, purchase_id, product_id, 決済日時, card_last4 or 金額）。`selected_layout` は廃止
- **PDF はクライアントサイド生成**（pdf-lib・ベクターのみで数十KB・レイアウトエンジンは商品ページプレビューと共通）。サーバ側 PDF 生成・S3 PDF 保管なし
- 認証済セッションに対し**購入 SKU の問題データ（JSON）のみ**を返す API（Lambda）。これが配信の保護対象
- 自前マジックリンク: Lambda 2個（request-link / verify）+ DynamoDB tokenテーブル
- pdf-lib は Node でも動作 → 将来メール添付・事前生成バッチが必要になれば同一コードを Lambda 転用可

**未決**: なし（このフェーズは設計完了）。

### ⑤利用

**顧客行動**: PDFを印刷 → 子どもが紙で解く → 親がスマホで**公開WEB解答ページ**を開いて丸つけ。

**既決ポイント**:
- 「子=紙、親=スマホ」の役割分担
- **解答ページは公開**（アクセス制御なし、誰でも閲覧可）
- 解答画像 = 完成図（線がつながった状態）。点描写の特性上、見ても「子どもが書く」需要は不変
- 解答ページにCTA設置: 「この問題は『〇〇パック』に収録」「他の問題も見る」
- 解答ページ自体が**SEO流入の入口＋購入導線**として機能

**未決**: なし（このフェーズは設計完了）。

### ⑥補填/再DL

**顧客行動**: メールが届かない → 補填フォームでメアド・決済日・カード末尾4桁（PayPayは決済金額）入力 → 画面でDLリンク表示。

**既決ポイント**:
- 3要素照合
- 5回失敗でロック、15分クールダウン
- 試行ログをDynamoDB
- ダウンロードページ入口・問い合わせ・Thank Youの3箇所にリンク常設
- 認証成功時はワンタイムDLセッション発行（マジックリンクと同じ仕組み）

**未決**: なし（このフェーズは設計完了）。

### ⑦リピート/レビュー

**顧客行動**: 解答ページからレコメンドで関連パックを発見 → 再購入。Google Formsアンケートに任意回答。MailerLiteのシナリオメールから次商品ページへ遷移。

**既決ポイント**:
- 解答ページ→関連パック動線の骨子（公開解答ページがリピートの主軸に昇格）
- **MailerLite Automation フルシナリオ運用**（2026-04-27 ❓4方針転換）:
  - Stripe決済完了→Webhook→MailerLite同期（メアド・購入SKU・購入回数）
  - シナリオ詳細（ウェルカム／使い方／F2転換／F3転換／非アクティブ復活等）はB-2と並走で別途設計
  - 計測基盤は DynamoDB に既存フィールド（email, purchase_id, product_id, 決済日時）で完全カバー
  - 運用方針: **初期設定が重く運用は自動化** — シナリオ組み終わればモニタリング中心
  - カート放棄メールも同フレームで実装可（❓11と関連）
  - 設計担当=ユーザー本人（CRMベンダー12年・WEBマーケSE3年の専門領域）
- **レビュー導線 = Google Forms手動掲載式（A方式）**:
  - **収集導線**: Thank Youページ／Stripeメール（カスタムメッセージにURL）／ダウンロードページ常設リンクの3箇所
  - **アプリ内では取らない**（購入者母集団に絞ってノイズ排除）
  - **インフルエンサー枠も同じFormsで収集**（フォーム内「経路」選択肢で一般購入者／インフルエンサーを分岐、集計時に分離）
  - **フォーム必須項目**: 購入SKU（複数購入は代表1つ）／5段階評価／感想（自由記述）／**公開可否チェックボックス**
  - **任意項目**: 学年／改善要望（非公開）／メアド（追加質問用）
  - **公開単位**: TENZU全体プール1つ（タスク別バケツは作らない）
  - **公開先**: TOPページ「お客様の声」セクション＋専用「お客様の声」ページ（フッターからリンク）。商品ページには出さない
  - **運用フロー**: Forms回答 → 公開可チェック済み回答だけ手動で `reviews.json` に転記 → デプロイ
  - **公開時の表示工夫**（学年タグ・購入タスクタグ・並び順・絞り込みUI等）はB-2/C-4で詰める将来論点
  - 動的レビュー（DB保存・購入者投稿UI・モデレーション運用）は永久に不採用候補
- **問い合わせ窓口 = Mid構成**（2026-04-27 ❓6クローズ）:
  - **Tally（問い合わせフォーム・reCAPTCHA付）** — メアド非公開でスパム99%カット、Slack/Gmail通知で気づける
  - **LINE公式アカウント** — 月1,000通まで無料、ママ層リーチ強化（メール開かない層への補完）
  - **FAQページ** — 印刷推奨設定／レイアウト変更／再DL方法／解答ページの見方／声かけのコツ等。B-2のローンチ必須コンテンツに含める
  - 返信用メアド（`support@tenzu.jp` 等）は**送信元のみで公開しない**
  - 自己解決→Tally→LINEの3層で受け付け
  - X DM・ライブチャット（Crisp等）は不採用（個人運営の持続性考慮）

**未決**: なし（このフェーズは設計完了）。

## 4. クローズ済み論点

### 2026-04-28 セッション成果

#### 論点9: 法務ページ → **3ページ構成・雛形サービス利用・フッター3リンク**

- **構成**: 特定商取引法に基づく表記 ／ プライバシーポリシー ／ 利用規約 の3ページ
- **返金ポリシーの位置**: 独立ページは作らず、**特商法ページ内に記載**（❓10と統合）
- **生成方法**: 雛形サービス（bizocean等のジェネレーター）＋特商法は自前記入。将来規模が出たら弁護士レビュー
- **フッター**: `特商法 ／ プライバシーポリシー ／ 利用規約` の3リンクのみ
- **更新運用**: 手動（個人運営フェーズは手間対効果でこれで十分）

#### 論点11: カート放棄リカバリ → **❓4（MailerLite Automation）に統合済み・形式クローズ**

- 実質は❓4（2026-04-27クローズ）のMailerLite カート放棄シナリオとして対応済み
- Stripe Webhook → MailerLite同期で「決済未完了」タグ付け → 24h後フォローメール
- 本論点は形式残置のため、ここでクローズ扱いとする

#### 論点10: 返金ポリシー → **原則不可＋4例外＋30日期限**

- **基本方針**: デジタルコンテンツにつき、原則返金・キャンセル不可（特商法の返品特約として明示）
- **例外4ケース（返金または代替対応）**:
  - ① **二重決済**: 全額返金（TENZU側責任）
  - ② **PDF破損・DL不可など技術的不具合**: 再送・修正で対応（返金ではなく）
  - ③ **商品説明と内容の重大な相違**: 全額返金
  - ④ **未成年者が親の許可なく購入**: 個別判断（民法上の取り消し権、規約に明記して対応窓口を案内）
  - ⑤ お客様都合（誤購入・気が変わった等）: **不可**
- **期限**: 決済日から30日以内の申告に限る
- **申告窓口**: Tally問い合わせフォーム（❓6で確定済み）
- **表示**: ❓9 法務ページ（特商法表記）に統合して記載
- **返金実行**: Stripe管理画面から元の決済手段へ返金処理

#### 論点8: 記事→購入の橋渡し → **LLMO前提＋テンプレートスロット化＋target_skusメタ自動展開**

> **設計思想の前提**: (1) 記事はアプリ・商品ページと並ぶローンチ必須要素。(2) アプリ→記事→商品の3段階階段（❓7）は記事のごく一部。記事全体を意識した設計が必要。(3) Claudeで量産する前提＝テンプレート＋スロットで設計する。1記事ずつ手で書くと10本で力尽きる。LLMO観点でも記事数とエンティティ網羅性で勝負が決まる。

##### A. 記事の5系統整理

旧整理の5種類を再分類した。

```
記事本体（B-2の射程）
├─ Pillar（3〜5本・大トピック・SEO主砲・LLM引用源）
│   例: 「点描写とは何か」「図形力を伸ばす知育の全体像」「年齢別 知育ドリルの選び方」
│
└─ Cluster（個別深掘り・Pillarに紐づく・量産対象）
    ├─ ノウハウ系（旧②に相当）
    │   例: 年齢別の進め方／丸つけのコツ／声かけ／鉛筆選び
    ├─ 比較・選び方系
    │   例: 点描写 vs ジオボード／市販ドリル比較／PDF vs ノートタイプ
    └─ 課題解決系
        例: 「線がはみ出る子へのフォロー」「集中が続かない子への対処」

商品ファミリー（旧①③・C-3で既決）
├─ タスク紹介記事（9本・ローンチ必須）
└─ 公開解答ページ（CTA付き、§5利用で骨子確定済）

機能ページ（旧④・記事本体とは別レイヤー）
├─ お客様の声ページ
└─ FAQページ
```

##### B. LLMO最適化の前提原則

全記事タイプに共通で適用：

1. **チャンク単位の引用容易性**: 1段落＝1主張＝1完結。質問→定義→根拠→例の逆ピラミッド
2. **冒頭150字に「答え」**: AI Overviews抜き取り想定のリードチャンク
3. **エンティティ強化**: 「点描写」「図形力」「TENZU」をLLMの知識グラフに刻み込む。同義語網羅
4. **一次情報・独自分類の権威化**: 9タスク分類／Lv.1〜5×Vol.ラダー／年齢×Lvキャッチコピーマップを記事内で繰り返し参照
5. **Schema.org構造化データ**: Article + FAQPage + Product（target_skus分） + BreadcrumbList を全記事に自動付与
6. **自然言語クエリ網羅**: 「年長の子に点描写って効果ある？」のような会話文H2見出し
7. **E-E-A-T**: 著者情報＋更新日＋出典明示＋一次情報リンク
8. **AI検索からのファネル**: LLMが引用したパラグラフの直近にCTAを配置（=チャンク末CTA原則）

##### C. CTA強度マトリクス

| 記事タイプ | LLMOでの役割 | CTA強度 | 主要CTA位置 | 量産難易度 |
|---|---|---|---|---|
| **Pillar**（3〜5本） | エンティティ権威化・引用源 | **弱** | 末尾のみ「点描写ドリルを探す」程度 | ⚠️ 半人力（厚く監修） |
| **Cluster ノウハウ** | PaA回収・課題啓発 | **中** | 関連タスク言及直後の文脈CTA＋末尾レコメンド | ⭕ 量産向き |
| **Cluster 比較・選び方** | 比較検討層への決定打 | **強** | 比較表直下に該当SKU | ⭕ 量産向き |
| **Cluster 課題解決** | 顕在ニーズ即CV | **強** | 解決策提示直後（読者の納得ピーク） | ⭕ 量産向き |
| **商品ファミリー** | SKU理解・SEO直接流入 | **最強** | 全所・SKU直結（既決） | ⭕ ローンチ時固定 |

**判断の根拠**:
- Pillar記事を売り込むとLLM引用率が落ちる（広告色排除のほうが引用される＝逆説的にCV増）
- Clusterは課題顕在化済み読者なので強CTAで離脱前にCV回収
- 「LLM引用パラグラフの直近にCTA」原則を全タイプで貫徹

##### D. テンプレートスロット構成（量産パイプラインの心臓部）

各記事は固定構造のMDXで出力。Claudeは「メタ＋トピック」を入力にテンプレを埋めるだけ。

```
---
frontmatter:
  tier: pillar | cluster
  category: knowhow | comparison | problem_solving | task_intro
  target_age: [3-4 | 4-5 | 5-6 | 6-7 | 7-9]
  target_skus: [tenzu-sentaisho-vol1, ...]    ← CTA自動生成のキー
  parent_pillar: tenten-towa
  primary_question: "年長の子に点描写って効果ある？"
  related_questions: [...]                     ← PaA向け
  updated_at: 2026-04-28
---

[1] リード（150字以内・「答え」チャンク）    ← AI Overviews抜き取り想定
[2] 目次（自動生成）
[3] H2: primary_question（自然言語見出し）
[4] H2セクション群（各H2は1テーマ完結）
[5] 独自データ参照ブロック（9タスク／Lvラダー／年齢×Lvマップ）
[6] 文脈CTA（target_skusから自動展開）        ← ★スロット
[7] FAQ（FAQPage Schema用・PaA回収）
[8] 関連記事（Pillar↔Cluster相互リンク）
[9] 末尾CTA（記事タイプ別テンプレ）           ← ★スロット
[10] 著者情報＋更新日（E-E-A-T）
[11] JSON-LD（Schema.org自動生成）
```

**スロット注入ロジック**:
- `target_skus` が指定されていれば → 文脈CTA・末尾CTAに該当SKUカードを差し込む
- `category: comparison` なら → 比較表直下にCTAスロットを追加
- `tier: pillar` なら → 文脈CTAは抑制し末尾CTAのみ
- 全記事末尾に「点描写アプリで試す（無料）」を並列で入れる（3層サンプルの一つ）

##### E. CTA形式の3種固定

都度デザインしない。テンプレ化された3種だけを使い回す。

| 形式 | 重量 | 用途 | 配置 |
|---|---|---|---|
| **文脈テキストリンク** | 軽 | 文中で自然に商品参照 | 関連タスク言及の直後 |
| **SKUカード** | 中 | 商品名＋価格＋サムネ＋CTAボタン | 文脈CTA位置・FAQ直後 |
| **末尾レコメンド** | 重 | 3商品横並び＋「点描写アプリ無料」並列 | 記事末尾 |

##### F. 量産パイプライン

```
①トピックリスト（B-2で生成・PaA調査ベース）
   ↓
②Claude Code に テンプレート＋ナレッジベース＋メタ投入
   ├─ ナレッジ: pack-design.md / Lvラダー / 9タスク定義
   ├─ ガードレール: NGワード／お店路線／傷つきにくさ

```

**Claudeへの入力例**（1コマンド＝1記事）:

→ テンプレ通りの記事が1本出てくる仕組み。

##### G. ❓8 確定事項のまとめ

1. **記事は5系統に整理**（Pillar / Cluster×3 / 商品ファミリー / 機能ページ）
2. **LLMO最適化を全記事の前提**にする（8原則）
3. **CTA強度を記事タイプ別に変える**（弱→中→強→最強の4段階）
4. **CTAはテンプレートスロット化**（都度設計しない）

6. **チャンク末CTA原則**（LLM引用想定パラグラフの直近にCTA）
7. **CTA形式は3種固定**（文脈テキストリンク／SKUカード／末尾レコメンド）
8. **構造化データ**: Article + FAQPage + Product + BreadcrumbList を全記事に自動付与
9. **量産パイプライン**: Claude Code＋テンプレート＋ナレッジベースで1コマンド1記事
10. **Pillarは半人力監修・Clusterは量産可**

### 2026-04-27 セッション成果

#### 論点4: MailerLiteの位置付け → **MailerLite Automation フルシナリオ運用**（同日2回目更新で方針転換）

> **方針転換の経緯**: 当初「リスト保管のみ・配信運用なし」で確定したが、F2転換施策の実現性確認の中でユーザーがメールマーケのプロ（CRMベンダー営業12年・WEBマーケSE3年）であることが判明。「シナリオ1本案は甘い／フルでやるなら初期設定が重いだけで運用は自動化される」との指摘で全面見直し。

- **方針**: MailerLite Automation でフルシナリオ運用。能動的なメール戦略を CRM 主軸として位置付け
- **やること**（運用範囲）:
  - ウェルカム／オンボーディング
  - 使い方ガイド配信
  - **F2転換シナリオ**（初回購入後の2回目促進）
  - **F3転換以降のリピート促進**
  - 非アクティブユーザー復活
  - **カート放棄リカバリ**（❓11と統合）
  - 新作・キャンペーン告知
- **計測基盤**: 既決の DynamoDB 設計（email, purchase_id, product_id, 決済日時）で完全カバー、追加実装不要
- **同期方式**: Stripe Webhook → Lambda → DynamoDB保存 + MailerLite API同期（購入トリガー・カスタムフィールドで購入回数・SKU・累計金額を保持）
- **シナリオ詳細設計**: B-2（コンテンツ設計）と並走で別途設計タスク化。設計担当=ユーザー本人（専門領域）
- **運用方針**: **初期設定が重く、運用はモニタリング中心**。開封率・CTR・F2転換率・解約率を月次でレビュー、シナリオ調整
- **メアド取得経路**: Stripe決済時のみ（アプリ・記事からの「メアド登録だけお願い」CTAは依然として設けない、購入者母集団に絞る）

#### 論点5: レビュー収集導線 → **Google Forms 手動掲載式（A方式）Phase1から採用**

- **方針**: 動的レビュー機能（購入者投稿UI＋DB＋モデレーション）は永久に不採用候補。手動掲載式で運用負荷ゼロを死守
- **収集**:
  - Google Forms（無料・bot対策・集計標準装備）
  - 導線3箇所: Thank Youページ／Stripeメール（カスタムメッセージにURL）／ダウンロードページ常設リンク
  - **アプリ内では取らない**（購入者母集団に絞る）
  - **インフルエンサー枠も同じFormsで収集**（経路選択肢で分岐）
  - フォーム必須: 購入SKU／5段階評価／感想／公開可否チェック
- **公開**:
  - 単位: TENZU全体プール1つ（タスク別バケツは作らない）
  - 表示先: TOPページ「お客様の声」＋専用「お客様の声」ページ
  - 商品ページには出さない
  - 運用: Forms → 公開可チェック済みのみ手動で `reviews.json` 転記 → デプロイ
- **将来論点（B-2/C-4で詰める）**: 公開時の絞り込みUI／タグ表示／並び順／引用文量
- **判断の決め手**: ¥200デジタル単品でレビューCVR寄与は限定的だが、インフルエンサー試打＋初期購入者の生声は欲しい。手動掲載式なら半日実装＋月数十分運用で済む

#### 論点6: 購入後フォロー → **Mid構成（Tally + LINE公式 + FAQ）+ メール再接触は❓4へ統合**

- **メール再接触の扱い**: ❓4の方針転換により、ステップメール・F2/F3転換・非アクティブ復活はすべて MailerLite Automation 側で運用。本論点ではメール以外の購入後接点を扱う
- **問い合わせ窓口 = Mid構成**:
  - **Tally（問い合わせフォーム・reCAPTCHA付）** — メアド非公開でスパム99%カット、Slack/Gmail通知
  - **LINE公式アカウント** — 月1,000通まで無料、メール開かないママ層へのリーチ補完。ブロック自由で心理的負担少ない
  - **FAQページ** — 印刷推奨設定／レイアウト変更方法／再DL／解答ページの見方／声かけのコツ等、B-2でローンチ必須コンテンツとして設計
  - 返信用メアド（`support@tenzu.jp` 等）は**送信元のみで公開しない**（直接公開はスパム不可避のため）
  - 自己解決→Tally→LINEの3層フロー
- **不採用**:
  - メアド直接公開（スパム被害不可避）
  - X DM対応（カジュアルすぎ・エビデンス残らない）
  - ライブチャット（Crisp/Tawk.to等）（個人運営で営業時間外の対応負担破綻リスク）
- **判断の決め手**: メール使わない層（特にママ層）への到達経路としてLINE公式は強力。個人運営の持続可能性とユーザー手厚さのバランス点

#### 論点7: アプリ→購入の橋渡し → **アプリの2モード分離 + 3段階階段モデル**

- **2モード設計**:
  | モード | 対象 | アプリの役割 | CTA方針 |
  |---|---|---|---|
  | ①インフルエンサーフック | ブロガー・SNSインフル | TENZU紹介価値の提供 | **商品CTA不要・むしろ邪魔**（広告色排除で紹介されやすく） |
  | ②流入ユーザー受け皿 | ①経由でアプリ触った人 | 体験の入口・次の一歩へ橋渡し | 商品ページ直送せず**記事ページ（ノウハウ系）へ振る** |

- **CTA動線 = 3段階階段モデル**:
  ```
  アプリ（無料体験・満足度ピーク）
    ↓ ノウハウ系記事リンク
  記事（価値訴求・ファネル教育）
    ↓ 「この問題は『〇〇パック』に収録」CTA
  商品ページ（購入）
  ```
  商品到達は**必ず記事を経由**＝記事側で価値伝達してからCV。アプリ単体はピュアな体験版に保つ
- **誘導タイミング**: A+B併用
  - **A. 問題作成完了画面**（「お疲れ様」的画面で記事リンク2〜3本）— 満足度ピーク時の振り向き
  - **B. アプリのフッター常設**「点描写についてもっと知る」— いつでもアクセス可能
- **商品リンク強度**: **About画面のみ控えめ**（「PDFパックも販売中」程度）。フッター・メイン画面には置かない
- **アプリのドメイン**: **別ドメイン**（`tenzu.jp/app` でなく独立ドメイン）。インフルエンサーフックとしての独立性を強化、「無料アプリ」感を強める。具体ドメイン名は別途検討
- **クロスドメイン計測**: GA4 クロスドメイントラッキング設定が必要（Step Dの技術検証範疇）
- **判断の決め手**: アプリは「中身が見える3層」の中で**最強の体験版**。ここで購入を急がせると紹介価値が損なわれる／記事を中継させることで価値訴求の段階を踏める／別ドメインにすることで「TENZUの販促ツール」感を消し、純粋な「無料アプリ」として紹介してもらいやすくする

  - 解答ページは公開なのでスコープ外

### 派生変更2: Cognito完全削除 → 自前マジックリンク実装

- マイページ廃止＋解答ページ公開＋補填フォームでセッション付与不要 → Cognitoの用途がマジックリンク認証1個だけに縮小
- そのため Cognito Custom Auth Challenge（3 Lambda構成）はオーバースペック
- **自前実装**に切替:
  - Lambda 1: `POST /auth/request-link`（email→token生成→DynamoDB保存→SES送信）
  - Lambda 2: `GET /auth/verify?token=xxx`（token検証→ダウンロードページ表示）
  - DynamoDB: tokenテーブル（token, email, expires_at:15min, used_at）
  - レート制限（同IP 5/15min）
- AWSスタック簡素化: Amplify + Lambda + DynamoDB + S3 + CloudFront + SES（Cognito削除）
