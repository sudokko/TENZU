# 個人開発者の意思決定論——「続けられる複雑度」を選ぶ

TENZU は 1 人で運営する小規模 EC サービスだ。個人開発者の意思決定には、チーム開発とは違う独自の論理が必要になる。「ベストプラクティス」と書かれているものをそのまま採用するのではなく、「自分一人で運用しきれるか」「フェーズに合っているか」「正しい問いに答えているか」を問い直す習慣が、設計の質を決める。

このエッセイでは、TENZU の設計プロセスから抽出された 4 つの個人開発者特有の意思決定パターンを論じる。

---

## パターン1: 「続けられる複雑度」で技術スタックを決める

最も繰り返し現れたパターンが「マネージドサービスの過剰利用を避ける」という判断だ。これは技術的な保守主義ではなく、**個人運営の運用キャパシティに合わせてスタックを選ぶ** という現実的な原則の表れだった。

具体例を時系列で並べる：

**2026-04-22 — Storybook/Chromatic 不採用**（EP-028）
UI コンポーネントの確認手段として Storybook + Chromatic を検討した。しかし Storybook が解決する「複数人開発でのコンポーネント管理問題」は 1 人開発に存在しない。Amplify Preview の PR プレビュー環境で本番同等の UI 確認ができるなら、Storybook を維持するコストは正当化できない。

**2026-04-26 — マイページ廃止**（EP-014）
当初は AWS Cognito ＋ マイページを想定していた。しかし「会員登録なし哲学」と「マイページ有り」が構造的に矛盾していると気づき、Lambda 2 個 + DynamoDB token テーブル + SES の自前マジックリンクに置き換えた。Cognito の機能群の大半は TENZU では使わない。必要な単機能だけを最小コストで実現できる自前実装の方が合理的だった。

**2026-05-08 — AWS Bedrock/Kendra/Lex/DynamoDB 全部不採用**（EP-027）
FAQ 運用に AWS の 4 サービスを検討したが、すべて不採用にして Next.js 標準 MDX 運用に着地した。FAQ 50 件規模に Kendra（月額 $810〜）は過剰、Bedrock のハルシネーション管理は 1 人運営では現実的でない、Lex の設計工数は機能対効果を超える、DynamoDB は MDX の git 管理で代替できる——4 つすべてが「使えるけど採用すべきでない」だった。

**2026-04-19 — 無料サンプル PDF 廃止**（EP-026）
全 SKU 140 本に対して個別サンプル PDF を作る設計を廃止し、「アプリ無料体験 + Web プレビュー画像 + 記事埋込」の 3 層代替に置き換えた。140 本 × 2 系統（有料版 + サンプル版）の管理は個人開発者には重すぎる。

これらの決断に共通する判断軸は次のとおりだ：

| 問い | 答えが Yes なら不採用 |
|---|---|
| そのツールが解決する前提問題が、自分の環境に存在するか？ | 存在しない |
| マネージドサービスの月額固定費・チューニング工数を継続的に払えるか？ | 払えない |
| 自前実装で同等の単機能を実現できるか？ | できる |
| 機能の大半が「将来必要かもしれない」だけか？ | そうだ |

特に重要なのは **「使えるから使う」を疑う** という姿勢だ。技術的に採用可能であることと、運用として採用すべきであることは別の問いだ。マネージドサービスの本当のコストは月額料金ではなく、設定・運用・チューニング・障害対応の工数を含む。

> **教訓**: 個人運営の基準は「機能の豊富さ」ではなく「運用しきれる複雑度」。「後で必要になれば追加できる」前提で、今必要ない機能を外す決断ができるかどうかが、設計の持続可能性を決める。

## パターン2: 「誰もやっていない」を二通りに読む

TENZU プロジェクトの最初のセッション（2026-03-11）で、「点描写 プリント」「点描写 無料」で検索上位 10 サイトをすべて調査した。結果は「全サイトが完全無料配布、有料販売はゼロ」という事実だった（EP-000）。

通常、こういう調査結果を見ると 2 つの解釈が可能だ。

| 解釈 | 内容 |
|---|---|
| 解釈 A | 需要がない。だから誰もやっていない |
| 解釈 B | チャンスがある。誰も深く考えていなかっただけ |

TENZU は解釈 B を選び、有料参入を決めた。判断の根拠は「競合の弱点の構造」を見たことだった。すべてのサイトが「無料だが難易度の体系化が甘い」「枚数が限られている」「進捗管理がない」という共通の弱点を持っていた。これは「需要がないから供給されていない」のではなく、「供給側が深く考えていなかった」ことの証拠だった。

¥200 一律価格（EP-011）も同じ思想の延長にある。市販ドリル（こぐま会・ピグマリオンなど）が ¥1,000〜2,000 で売れている市場で、PDF を ¥200 で売る前例はなかった。しかし「前例がなかった」ことと「需要がない」ことは別だ。WEB での有料 PDF 販売市場は単に未開拓だっただけで、保護者の「体系化された点描写教材にお金を払う」意欲は市販ドリル市場で証明されていた。

AWS スタックの不採用（EP-027）も、別の角度からこのパターンを実践している。「Bedrock を使った FAQ 運用」を実装している小規模 EC サイトは少ないが、それは「やってないから劣っている」のではなく「過剰だから誰もやっていない」だ。「誰もやっていない」を見たら、その理由を構造的に分析する習慣が、無駄な投資を避ける判断軸になる。

> **教訓**: 「誰もやっていない」は二通りある。「需要がないから」と「気づかれていないチャンスだから」だ。競合の「なぜ」を見て区別する。前者なら避け、後者なら飛び込む。区別の判断軸は「全員が同じ弱点を共有しているか」だ。

## パターン3: 方針転換は「失敗」ではない

2026-05-07 に確定した先行リリース戦略 HO-B2-25 を、翌 2026-05-08 に全面撤回した（EP-013）。確定した設計書を翌日撤回する——通常なら「設計の失敗」「迷走」と呼ばれそうな状況だ。

しかし TENZU ではこれを「設計プロセスの正しい挙動」として記録した。撤回理由は「目的の再定義」だった。HO-B2-25 は「先行リリースで売上を上げる」目的で設計されていたが、実際にユーザーが求めていたのは「インフルエンサー・ブロガーとの濃いコミュニケーション」と「先行モニターからの具体的なフィードバック」だった。目的の認識違いに気づいた時点で、設計の方向そのものを見直す必要があった。

撤回の処理は「削除」ではなく「撤回処理済として残置」だった。`pack-design.md §14.9` に「2026-05-08 撤回」と明記し、旧設計を歴史として保存した。これにより「なぜこの設計が変わったか」が後から追える。スタートアップが陥りがちな「突然方針転換した」問題を防ぐ仕組みでもある。

お店メタファー堅持（EP-024）も、繰り返し再燃する道場路線への誘惑に対して、何度も同じ方針を再確認するという形の「方針堅持」だった。設計が進むにつれて「初段・二段」「上巻・下巻」「小1相当」のような道場路線的な表現が局所的に魅力的に見える瞬間が何度もあった。その都度「全体方針との整合性」に立ち戻り、専門店メタファーを選び直した。

このパターンには 2 つの局面がある：

| 局面 | 例 | 必要な判断 |
|---|---|---|
| **大転換**（方針を変える） | EP-013 先行リリース戦略 | 「目的が変わったか」を問う |
| **堅持**（方針を維持する） | EP-024 お店メタファー | 「全体方針と整合するか」を問う |

両方に共通するのは **「何を目的にしているか」を毎回確認する** 習慣だ。目的が変わったなら設計を変える。目的が変わっていないなら、局所最適の誘惑に屈しない。

撤回ドキュメントを残す運用は副次効果として、「次のフェーズで再び同じ議論が出てきたとき」のガード機能を果たす。`pack-design.md §0.5` の「不採用案の記録（再燃防止）」も同じ思想だ。決めたことより「なぜその選択肢を捨てたか」を残す方が、長期的な判断の一貫性を保ちやすい。

> **教訓**: 設計プロセスでは「方針転換」も「方針堅持」も同じ重みで起きる。前者は「目的が変わったか」、後者は「全体方針と整合するか」を問う。両方とも撤回・再確認の経緯をドキュメントに残すことで、後から経緯が追える透明性が生まれる。

## パターン4: 不安を「説得」ではなく「構造」で解消する

TENZU のターゲット（点描写を始める保護者）には、特有の不安がある。「うちの子、図形苦手かも」「年齢に対して遅れているかも」「買って失敗するかも」。これらの不安に対して、単に「個人差があります」「大丈夫です」と説得文を書くのは効果が薄い。**情報の構造そのもので不安を生まない設計** の方が強力だ。

具体例を 3 つ挙げる：

**年齢フレーミング 3 層構造**（EP-043）
各 Lv の年齢目安を「〇歳向け」と単一値で表記すると、「うちの子はその年齢より遅い」と読まれやすい。代わりに「早めの子（先取り層）」「標準的な子」「ゆっくりの子」の 3 層を重なる帯として表示する。Lv.3 なら早め 5〜6 歳・標準 6〜8 歳・ゆっくり 7〜9 歳。年齢の帯が重なっているため、「うちの子は外れている」という判断が構造的に成立しない。

加えて「ファーストビュー禁止ワード」を設けた。「差がつく」「遅れる」「今始めないと」「合格」「IQ」などの焦り訴求・受験強圧ワードは、商品の最初の画面に出さない。詳細ページの中盤では使ってもよいが、最初の印象として焦りを生む語彙は禁止する。

**先行リリースの目的を「売上ゼロ前提」に再定義**（EP-013）
「先行価格で安く買える」という設計は、保護者に「割引で釣られた感」と「定価が下がるかも」という不安を与える。これを撤回し、「先行モニターには無償でフルアクセス、フィードバックをもらう」という対等な交換関係に置き換えた。価格という変数を外すことで、不安の発生源そのものを消した。

**先行モニター制度の対等性設計**（EP-033）
モニターに「無料で全部使える代わりにフィードバック必須」という構造を作った。これは「施し」ではなく「対等な協業関係」だ。「あなたの感想がサービスを作る」というメッセージが、モニターに「貢献している」という自己効力感を与える。本リリース時の「TENZU 開店記念ギフト」も同じ思想で、「無料モニターを使った」のではなく「あなたたちのおかげで開店できた」という関係を実体化する。

3 つに共通するのは **「説明文より設計が伝える」** という原則だ。年齢個人差を説明文で書くより、年齢帯を重ねて表示する。割引で釣られた感を「実は定価は変わりません」と説明するより、割引そのものをなくす。施し感を「対等な関係です」と書くより、フィードバック必須＋お返しギフトという構造で対等性を実装する。

> **教訓**: ユーザーの不安は、説得文より情報構造で解消する方が強力で持続する。「何を見せるか」より「どう見せるか」「どういう関係を作るか」が UX の核心だ。コピーライティングは設計の代替にならない。

## 全体を通して見えた原則

4 つのパターンを並べると、個人開発者の意思決定の通底する姿勢が見えてくる。**「正しい問いに答えているか」を毎回確認する** という習慣だ。

- スタック選定（パターン1）は「機能を選ぶ」のではなく「自分が運用しきれる複雑度を選ぶ」
- 市場参入（パターン2）は「先行事例があるか」ではなく「競合の弱点が構造的か」
- 方針転換（パターン3）は「決めた設計を守る」のではなく「目的に整合するか」
- UX 設計（パターン4）は「不安を説得する」のではなく「不安を生まない構造を作る」

すべてが「業界の標準的な答え」をなぞるのではなく、**自分の文脈で問いを再定義する** という方向を向いている。「Storybook を入れるべきか」ではなく「自分の環境で Storybook が解決する問題は何か」。「先行リリース価格をいくらにするか」ではなく「先行リリースの目的は何か」。

個人開発者の最大の強みは「決定権が自分にある」ことだ。標準解を採用するか、文脈に合わせて再定義するか、その選択が自分次第だ。標準解を採用するのは思考停止の言い訳としても機能してしまうため、毎回「自分の文脈ではどうか」を問い直す習慣が、設計の質を決める。

そしてもう一つ重要なのは、**「削る」ことが設計の主作業になる** という点だ。マイページを削る、AWS スタックを削る、Storybook を削る、サンプル PDF を削る、サブ Lv を削る、仕上げ編を削る、先行価格を削る、ペルソナ 8 人格を削る——TENZU の設計の半分は「何を入れるか」より「何を削るか」だった。シンプルにすることそのものが、個人開発者にとって最も困難で、最も価値のある作業だ。
