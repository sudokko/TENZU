# TOP Hero 再設計とフォント Tier② 差し替え（オーナーのデザイン反復スタイルの言語化）

## 何が起きたか（要約）

2026-07-07、TOP（`web/app/page.tsx`）をオーナーとの対話で段階的に作り直した。① Hero は往復の末「H1＋コアタグライン＋無記名の店主紹介文カード＋署名アニメ」へ着地、②「なぜ、点描写なのか」は画像を線画からリアル写真へ転換して本文も刷新、③「品ぞろえ」は静的カードを撤去してインタラクティブ部品 `CoverageStudio` に置換した。並行して、サイト全体の Tier② 本文フォントを Zen Kurenaido から Klee One 400 へ差し替えた（decisions §3.64）。セッション末に一式 17 ファイルをコミット `02e987e` として確定。この反復で観察されたオーナーの意思決定スタイルを feedback メモリとして言語化し、以後の提案の前提にした。実写採用と visual-identity §6 の矛盾は未解決のまま記録した。

## 状況・背景

前提はタグライン第4世代の確定と設計書クリーンアップ後の構成。TOP はストアフロント化を経ていたが、Hero のメッセージ密度・品ぞろえ予告の静的カード・長文フォントの可読性に課題が残っていた。参考例は Brilliant.org。ただし色のカラフルさはブランドの「端正で静か」と衝突するため、借りるのは構造だけに絞った。スマホ実機確認は LAN バインドの dev サーバーで行った。

## やり取りの中身

**Hero の往復と CSS カスケードのバグ**。サブ文と CTA ボタンを一度撤去→オーナー指摘でサブタグラインを復活→後半でさらに撤去し無記名の店主紹介文カードへ置換、という三段の往復になった。スマホでは署名アニメをメッセージより上へ配置（`order:-1`）し、モバイル H1 を `clamp(34px,10.5vw,44px)` まで拡大。当初「サイズが変わらない」と指摘された原因は CSS カスケード順のバグで、無条件の基本ルールがモバイル用オーバーライドより後にあり上書きしていた。署名アニメもお手本1.25倍拡大とラベルの単語化（模写・鏡・回転）で整えた。

**案Cの完全削除と CoverageStudio**。Brilliant.org 構造を完全模写した案Cを別ルート `/top-c` に試作したところ、オーナーは「Cは微妙・完全削除」と即断。比較用に残さずファイルごと削除し、正本の直接反復へ戻った。ただし「構造だけ借りる」路線は品ぞろえで生きた——3力のピル切替＋タスク一覧＋SVG 実演アニメ（お手本の墨色→こたえの teal を描いて消す無限ループ）の `CoverageStudio.tsx` を新設し、9タスク全てに実演スペックを定義した。

**店主紹介文と実写への転換**。chiiku-baby.jp の冒頭コメントを参照したオーナー要望「顔は出さず、作り手はこう考えていると伝えたい」を反復推敲した。二児の父・IT企業での新製品企画という最小開示のみで、「手間をかけているぶん有料ですが、広告は一切入れていません」を軸にした無記名三人称のカード（淡い teal 面）に確定し、visual-identity §8.1・decisions §3.65 として SSOT 化した。②の画像は幾何学線画の提示から、オーナーの「写真はリアルに」で実写へ確定。本文も点つなぎ／図形パズル／タブレットの3連対比から「見て・考えて・鉛筆で書く」へ流す構成に差し替えた。

**Tier② フォント差し替え**。オーナーが「前々から思っていたんだが」と長文用フォント（Zen Kurenaido）の可読性を自発的に指摘。Hero 固有でなくサイト全体の Tier② と判明し、`tokens.css` の `--font-tier2-pencil` 1箇所の変更で50箇所超へ波及させ Klee One 400 に差し替えた。rev.5 の3階層は①見出し Klee One 600／②本文 Klee One 400 の同一書体ウェイト違い（③は Plex）になった。

**反復スタイルのメモリ化**。この日の観察を feedback メモリに言語化した——(1) 却下方向は残さず完全削除、(2) 人物はイラストでなく実写でリアルに、(3) 可読性の不満は「ふと思い出した」形で唐突に顕在化——の3点である。

## なぜそう判断したか

**却下案を残さなかった理由**。一度「違う」と判断した方向を比較用に残すと、後から迷いの種になる。オーナーは比較検討より「今のベストへの一本化」を好み、「一応残しておきますか」と聞くより次の一手へ進むことを歓迎する。適用方法まで含めてメモリ化したのは、単発でなく繰り返し効く前提だからだ。

**実写を例外運用として通した理由**。抽象的な幾何図形が続くページで人の温度を出す一点には、フラットイラストよりドキュメンタリー的な実写が刺さる、というオーナー判断だった。ただし visual-identity §6 は「写真不使用（使う場合はモノクロ・hard edge 限定）」を明記しており、フルカラー実写は原則の例外運用になる。承認は得たが SSOT 側は未更新のため、例外の明記・モノクロ化・不掲載の三択をオーナー判断として残し、「解決したことにしない」記録を選んだ。

**フォント差し替えが1箇所で済んだ理由**。Tier② が `tokens.css` の1変数に集約されていたため、書体の再選定という大きい判断を実装上は1行の変更で全体へ波及できた。

**店主紹介文を無記名にした理由**。信頼性の根拠（二児の父・製品企画の経歴）は開示しつつ、実名・顔・社名は出さない。「無料じゃない・でも作り込んでいる」を正面から言うカードに徹し、マスコットや開閉 UI の装飾的な人間味は不採用にした。

## 学び（一般化できるノウハウ）

1. **明確な却下は削除まで進めてよい** — 複数案の試作は良いが、却下が明確なら比較用に残す提案をせず削除して正本の反復へ戻る。意思決定者が「一本化」型か「比較保持」型かを見極め、観察を再利用可能な形で言語化しておくと、以後の提案の外し率が下がる。

2. **デザイントークンは「大きい判断を1行にする」保険** — 書体・色などの横断値を1変数に集約しておくと、後からの再選定が全域一括で安全に効く。50箇所に直書きされていたら、この日の差し替えは起案すらされなかった可能性が高い。

3. **例外運用は承認と同時に SSOT へ書くか、未解決と明記する** — 原則に反する採用を口頭承認だけで通すと、設計書と実装の矛盾が静かに残る。すぐ書けないなら「未解決」として選択肢つきで記録し、解決済みを装わない。
