# 設計書クリーンアップと pack-design 3分割・スキルの SSOT 参照方式化

## 何が起きたか（要約）

実装ラッシュの2ヶ月で、設計書と現実の乖離が溜まっていた。2026-07-06 に設計書全域（8領域＋ルート）を5系統の並列監査にかけ、Pass 1（事実修正）と Pass 2（構造掃除）を実施した。ローンチ総 SKU＝48 の正を裁定して旧値（63・56 など）を全域から掃除し、1288行に肥大化した pack-design.md をオーナー指示で3分割（pack-design 610行／pack-tasks 790行／pack-commerce 462行）。§番号を変えずファイルだけ移す方式で既存参照を保護した。3日後の 07-09 には .claude/skills/ 7本と article-reviewer エージェントを棚卸しし、ルール複製が生んだドリフト3件を「SSOT 参照方式」への改修で解消（削除ゼロ）。文書とスキルの両面で「同じ内容を2箇所に書かない」を運用原則に固めた。

## 状況・背景

TENZU の設計書は8領域構造・サマリ20行・SSOT・archive 退避の原則で運用してきた（EP-009・EP-046 の系譜）。だが6月のメーカー10種・問題パイプライン・決済の実装で、設計書側の数値や名称が現実から遅れた。pack-design.md は9タスク仕様・ラダー・価格・メーカー商務が同居して「サマリだけ読む」運用が崩れかけていた。スキル群にも構造問題があった——article-reviewer は 2026-05 頃の設計書からルール表をインライン複製して書かれており、その後の設計書改訂に追従していなかった。

## やり取りの中身

**5系統並列監査と正の裁定**。領域を分けて並列に監査をかけ、乖離を列挙してから Claude が「正」を裁定し、オーナー確認のうえ全域へ展開した。ローンチ総 SKU は 48（模写8＋線対称4＋回転5＋平行移動4＋拡大縮小6＋かさね7＋分解7＋欠け補完4＋立体3）と確定し、旧値を掃除。記事本数の SSOT は clusters.md に一本化し、phases.md は実体数値を持たない参照へ変えた。screen-flow §6 は web/ コードと突合のうえ per-maker 買い切りモデルへ全面書換（/login・/pricing は削除でなく転用と判定）、phase-1-todo はゼロから再構築した。撤回コンテンツは archive へ完全退避しつつ、不採用案の記録（§0.5・§13.7.6・§24.5）は再燃防止ガードレールとして意図的に温存した。

**pack-design の3分割**。旧1288行を、全体設計（pack-design.md）／タスク別ラダーと D スコア実装（pack-tasks.md）／価格・メーカー・広告バンドル・検索意図（pack-commerce.md 新設）へ分割した。§番号は一切振り直さず、§12.7 や §23.9 は「ファイルだけ移動」。リポジトリ全域の参照リンクを付け替え（archive/journal は不可侵）、CLAUDE.md の SSOT 対応表も3行に分割した。decisions.md は実体を動かさず、冒頭に「現行の背骨（Tier 1）＋系譜」の索引だけ新設した。

**スキル棚卸し（07-09）**。3日後、7スキルと article-reviewer を棚卸しした。未使用スキル（dm-kit・article-export・weekly-ops）はローンチ前運用ツールで「出番前」と判定し削除ゼロ。article-reviewer にはルール複製由来のドリフト3件——不存在ファイル名への参照・article_type enum が旧7値のまま（現行10値）・消滅済み仮置き URL への制約——が見つかり、骨格（観点・severity・出力形式）のみインラインに残し、中身はレビュー開始時に SSOT 必読リストを読む方式へ全面改修した。revision-craft §3 に小見出しを付けて8箇所の参照を実アンカー化。改修後は stale 参照の grep 全滅と、実記事での実地テスト（Critical 誤爆なし）で検証した。

## なぜそう判断したか

**§番号を保存してファイルだけ割った理由**。decisions.md や他設計書からの参照は §番号アンカーで書かれており、分割で振り直すと全参照が壊れる。凍結済みの archive/journal は直せない。§番号を「ファイルをまたいで安定な ID」として扱えば、分割コストはリンク付け替えだけに縮む。

**decisions は索引化に留めた理由**。§3 の実体を archive へ退避するには参照グラフの確認が前提で、当日の作業量では安全に踏み切れない。索引の新設だけなら参照を壊さず読み手の導線を改善できる。実体退避は「やり残し」として明示的に残した。

**スキルを削除でなく参照方式化した理由**。未使用は問題ではなく、出番が来ていないだけだった。真の問題はルール複製で、複製をやめて SSOT 参照にすれば設計書を直すだけでスキルが追従する。当初から参照方式で書かれた新スキル群にドリフトが皆無だったことが、この原則の傍証になった。

**「乖離の列挙」と「正の裁定」を分けた理由**。複数文書が違う値を持つとき、どれが正かの裁定こそが監査の本体である。裁定結果（SKU=48 等）を先に固定してから全域置換に入ることで、掃除の途中で判断がブレることを防いだ。

## 学び（一般化できるノウハウ）

1. **文書分割はアンカー ID の安定性を最優先する** — 節番号を振り直す分割は参照網を全滅させる。節番号をファイル横断で一意な ID として保存し「実体の置き場所だけ動かす」方式なら、分割は参照リンクの付け替え作業に縮み、凍結文書からの参照も生き残る。

2. **派生物（スキル・エージェント・プロンプト）にルールを複製しない** — 複製した瞬間から SSOT との乖離が始まる。派生物には骨格（観点・出力形式）だけを書き、中身は実行時に SSOT を読む設計にすれば改訂へ自動追従する。ドリフト検査は「不存在ファイル名・旧 enum・消滅 URL」の grep で機械化できる。

3. **監査は列挙と裁定を分離し、裁定を先に固定する** — 並列で乖離を洗い出す作業と、正を決める判断を混ぜると、掃除しながら基準が揺れる。裁定を一点で済ませ確定値を固定してから全域置換に入るのが、複数文書の整合回復の最短路である。
