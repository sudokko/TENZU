# 開店（T=0）——7 週間の準備期を、日付を動かさずに終える

## 何が起きたか（要約）

2026-08-30、TENZU が開店した。作業自体は 2 つだけ——Amplify へ `PREOPEN=0` を投入し、空コミットを push して新規ビルドを起こす。約 200 秒後にプレオープン告知帯が消え、実測で開店ゲート 6 件すべての通過を確認した。**準備期の開始時に置いた開店日 T=0＝2026-08-30 を、一度も動かさずに到達した**。

## 状況・背景

準備期の 7 週間は、計画どおりに進んだ期間ではなかった。SES の本番アクセスが却下され（EP-145）、Amplify が env を 1 変数だけ渡さず購入確認メールが 4 日間止まり（EP-147）、開店前日には Chrome がフィッシング判定で赤い全画面を出した（EP-149）。いずれも「開店を延ばす」という選択肢が現実的に存在した局面だった。

運用ルールとしては、日付を動かしてよいのは P0 テストが緑にならないときだけ、と決めてあった（launch/operations.md §2）。遅延時の削り順も先に決めてあった——記事公開本数 → SNS 在庫の順に削り、**開店日を守る**。

## やり取りの中身

**当日の作業は分担が明確だった**。env の投入は AWS コンソール（人間）、ビルドの起動は空コミットの push（AI）。`PREOPEN` は事前に `amplify.yml` の whitelist へ入っていることを確認済みで、EP-145 の罠は踏まなかった。

**オーナーはアプリ全体に入れた**（main のブランチオーバーライドではなく）。staging からも帯が消えるのが正しい、という判断で、staging は noindex の内部用だから実害はない。キー単位ではブランチ設定がアプリ全体を上書きする仕様だが、`PREOPEN` はどこにも無かったので main にも届く。

**確認は実測で行った**。①5 ページで告知帯の出現 0 回 ②`check-env-gates.mjs` 全通過（本番 index / staging noindex / canonical 自己一致）③カート→決済で `cs_live_…` セッション生成・Checkout タイトルが `TENZU` ④`/restore` 200・旧 URL 307 ⑤法務 3 ページと問い合わせが 200 ⑥sitemap 77 URL。

**開店ゲートは 6/6**。G1 決済〜受け渡しの本番再走、G2 全 43 巻 publish、G3 記事 14 本 live、G4 env・index・帯、G5 計測 3 イベントと Search Console、G6 送客導線。

## なぜそう判断したか

**日付を守れたのは、削る順序を先に決めてあったからである**。障害が起きるたびに「何を諦めるか」をゼロから考えていたら、都度「開店を延ばす」が選択肢に上がっていた。**先に削る順序を決めておくと、危機のときに考えることが減る**。実際には記事も SNS も削らずに済んだが、削れる余地があると分かっていること自体が判断を軽くした。

**障害の多くが「開店を止めない」形で設計されていた**のも効いた。決済の受け取りは webhook に依存せず（EP-145）、フィッシング判定を受けたのは購入後の復元リンクだけで購入導線は無傷だった（EP-149）。**単一障害点を減らしておくと、事故が事故のまま終わる**。

## 学び（一般化できるノウハウ）

1. **締切を守るために、先に「削る順序」を決めておく** — 危機のときに優先順位を考え始めると、いちばん大きな約束（日付）が最初に崩れる。何から削るかを平時に決めておけば、危機は「順に削るだけ」の作業になる。

2. **単一障害点を減らすと、障害が事業を止めない** — 4 日間 webhook が死んでも購入者は商品を受け取れていた。設計時の「メールが落ちても受け取れる」という選択が、そのまま障害耐性になった。

3. **最後の作業は小さくしておく** — 開店当日にやったのは env 1 個と再ビルドだけだった。大きな作業を当日に残さない構成にしておくと、当日の失敗の余地がほぼ消える。
