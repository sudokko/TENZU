# 設計書全体リファクタと 4 値 phase モデルの確定（先行SKU概念の廃止・archive/ ディレクトリ新設）

## 何が起きたか（要約）

B-2 Block 2 の残タスク（HO-B2-6/7/11/20/22/23）統合作業のなかで、MDX フロントマターの `phase` 値が `pre-launch | post-launch` の 2 値モデルのまま残っていることが判明。前日（2026-05-08）に確定済の 4 フェーズ構成（Phase 0/1/2/3）と整合せず、テンプレを書きながら旧前提を引きずっていた「先行SKU 4本」もハードコードしていたことに気付いた。phase を `phase-0/1/2/3` の 4 値へ統一・「先行SKU」概念ごと廃止・撤回設計と議論経緯を `docs/archive/` 配下へ完全分離、の 3 点を同セッション内で決着させた。

## 状況・背景

2026-05-08 のセッションで launch-plan を 4 フェーズ構成に全面再設計し、HO-B2-25「先行価格 ¥100/¥200・10 SKU・プレローンチクーポン」も同日撤回していた。翌日 2026-05-09 は B-2 Block 2 の残タスクとして MDX フロントマター標準・11 セクションテンプレ・CTA 設計・ガードレールをまとめた `content-design-templates.md` を新設する作業に着手していた。

着手早々、テンプレ §2.3 の `phase` 定義を書いている段階で、enum 値を `pre-launch | post-launch` のまま流用しようとしていることに気付いた。前日の決定では Phase 0（アプリ＋最小LP）／Phase 1（サイト本体オープン）／Phase 2（修正期間）／Phase 3（本リリース）の 4 段階になっており、`pre-launch / post-launch` の二分では Phase 1/2 の「サイトはあるが本リリース前」の状態が表現できない。さらに §3.3 の `<SkuCards />` コンポーネント仕様には「先行SKU 4本（S01/S05/S06/S07）」が直接埋め込まれており、これも前日の launch-plan 再設計とは整合していない。

## やり取りの中身

最初に上がった論点は「`phase` 値を 4 値にする以上、過去の `pre-launch | post-launch` 記述を全部置換する必要がある」というスコープの確認だった。grep の結果、影響範囲は content-design 系 5 ファイル＋pack-design 2 ファイル＋MEMORY.md＋既存ドラフト 2 本に及び、機械的置換では済まないことが判明した。各箇所で文脈に応じて Phase 0/1/2/3 のどれに対応するかを判断する必要がある。

次の論点は「先行SKU 4本」だった。これが残っていた理由は「Phase 1 で何を販売するか」が直前まで揺れていたためで、`S01/S05/S06/S07` という具体的な SKU リストはテンプレ §3.3 と研究メモ §5.6 にハードコードされていた。launch-plan の再設計後は「Phase 1 から全 140 SKU を通常価格 ¥200 で販売開始（売上ゼロでも非目的なのでOK・主動線はモニター無償）」が確定しているため、「先行SKU」という概念自体がもう要らない。`cta_mode: sku-preview` という enum 値も同時に廃止対象になった。

3 つ目の論点は「議論経緯と撤回設計をどう保管するか」だった。これまでは設計書本体に「直近セッション」セクションを残したり、撤回された設計を脚注的に残したりしていたが、grep で「あの設計どこ行った？」と探したとき到達できなくなっていた。`docs/archive/` を新設し、`sessions/YYYY-MM/` と `retired-designs/` に分離して「いつ・なぜ撤回されたか／何が代替になったか」を必ず明記する運用ルールに変更した。

## なぜそう判断したか

phase を 4 値にしたのは、Phase 1（サイト本体オープン後・本リリース前）と Phase 2（修正期間）が `pre-launch / post-launch` の二分では同じ箱に入ってしまい、CTA モード（`app-only` か `sku-full` か）を分岐できないからだ。記事ごとに「いつ公開され、その時点でどの CTA を出すか」が決まる以上、phase は公開タイミングと CTA モードの両方を表現できる粒度が要る。

「先行SKU」を概念ごと廃止したのは、販売 SKU を絞る集客上の利点が無く、商品ファミリー記事 4 本（タスク紹介）と SKU 販売数を分離した方が記事側の設計がシンプルになるからだ。主動線が「先行モニター応募・無償フルアクセス」に確定した時点で、有償 SKU の本数を絞る理由は完全に消えていた。テンプレへハードコードしてしまった事実そのものが「概念を残す限り再発する」ことの証拠になり、用語ごと grep で除去する判断に至った。

archive/ を新設したのは、現役の設計書に履歴を残し続けると本文の信号対雑音比が下がり、新規セッションでの参照効率が落ちるからだ。設計書本体は「現在の確定版」だけを持ち、撤回や議論経緯は archive 側に逃がす。設計書側に残すのは「→ archive/{path} 参照」の 1 行リンクのみ、というルールを採用した。

## 学び（一般化できるノウハウ）

1. **enum の値域変更は設計の整合性チェック機会** — `phase` の 2 値→4 値置換のような機械的に見える作業は、実際には各設計書が前提していたフェーズ感をあぶり出す。grep で全件洗うことで、テンプレに紛れ込んだ古い前提（先行SKU 4本）も同時に発見できた。

2. **「概念ごと廃止」は再発防止の最強手段** — ハードコードしてしまった事実は「概念を残す限り別の場所でも再発する」という証拠。用語そのものを grep で全削除し、enum 値も削除することで、復活させる余地を構造的に消す。

3. **現役設計書と履歴を物理分離する** — 議論経緯・撤回設計を本文に残すと信号対雑音比が下がる。archive ディレクトリへ逃がし、本文は「現在の確定版」だけにすることで、新規セッションでの参照効率が上がる。撤回設計には必ず「撤回日／代替／影響を受けたファイル」を書く運用ルールを併設する。
