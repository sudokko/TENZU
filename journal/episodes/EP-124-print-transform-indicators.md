# 紙面に変換指示子を導入する（回転=弧の矢印・移動=★●）と手設計モチーフの散布

## 何が起きたか（要約）

問題データの量産が一巡し、2026-07 後半は紙面と中身を磨くフェーズに入った。3本の流れが束になっている。(1) 07-17、模写全8巻の候補へ手設計モチーフ15問を散布投入した（`seed-motif-scatter.ts`・巻制約の自動検証つき・BOM 破損 JSON の修復も）。(2) 07-23、移動 Lv.2 の横巻・縦巻を「左右上下」1巻へ統合し（dir:hv・decisions §3.85）、atelier の編集で移動先●を選べるようにした。(3) 07-25、紙面に変換指示子を導入した——回転はペイン間の弧の矢印＋目じるし□、移動はみほんの★と行き先の●（§3.87・commit a655de5）。同時に回転 Lv.5 を右90°・左90°・180°の3角度混在へ改め、copy-lv5-vol2 へ手設計モチーフ15問を追加投入した（1610ee1）。共通する狙いは「この問題で何をするのか」を言葉でなく紙面自体が伝えること。幼児が文字を読めなくても解ける紙面、という商品思想の実装である。

## 状況・背景

生成器はランダムウォーク系で、制約を満たす図形は量産できても「絵になる図形」は出ない。模写巻の候補が無機質な図形に偏ったため、ひらがなラベル付きの手設計モチーフを差し込む方針になった。移動では検品中のオーナー実感「12問が全問同方向だと単調すぎる」が §3.85 の起点。回転では「Lv.5 を3角度混在にしたい」という要望を検討したところ、データは以前から1問1角度を保持していた（`answer.transform.deg`）のに、紙面はみほん→矢印→空欄の3点だけで角度も向きも表示していないことが判明した。混在の唯一のブロッカーは紙面だった。さらに移動 Lv.2 は published 12問が4方向混在なのに★●が紙面に出ておらず、印刷しても解けない状態が実害化していた。

## やり取りの中身

**手設計モチーフと品質ゲート**。07-17 の散布はロボット・自然・動物の顔・動物フォルム・食べ物の5系統×3問。投入スクリプトは本物の computeMetrics / baseDifficulty / COPY_LADDER で巻制約（斜め条件・スパン・D窓）を検証し、published・candidates・生成ライブラリ全変種と形シグネチャを照合する（いたチョコの田の字が既存の格子形と衝突し、非対称の溝へ修正した）。`--png` でコンタクトシートを出して Claude が目視検品し（とんぼ・みかづき・ソフトクリームは見た目で3回改稿）、`--write` で pending 投入。SEEDS 配列を差し替えれば第2弾を同じゲートで通せる設計にし、実際 07-25 の copy-lv5-vol2 追加15問につながった。副次で、外部ツール書き込み由来の BOM 付き JSON 3巻が atelier から読めない状態を発見し、正規形へ再書き出しして修復した。

**移動巻の統合と編集 UI**。TranslateDir に "hv" を新設し、1問1方向で巻内に左右上下を混在させる。旧縦巻は SKU_ALIASES でリダイレクト。atelier には点クリックで●を置く編集、「移動を選ぶ」ワンタッチ（形が収まらなければ盤面中央へ自動配置し直して成立させる）、一覧カードの方向バッジを実装した。旧生成の採用9問は形が縦いっぱいで縦移動が幾何的に不可能と分かり、hv 生成15問を pending へ補充した。移動選択 UI は 07-25 に盤面マス目表示へ刷新した。

**変換指示子の設計**。回転は、ペイン間の弧の矢印（弧の長さ＝まわす量・矢じり＝向き）と、両ペインの対応する隅に置く目じるし□。左上の点は右90°で右上、左90°で左下、180°で右下と別々の隅に落ちるため、目じるし1個で角度が一意に決まる。弧はペイン間ギャップだけでは豆粒で 1/4 周か半周か読めないため、ドットのないペイン端 10% まで食い込ませて半径を確保した（rotArcRadius）。移動はみほん側に★（図形の起点＝辞書順最小点）、かく側に●（行き先）を置く。幾何は print.ts に集約し、プレビュー SVG と PDF が同じ数式を呼ぶ。回転 Lv.5 はラダーに angle:mixed を新設し、生成器が退化・公開済みかぶりを角度ごとに判定して採用最少の角度へ配る（実測20問で右7・左7・180°6）。atelier には角度ピッカーも追加した。

## なぜそう判断したか

**表記を絵記号のみにした理由**。度数や文字を使わない理由は2つ。①主戦場は就学前後で「90°」が読めない。②PDF は Courier しか埋め込んでおらず日本語を印字できない。ユーザー制約と技術制約が同じ方向を向いたことで、言葉に頼らない紙面という商品思想がむしろ純化された。オーナーは複数案から弧の矢印＋目じるし案を選んだ。

**手設計にも生成系と同じ検証を通した理由**。巻制約は ladder.json が SSOT であり、手投入だけ例外にすると巻の難易度秩序が静かに壊れる。本物の検証関数とかぶり照合を再利用したスクリプトを通せば、手設計でも「その巻に置いてよい問題」であることを機械的に保証できる。

**紙面を仕様の最終検収先とみなした理由**。移動12問はデータとして完全に正しかったが、紙面に指示子がなく商品として解けなかった。スキーマの正しさは最終出力の正しさを含意しない。変換系タスクは「紙面だけで解けるか」を検収基準にする。

## 学び（一般化できるノウハウ）

1. **指示子は言語でなく幾何で設計する** — 読者が文字を読めない、または出力基盤が文字を出せないとき、位置と形だけで意味が一意に決まる記号系を探す。対応点が変換ごとに別の場所へ落ちる性質を使えば、記号1個で操作を特定できる。制約は表現を純化する道具になる。

2. **手作業データにも自動生成と同じ検証器を通す** — 人手投入用の例外経路を作ると制約体系が静かに崩れる。生成パイプラインの検証関数をそのまま再利用した投入スクリプトにすれば、手設計の自由と制約の秩序を両立できる。

3. **「データは持っているが表示していない」ギャップを疑う** — スキーマが情報を保持していても、最終出力に出ていなければ機能は存在しないのと同じ。新しい変種（角度混在など）を足す前に、既存情報が最終出力へ届いているかを先に検収する。
