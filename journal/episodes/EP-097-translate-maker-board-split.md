# 平行移動メーカー——モード切替を捨て「盤面の役割分離」で意図を表す

## 何が起きたか（要約）

メーカー 9 タスク（模写・鏡・回転・欠け補完・拡大・縮小・重ね・折り重ね・平行移動）の最後＝平行移動メーカー `/maker-translate` を実装した。拡大メーカーの near-clone で、新規 2 ファイルのみ、print.ts・schema・data・maker.css は無改修。仕様は「起点★（自動＝最初に描いた点）から、移動先●を 1 クリックするだけで移動ベクトル `(dc, dr)` を自動算出」。最大の設計転換は操作モデルにある。初案は「図形を描く／移動先を置く」というセグメントトグル（同じ盤面の役割を OFF/ON で切り替える）だったが、オーナーが「直感的でない」と指摘し、さらに移動先ボタンが図形未描画時に disabled で『反応しない』という二重問題が出て撤回した。代わりに盤面そのものを役割で分離した——左盤面は図形を描く専用、右盤面（結果盤面）は移動先●を置く専用。どちらの盤面をクリックしたかで意図が決まり、モード切替（トグル）という概念が消える。動的キャプションで次のアクションを誘導する。tsc・幾何アサーション 6/6・全ルート 200 がクリーン。

## 状況・背景

平行移動はメーカー 9 個目＝最後だ。`maker-shrink`（EP-096）と同じ「拡大メーカーを複製して幾何だけ差し替える」型で作った。マーカー描画は print.ts ではなくメーカー内の SVG 生成にハードコードされているので、移動先●の追加もメーカー内で完結する。

紙面は二面式にした——左がもと図＋★起点、右の出題が空欄＋●「ここへ」（移動先）、右の解答が平行移動した図＋★（着地位置）。子は★が●に重なるように図を写す。重なりがなく図を大きく描け、「きてん→ここへ」のラベルだけで意味が通る（演算子テキストなし・矢印のみ）。起点は拡大と同じ思想で自動（最初に描いた点 `edges[0].a`）。だからオーナーが手で指定するのは移動先●だけだ。移動量の数値入力はなく、ベクトル `(dc, dr) = 移動先 − 起点` を自動算出する。

問題は「移動先●をどう置かせるか」というインタラクションだった。

## やり取りの中身

**初案＝セグメントトグル。** 一つの編集盤面に「図形を描く／移動先を置く」というトグルを置き、ON/OFF で盤面のクリックの意味を切り替える設計だった。OFF なら線を描き、ON なら移動先を置く。

**二重の問題で撤回。** これが二つの理由で破綻した。一つはオーナーの「直感的でない」という指摘——同じ場所をクリックしているのに、トグルの状態によって全く違うことが起きる。子が今どちらのモードかを覚えていないと操作を間違える。もう一つは実装上の事故で、移動先を置くボタン（あるいはトグル）が図形未描画時に disabled になり、押しても『反応しない』状態が生まれた。「押せるはずのものが反応しない」と「同じ操作が状態次第で意味を変える」が重なって、操作が分からなくなった。

**改訂＝盤面の役割分離。** トグルを捨て、盤面そのものを役割で分けた。左盤面は図形を描く専用、右（結果）盤面は移動先●を置く専用。子は「左で描く／右で移動先を置く」と、場所で操作を覚える。どの盤面をクリックしたかで意図が一意に決まるので、モード（状態）という概念そのものが要らなくなる。右盤面の PaperSVG に `onDotClick={handleTarget}` と `targetAt` を渡し、動的キャプションで誘導する——図形がなければ「まず左で描いてね」、移動先未設定なら「ここをクリックして移動先●」、収まるなら「クリックで移動先を変更」、はみ出すなら「枠からはみ出します」。★優先描画なので着地点は★で出て、はみ出し時は●が見える、という挙動を 1 コンポーネントで賄える。

**核の純関数。** `computeTranslate(edges, target, n) → { edges, star, targetMark, dc, dr, fits }`。target が null（移動先未設定）なら移動なし＝fits は true で警告を出さない。マーカー描画は 3 レンダラ（画面・PDF・ミニプレビュー）に `targetAt?` を追加し、★優先で中空●＋芯点＋「ここへ」を出す。グリッドは 3/4/5/6（family 標準・既定 4・拡大の 5-8 から変更）。平行移動後が枠内に収まる制約（`fits = inGrid(R, n)`）と、移動先＝起点の `isZeroMove`（移動ゼロ）は保存をブロックする。

## なぜそう判断したか

トグルを盤面分離に置き換えたのは、「モード（隠れた状態）」がインタラクションの分かりにくさの根だったからだ。トグルは UI 上の一箇所（盤面）に二つの意味を時間で多重化する。利用者は「今どちらの意味か」を頭の中の状態として保持しなければならず、それを忘れると誤操作する。子ども相手では特に重い負担だ。

盤面を二つに分けると、二つの意味が空間で分かれる。状態（OFF/ON）を場所（左/右）に写像したわけだ。こうすると「今どのモードか」を覚える必要が消える——左を触れば描く、右を触れば移動先、それだけ。モードという概念自体が UI から消滅する。隠れた状態を可視の構造に置き換えると、説明もモード表示も要らなくなる。

disabled ボタンの『反応しない』問題も、この置き換えで構造的に消えた。トグル設計では「図形がないと移動先は置けない」という前提を disabled で表現するしかなく、それが『押しても無反応』に見えた。盤面分離なら、図形が無い状態で右盤面を触ったら「まず左で描いてね」と動的キャプションで返せる。「無反応」が「次にすべきことの案内」に変わる。禁止を黙って表す（disabled）のでなく、次の一手を語る（キャプション）方が、利用者は迷わない。

起点を自動（最初に描いた点）にしたのは拡大・縮小と揃えるためだ。三部作で「最初に描いた点が変換の基準点」という規約を共有すると、子は一つのルールで三タスクを操作できる。

## 学び（一般化できるノウハウ）

1. **「隠れた状態（モード）」を「可視の構造」に写像すると、トグルが消える** — 一つの UI 要素の意味を ON/OFF で切り替えるトグルは、利用者に「今どちらか」を記憶させる負担を課す。同じ二つの意味を二つの場所（ここでは左盤面＝描く／右盤面＝移動先）に空間的に分けると、状態を覚える必要が消え、モードという概念そのものが UI から消滅する。状態の時間多重化を空間分離に置き換えるのは、迷いを減らす定石だ。

2. **「禁止を disabled で表す」より「次の一手をキャプションで語る」** — 前提が満たされない操作を disabled にすると、利用者には『押せるはずが反応しない』と見える。代わりにクリックを受け付けて「まず左で描いてね」と次のアクションを案内すると、無反応が誘導に変わる。動的キャプションで「今・未設定・成立・はみ出し」を出し分ければ、状態表示も別途要らない。禁止より誘導。

3. **同族タスクは「基準の決め方」の規約を共有させる** — 拡大・縮小・平行移動の三部作はすべて「最初に描いた点」を変換の基準（固定点／起点）にした。タスクごとに基準の決め方を変えると子は都度学び直すが、規約を揃えれば一つのルールで族全体を操作できる。関連タスク群では、共通化すべきは実装だけでなく「ユーザーが覚えるルール」でもある。
