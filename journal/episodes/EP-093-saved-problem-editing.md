# 保存済み問題をその場で編集する（中央エディタを編集モードに切り替える案A）

## 何が起きたか（要約）

「保存済みの問題をあとから編集したい」というオーナーの気づきから、保存済みセルに ✎ ボタンを置き、押すと中央のエディタがそのまま「編集モード」になって元の問題を読み込み、その場で上書き保存する機能を模写メーカー（MakerApp）に実装した。新規追加ではなく上書きで、位置順・PDF 選択・名前は保持する。編集中は題名が「問題 #03 を編集中」になり、対象セルに破線リングと「編集中」バッジが付き、保存ボタンが「変更を保存」へ変身し、グリッドサイズはロックされる。作りかけや編集中の変更がある状態で別の問題を編集しようとすると `window.confirm` で破棄を確認する。これは模写メーカーだけのプロトタイプだが、全メーカー共通のニーズで、本命は他メーカー（重ね・折り重ね・分解＝edgesA/edgesB の2盤、鏡・回転＝TransformSpec）への横展開にある。dev 実機で tsc 0・コンソールエラー 0、#01 を1本→2本にその場更新できることまで確認した。

## 状況・背景

おためし点描写メーカーは、中央のキャンバスで問題を1つ作り、保存すると下の一覧にサムネイルとして並んでいく構造だ。並んだ問題はまとめて PDF に出力できる。だが「並べたあとに、3問目だけ線を1本足したい」となったとき、これまでは作り直して保存し直すしかなかった。オーナーの言葉では「保存済みの問題を編集したい。今までのすべてのメーカーで共通ニーズ。UI 表現が悩ましい」。機能そのものより、「どう操作させるか」が論点だった。メーカーは複数あり、模写・鏡・回転・重ね・折り重ね・分解・欠け補完がそれぞれ別ページとして存在する。同じ編集体験をどのメーカーにも載せられる形にしておく必要があった。

## やり取りの中身

入口の UI で3案を比較した。

| 案 | 操作 | 却下理由 |
|---|---|---|
| A | 各保存セルに ✎ ボタン（× の左隣）→ 中央エディタが編集モード | 採用 |
| B | サムネイルのクリック自体を「編集」に変更 | サムネのクリックは PDF 選択フローに使っており、それを壊す |
| C | サムネのダブルクリックで編集 | モバイルでダブルクリックは発見されない |

採ったのは案A。各保存セルの右上、削除の × の左隣に ✎ を置く。押すと中央エディタがその問題を読み込み、編集モードに入る。新しい問題を増やすのではなく、その問題を**その場で上書き**する。位置順・PDF 選択・名前はそのまま引き継ぐ。

編集モードに入ったことを5つのキューで示した。①題名が「問題 #03 を編集中」になり teal の ● アクセントが付く。②対象セルに teal の破線リングと「編集中」バッジが付く（選択中を示す実線リングと区別する）。③保存ボタンの文言が「この問題を保存する」から「変更を保存」に変わる。④隣に「やめる」ゴーストボタンが出る。⑤グリッドサイズのボタンがロックされる。⑤は、編集中にグリッドを変えると `changeGridSize` が辺データを消してしまう事故を防ぐためだ。

未保存ガードも入れた。作りかけ、または編集中で変更がある状態で別の問題の ✎ を押すと `window.confirm` が出る（「作りかけの問題があります。破棄して編集しますか？」、編集中は別文言）。変更が無ければ確認なしで切り替える。保存後は編集モードを解除して新規モードに戻りキャンバスを空にする。編集中の問題を削除したら編集モードも自動で解除する。

実装は `MakerApp.tsx` に `editingId` / `isEditing` の状態、未保存判定の `edgesEqual` ヘルパ、`startEdit` / `cancelEdit`、`saveCurrent` の編集分岐、`resetCanvas` の共通化、`deleteSaved` の編集解除、`changeGridSize` の編集中ガードを足し、`maker.css` に破線リング・バッジ・編集中の題名・ロックボタン・「やめる」ボタンのスタイルを足した。

dev 実機（port 3001）で確認した。2問保存→✎#01 で編集モード（題名・リング・バッジ・グリッドボタン disabled・「変更を保存」・「やめる」・線のロード、すべて確認）→1本追加→「変更を保存」で **#01 が1本→2本にその場更新・新規追加なし・位置01維持・#02 は不変**。「やめる」で破棄でき #02 不変。未保存ガードは両分岐（拒否で作りかけ維持／承認で破棄して読込）確認。

## なぜそう判断したか

案A を採ったのは、既存の操作を壊さず、モバイルでも発見できる入口だからだ。案B はサムネのクリックを奪うが、サムネのクリックはすでに「この問題を PDF に含める／外す」の選択に使われている。1つの操作に2つの意味を持たせると、どちらのつもりで押したかが曖昧になる。案C のダブルクリックは、デスクトップでは通じてもタッチ操作では誰も気づかない。明示的な ✎ アイコンなら、操作の意味が一目で分かり、タップ対象としても成立する。

「新規追加ではなく上書き」にしたのは、編集の自然な期待がそうだからだ。3問目を直したいのに、直すたびに4問目・5問目が増えていくのは編集ではない。位置・PDF 選択・名前を保持するのは、「同じ問題の中身だけ変える」という意図に一致させるためだ。

視覚キューを過剰なほど重ねたのは、「いま自分がどのモードにいるか」を見失わせないためだ。中央エディタは新規作成にも編集にも使う同じ場所なので、見た目が同じだと「これは新しい問題なのか、3問目を直しているのか」が分からなくなる。題名・リング・バッジ・ボタン文言・ロックの5つで、編集中という状態を画面のあちこちから同時に主張させた。

グリッドロックと未保存ガードは、データを失う事故を物理的に塞ぐためだ。編集中にグリッドを変えれば辺が消え、確認なしに別の問題へ飛べば作りかけが消える。どちらも「気をつける」では防げないので、操作そのものを止めるか確認を挟むかで対処した。

そして模写メーカー1つで止めてプロトタイプにしたのは、全メーカーに同じパターンを展開する前に、操作感をオーナーに確認してもらうためだ。横展開は機械的にできるが、操作の良し悪しは展開前に1つで確かめたほうが手戻りが小さい。

## 学び（一般化できるノウハウ）

1. **同じ場所を再利用する編集 UI は、状態キューを過剰に重ねる** — 新規作成と編集に同じエディタを使い回すと、見た目だけでは今どちらのモードか分からなくなる。題名・対象セルの装飾・保存ボタンの文言・取り消しボタンの出現・関連操作のロック、というように複数箇所から同時に「編集中」を主張させると、ユーザーがモードを見失わない。1箇所のラベルだけでは足りない。

2. **データを失う操作は「注意」でなく「物理的に止める」** — 編集中のグリッド変更（辺が消える）や、作りかけを残したままの画面遷移は、注意喚起では防げない。値を消す操作はボタンを無効化し、破棄が伴う遷移は確認ダイアログを挟む。事故の経路を操作レベルで塞ぐ。

3. **横展開が本命の機能は、1つでプロトタイプしてから一斉に広げる** — 全メーカー共通のニーズでも、まず1メーカー（模写）で操作感を確定させ、オーナー確認を経てから他へ広げる。データ表現が違っても（模写は `edges`、重ね系は `edgesA/edgesB`、変換系は `TransformSpec`）、「編集対象を識別する ID・元データの読み込み・その場上書き・✎ から編集モード」というパターン自体は読み替えで流用できる。確定したパターンを横に複製するのは安全だが、未確定のパターンを最初から全展開すると手戻りが全メーカーに波及する。
