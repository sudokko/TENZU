# 認証方式を3AIで再評価し「メール一本」へ撤回する（3者一致だけを信用する使い方）

## 何が起きたか（要約）

メーカー有償化の認証方式を、Claude（反証検証担当）・ChatGPT・Gemini の3AIで Deep Research し、判断材料を整理した。オーナーの当初意向は「Google＋LINE を初手から＋メール OTP・Clerk 不採用・自前(Auth.js) か Supabase か」だったが、セッション後半で方針が転換した——「Auth.js＋ソーシャルログイン＋DB は負担が大きい、できればやりたくない」。結論は **当面メール一本（メーカー＝OTP／商品＝マジックリンク）・DB なし・不達は手動リカバリ CLI で個別対応**。ソーシャルログインと DB は却下ではなく先送りで、3AI の分析はそのまま再開時に使える。最大の収穫は AI の使い方そのものだった。3者が一致した項目だけを「バンクしてよい確定」として9点抽出し、1社しか言わない数字・2社が踏んだ事実誤認は反証で落とした。

## 状況・背景

メーカー有償化（[EP-094](EP-094-maker-monetization-tiers.md)）は HMAC 署名 Cookie ＋ Stripe を会員台帳にする DB なし構成で、ログインはマジックリンクだった。オーナーの不安は「マジックリンク単独でリリースして大丈夫か」。メールアプリ内蔵ブラウザでリンクを開くと Cookie が別コンテキストに落ちる、キャリアメールが届かない、といった既知の弱点がある。そこで認証方式を腰を据えて再評価することにした。論点は二つ。①メール認証の運用に足りないものは何か。②日本での CVR を考えると LINE ログインを初手から入れるべきか、その場合どんな実装（自前 Auth.js か Supabase か）か、だった。

## やり取りの中身

3AI に役割を割り振った。ChatGPT と Gemini に Deep Research をかけ、Claude は両者の出力を**反証検証**する側に回す。AI の生成物を鵜呑みにせず、相互に潰し合わせる構図だ。

**3者一致＝確定9点**。一致したものだけを採用候補にした。要点は——(1) マジックリンク単独の長期運用は不可、(2) メール OTP フォールバック必須（別ブラウザ／メールアプリ内ブラウザの Cookie 断絶を6桁コードで救済）、(3) キャリアメール到達対策を本番前に実測（SPF/DKIM/DMARC＋SES カスタム MAIL FROM のアライメント。docomo の2025年2月厳格化対策）、(4) 最小の状態ストアが要る、(5) LINE ログインが日本の CVR 本命、(6) Stripe は Webhook で権限確定（署名検証・内部 ID 紐付け・冪等・解約で剥奪）、(7) Customer Portal は認証済み画面から短命 URL を生成、(8) OWASP の Cookie 一式とユーザー列挙対策、(9) パスキーは最終到達点（方向のみ）。

**反証で落とした地雷**。パスキー成功率を ChatGPT は「93% 対 63%」、Gemini は「99.9%」と出した。**両方却下**——根拠が示されず、しかも2社の数字が食い違う。バラついている時点で信用できない。サインイン時間や他社サービスとの速度比較も同様に落とし、「速い・強い」という方向だけを採った。EC でのパスキー採用率と離脱率の幅は3者が一致したぶんだけ生き残った。Gemini が警告した Next.js Middleware バイパスの脆弱性は、稼働中の Next 16.2.6 で対策済みと確認し、原則（Middleware の認可を過信せず DAL 層でも再検証）だけを採った。さらに2社は「実装は jose 前提」「Supabase は管理画面のコピペで LINE が開通する」と書いたが、前者は実際には Node 標準 crypto の HMAC 自前署名で事実誤認、後者は次項の通りハルシネーションだった。

**Supabase に LINE ネイティブは無かった**。「Supabase なら LINE がすぐ使える」を web 検索で検証すると、Supabase の組み込みプロバイダに LINE は無い（Google・Apple・Azure 等のみ）。2社の主張は誤りで、Supabase を採っても日本の主役 LINE は結局カスタム OAuth の手作業になる。一方 Auth.js (NextAuth v5) は LINE も Google もビルトインで、Postgres を持ち込める。LINE 中心の日本ケースでは Auth.js のほうが素直、という結論になった。

## なぜそう判断したか

**「メール一本・DB なし」を選んだ理由**。DB が要るか要らないかは、保持すべき状態がどこにあるかで決まる。現状を分解すると、会員マスタは Stripe（Customers／Subscriptions が台帳）、ログイン状態は署名 Cookie 自身（HMAC で内部 ID・tier・失効時刻を封じ、サーバー検証のみで DB 参照なし）、リンク発行は署名トークンで状態不要。emailが唯一のキーかつ唯一の手段だから DB なしで閉じる。ここに Google＋LINE を足すと話が変わる。**LINE はメールを返さないことがある**（email は任意スコープでユーザーが拒否できる）ため Stripe に email で紐付けられず、`LINE userId → stripe_customer` の永続マッピングが要る。加えて OTP・Google・LINE が同一人物のときに束ねないと「課金したのにログインできない」事故になる。だから**ソーシャルログインを入れた瞬間に DB は確定**——逆に言えば、入れなければ DB は要らない。「負担が大きいからやりたくない」というオーナーの感覚は、この構造を正しく言い当てていた。最小コストでローンチするには、ソーシャルログインごと先送りするのが一番効く。

**「3者一致だけ信用する」を方法論にした理由**。AI の Deep Research は、それらしく具体的な数字を返すほど検証が要る。今回まさに、根拠なき成功率という分かりやすい地雷を2社が踏んだ。1社の主張は仮説、2社一致でも事実誤認はあり得る（Supabase の LINE がそうだった）、3者一致は確度が一段上がる——この階層で扱うと、生成物を採否のシグナル付きで使える。反証担当を1枚噛ませる価値はここにあった。

**先送りでも調査を捨てなかった理由**。DB 要否の理屈・自前 vs マネージドの判断材料・梅竹松のロードマップは、ソーシャルログインを入れる日が来たらそのまま使える。今やらない判断と、分析を残す判断は両立する。

**手動リカバリで穴を塞いだ理由**。メール一本の唯一の弱点はメール不達だ。これをオーナー専用ローカル CLI（`web/scripts/recover.mjs`・依存ゼロ）で塞いだ。email や Stripe の各種 ID で購入を横断検索し、メーカーならログインリンク・商品なら DL リンクを再発行する。発行関数は本番と同一を流用。メーカーのログインリンクは検証時に Stripe を再照合するので、解約者には自動的に無効になる。低頻度の例外を仕組みで完全自動化せず、人手で安全に拾う——ローンチを止めないための割り切りだ。

## 学び（一般化できるノウハウ）

1. **複数 AI の Deep Research は「一致の段数」で信用度を階層化する** — 1社の主張は仮説、2社一致でも事実誤認は残る、3者一致で確度が一段上がる。特に根拠を伴わない具体的な数字（成功率・所要時間）は、各社で値が食い違ったら即落とす。反証専任の1枚を噛ませると、もっともらしい誤りを採否のシグナル付きで扱える。

2. **DB が要るかは「保持すべき状態が外にあるか」で決まる** — 会員台帳が Stripe、ログイン状態が署名 Cookie 自身なら、email が唯一キーで DB なしに閉じる。ソーシャルログインは、メールを返さない事業者の名寄せと複数手段の重複防止のために永続マッピングを呼び込む。「機能を一つ足すと DB が芋づるで付いてくるか」を見れば、最小構成で削れる対象が見える。

3. **低頻度の例外は自動化より手動リカバリで安く塞ぐ** — メール不達のような稀な失敗を完全自動化すると、状態ストアや再送ロジックが膨らむ。本番と同じ発行関数を使うオーナー専用 CLI を1本置けば、ローンチを止めずに個別対応できる。発行物が Stripe を再照合する設計なら、解約者への誤発行も自動で防げる。
