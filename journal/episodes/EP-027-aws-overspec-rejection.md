# AWS Bedrock/Kendra/Lex/DynamoDB 検討→全部不採用

## 何が起きたか（要約）

B-2 のコンテンツ設計フェーズで FAQ 運用方法を議論した際、AWS Bedrock（生成 AI による FAQ 自動応答）・Kendra（エンタープライズ検索）・Lex（チャットボット UI）・DynamoDB（FAQ データストア）の導入を検討したが、4 サービス全てを不採用とし、Next.js 標準 MDX 運用＋長短ハイブリッド型 FAQ（C+案）に着地した。1 人運営という文脈での「機能ではなく運用しきれる複雑度で決める」原則が適用されたケースだ。

## 状況・背景

B-2 Block 1（IA 骨格設計）が完了した後、FAQ の運用方法をどう設計するかという論点が浮上した。TENZU の FAQ は「現時点での想定 Q&A」を事前作成するだけでなく、先行モニターからの問い合わせや購入者のフィードバックから逐次追加されることが前提だ。追加が大前提の運用形態であり、通常の記事と設計が異なる。

TENZU は技術スタックとして AWS Amplify を採用しており、AWS サービスが利用しやすい環境にある。そのため、検索機能や AI 応答機能を AWS の豊富なマネージドサービスで補完するという方向性が自然に検討対象に上がった。

## やり取りの中身

### 検討した AWS スタック

| サービス | 検討した用途 | 不採用理由 |
|---|---|---|
| AWS Bedrock（Knowledge Base） | FAQ テキストを RAG で検索し、生成 AI が自然言語で回答 | 1 人運営で生成 AI 応答の品質保証・ハルシネーション管理は現実的でない。FAQ 件数 50 件程度では RAG の恩恵が少ない |
| Amazon Kendra | FAQ コンテンツ全体に対するエンタープライズ検索 | 月額固定費（$810〜）とチューニング工数が個人運営規模に対して過剰 |
| Amazon Lex | FAQ 向けチャットボット UI | FAQ 件数が数十件レベルでは Lex を設計・維持するコストが機能対効果を大幅に超える |
| Amazon DynamoDB | FAQ データの格納・クエリ | MDX ファイルをそのまま git 管理すれば DynamoDB は不要。JSON として静的配信でも十分 |

### 採用した運用（C+案: 長短ハイブリッド型）

| FAQ タイプ | 設計 |
|---|---|
| 長い FAQ（SEO KW あり） | 個別ページ（`/{slug}/`）＋集約ページへの掲載 |
| 短い FAQ（SEO KW なし） | 集約ページのみ（個別 URL なし） |

MDX フロントマターで `faq_format: long / short` を分岐させ、カテゴリは `product / payment / shipping / support` の 4 分類。検索機能は静的サイト内テキスト検索で対応し、件数が 100 件を超えた段階で Algolia 等の検索特化 SaaS を検討する余地を残した。

### FAQ 運用の三案比較

| 案 | 構造 | SEO | UI | メンテ |
|---|---|---|---|---|
| A. 個別ページ完全分離（1問1ページ） | ◎ | ○ | ○ | 短い FAQ が薄いコンテンツ扱いになるリスク |
| B. 集約 1 ページ集中 | △ | ◎ | △ | 個別 KW 最適化が弱い |
| C+. 長短ハイブリッド | ◎ | ◎ | ◎ | 採用 |

ユーザーから「短い FAQ が単独ページだと薄い」という直感的な問題提起があり、C+案を選んだ。

## なぜそう判断したか

TENZU の FAQ は当面 50 件程度で、エンタープライズ級の検索基盤が必要になる規模ではない。AWS のサービスが「技術的に使える」からといって「使うべき」にはならない。マネージドサービスの本当のコストは月額固定費だけでなく、設定・運用・チューニング・障害対応の工数を含む。

1 人運営の基準は「自分がメンテナンスし続けられる複雑度」だ。Bedrock を導入すれば生成 AI 応答の品質保証が恒久的な運用タスクになる。Kendra を導入すれば月額コストが発生し続ける。どちらも TENZU の現フェーズでは正当化できない。

MDX + git の組み合わせは、FAQ の追加・修正がコードレビューと同じフローで回せるという利点を持つ。Pull Request で FAQ を追加し、マージでデプロイされる。この運用は git に慣れた個人開発者にとって最もオーバーヘッドが少ない。

「使えるから使う」という誘惑への抵抗は TENZU の設計全体に一貫している（Cognito の過剰利用を避けた EP-014、Storybook/Chromatic を不採用にした EP-028 と同じ思想）。

## 学び（一般化できるノウハウ）

1. **「使えるから使う」を疑う** — クラウドサービスは「技術的に使える」と「運用として採用すべき」は別の問いだ。マネージドサービスは初期構築コストだけでなく、運用・チューニング・障害対応の継続的な負荷も抱える。

2. **個人運営の基準は「運用しきれる複雑度」** — 機能の豊富さではなく、自分のキャパシティで維持し続けられるかどうかが採用基準になる。「後で必要になれば追加できる」前提で、今必要ない機能を外す決断をする。

3. **MDX + git で済むことは多い** — 構造化データを別 DB に置く前に「MDX で試してみる」というアプローチは、個人開発の文脈では多くのケースで正解に近い。Algolia 等の専門サービスへの移行判断は、実際の規模感が見えてからで十分。
