# 全10メーカーの重複 85-90% を core へ抽出する（WS3 の1コミット1移行）

## 何が起きたか（要約）

「プログラムが散らかってる」というオーナーの依頼を起点に、Claude が web コードベース全域を洗い直した。山場は WS3＝正方格子メーカー10種の共通化である。各メーカーは約1,300行・計約13,500行が 85-90% 同一コードの fork で、約48の関数が全ファイルに複製されていた。共有 SSOT として `app/maker/core/` を新設し、WS3-a〜g の7コミット（1コミット＝1メーカー群移行）で段階的に移した。各本体は 300-1,050 行へ減少（鏡 1288→593・模写 1421→661 など）。リファクタ前後で出力 SVG のバイト一致を確認する回帰ハーネスで挙動不変を担保した。同日に死骸コード削除（WS1）と絵柄ライン残骸の掃除（WS2）も実施し、以後「メーカーを直すときは core を直す」が運用原則になった。

## 状況・背景

メーカーは模写1本からコピペ横展開で増え、正方格子系だけで10種（模写・鏡・回転・欠け補完・重ね・折り重ね・分解・拡大・縮小・平行移動）に達していた。EP-099 の quickbar 改修のような一斉修正では同じ差分を10ファイルへ当てる必要があり、並列サブエージェントで展開してしのいでいた。見た目は共有 maker.css への集約で1点化済みだったが、ロジックと構造は複製されたままで、修正コストが台数に比例していた。branch は deploy/amplify。作業ツリーにはオーナーのタグライン第4世代実装 WIP が未コミットで同居しており、そこへ一切触れない制約付きの作業だった。

## やり取りの中身

**削除→掃除→共通化の順**。WS1 で死骸を削除した——本番未連携の立体試作 maker-solid-proto（437行）・旧デザイン比較用 products-b・インポートゼロの lucide-react。WS2 で商品廃止済みの絵柄ラインの残骸（ladder.json の motif 7 SKU＋候補 JSON）を消したが、単純削除では温存機能 seed-motif-inspo が例外で壊れると判明し、参照される5巻分の帯を gen/motif.ts へ verbatim 移設した。「孤立候補」と誤認しかけた overlay-lv3-vol1.json は検品済みライブ SKU と分かり温存。死骸を先に消したのは、死んだコードまで core 参照へ移行する無駄を避けるためである。

**core の切り出し**。共有部を8モジュールに分けた——幾何ユーティリティ・ページ枠（タスク固有描画は renderCell 注入）・PDF 書き出し・盤面コンポーネント（render prop 方式）・履歴と保存リストのフック・用紙レイアウトのフック・画面 chrome・純変換。一方、タスク固有の描画（平行移動・拡大・縮小の★マーカー置換 pane、欠け補完の点線 R 辺、分解の ghost 下敷き、演算子グリフ、3セル印刷シート）は各ファイルに温存し、byte-identity を重複解消より優先した。

**1コミット＝1メーカー群の移行**。WS3-a で core 抽出と鏡の移行を同時に行って設計を検証し、以後 b 模写（DoneScreen 分離）→ c 回転・平行移動 → d 拡大・縮小 → e 欠け補完 → f 重ね・折り重ね・分解 → g 立体（部分適用）と進めた。各コミットで tsc --noEmit と next build のグリーンを維持した。

**SVG フィクスチャ回帰**。各メーカーの buildPageSvg を一時 export し、固定入力で {メーカー}×{問題/解答}×{並び}×{記名欄}＝72本の SVG 文字列を採取、リファクタ前後でバイト一致を確認した。PDF はタイムスタンプ入りで比較不能なため、その手前の SVG 文字列を比較面に選んだ。ハーネスは作業後に削除し、仕上げに dev preview で模写・鏡・折り重ね・立体を実機スモークした。

## なぜそう判断したか

**byte-identity を重複解消より優先した理由**。リファクタの価値は「挙動が変わらない」ことの証明で決まる。共通化率を上げるために出力へ微差を許すと、全メーカー×全ページの目視検品が必要になり、個人運営では回らない。バイト一致なら機械照合だけで安全を言い切れる。共通化しきれない固有部分を残すのは、この証明を成立させるための正しいトレードオフだった。

**1コミット＝1移行にした理由**。一括移行では後から問題が出たとき、どの移行で壊れたかを特定できない。メーカー群単位でグリーンなコミットを積めば bisect で切り分けられる。最初の WS3-a を「core 抽出＋鏡1本」にしたのも、抽出した抽象の妥当性を実移行1本で検証してから残りへ流すためである。

**立体メーカーを部分適用に留めた理由**。立体模写は矩形格子・style 付き辺・localStorage 保存と前提が異なり、行数も元々リーンだった。無理に正方格子の core へ合わせると core 側に条件分岐が増え、共通部の純度が下がる。共有できる周辺部品（chrome・PDF 書き出し・PNG 変換）だけを再利用した。EP-099 で共有 CSS に感じた「波及の単一点」の効きを、今回はロジックと構造の層まで拡張した形になる。

## 学び（一般化できるノウハウ）

1. **横展開 fork の共通化は「出力のバイト一致」を検証面に据える** — 挙動不変を人の目で保証するのは非現実的。決定的な中間表現（ここでは SVG 文字列）を固定入力のフィクスチャで前後比較すれば、機械照合で回帰を証明できる。タイムスタンプ等の非決定要素が混ざる最終出力ではなく、その手前を比較面に選ぶのが要点。

2. **段階移行は1コミット＝1移行単位で bisect 可能性を買う** — 一括移行は失敗時の切り分けが総当たりになる。移行単位ごとにコンパイル・ビルドが通るコミットを積めば、将来の調査は二分探索で済む。最初の1単位で抽象の設計を検証してから、残りを同じ型で流す。

3. **コピペ横展開は返済期を決めて使う** — fork 横展開は新バリエーション追加を最速にする正しい初手だが、全体修正のコストが台数に比例し始めた時点が返済の合図。返済時は共通と固有の境界を理想論でなく「今の実出力」で引き、前提の違う個体（今回の立体）は無理に一般化しない。
