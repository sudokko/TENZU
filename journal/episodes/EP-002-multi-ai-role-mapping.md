# ChatGPT / Gemini / Claude の役割分担マップが固まるまで

## 何が起きたか（要約）

TENZU 設計プロセスを通じて、ChatGPT / Gemini Deep Research / Claude Code の 3 AI を「並列ブレスト」「採用判定」「実装パートナー」として明確に役割分担する運用が定着した。当初は Claude Code 単独で全工程を回す想定だったが、B-2 Block 1 後の引用論文補強で Gemini の捏造が発覚したこと（→ EP-001）と、先行リリース再設計の場面で複数 AI への諮問が有効だと分かったことが転機だった。

## 状況・背景

プロジェクト初期は Claude Code をメインエージェントとして使い、Web リサーチ・設計書更新・ドキュメント管理を一元的に任せる方針だった。ChatGPT や Gemini は補助的に使うことはあっても、Claude Code との役割分担を意識的に設計していたわけではなかった。

転機となったのは 2 回のできごとだ。1 回目は 2026-05-07 の引用論文補強セッションで Gemini DR が著者名・誌名・DOI を複数件捏造していたことが確認されたこと。2 回目は 2026-05-08 の先行リリース再設計セッションで、Claude Code だけでなく ChatGPT と Gemini にも同じ問いを投げ、両者の推奨を踏まえてユーザーが独自判断を下したことだ。

## やり取りの中身

### 各 AI の特性（実体験ベース）

TENZU 設計プロセスを通じて確認された各 AI の特性を整理する。

| AI | 強み | 弱み | 主な使い道 |
|---|---|---|---|
| Gemini DR（日本語/英語） | 広域の領域探索・大量出力・速度 | 著者名・DOI の捏造率が高い（今回のサンプルで 33% 以上） | 初期ブレスト・「どんな研究領域があるか」の地図作り |
| ChatGPT DR | 「該当なし」を誠実に明示・DOI 精度が高い・採用判定に向く | 提案数がやや控えめ | 採用判定・原典確認補助 |
| Claude Code | 設計コンテキストを継続保持・ファイル操作・コード生成 | 大規模 Web リサーチは得意でない・捏造防止の原典確認が必要 | 実装パートナー・設計書管理・対話設計 |

### 引用論文補強セッションでの役割分担実例

2026-05-07 のセッションでは、以下の流れで 3 AI を使い分けた。

1. Gemini DR 日本語版で「立体模写発達」「視覚的閉合」「空間訓練→数学転移」の各領域に関する論文候補を広く取得（ブレスト）
2. Gemini DR 英語版で追加の英語文献を取得
3. ChatGPT DR で同じ領域を調査し、Gemini との提案を比較
4. 全提示論文を J-STAGE / PMC / DOI.org で原典確認（人間主導）
5. 確認済みのものを Claude Code 経由で references-map.md に反映

Gemini が提示した論文にのみ捏造が含まれており、ChatGPT の提示論文は精度が高かった。この差が「Gemini はブレスト止まり・ChatGPT は採用判定」という役割分担を固定化した。

### 先行リリース再設計セッションでの諮問→統合判断

2026-05-08 の先行リリース再設計では、HO-B2-25（先行価格・限定 SKU 設計）の維持か転換かを検討する際に、Claude Code 以外の視点を求めてChatGPT と Gemini に同じ問いを投げた。

「集客とフィードバック収集を主目的とした先行リリース案があれば提案してほしい」という問いに対し、ChatGPT は「リードジェネレーション先行型」、Gemini は「PDF ミニβ先行型」をそれぞれ推奨した。双方とも「販売前面型の HO-B2-25 維持」より「集客特化型の新設計」を推奨した点で一致していた。

ユーザーはこの 2 つの推奨をそのまま採用するのではなく、自分の判断軸（主目的=集客・副目的=ブラッシュアップ・非目的=売上）を踏まえて「フィードバック駆動型先行リリース」として独自に再設計した。AI の提案は「材料」であり「答え」ではないという運用が機能した。

### 役割分担が固まった後の変化

役割分担が意識化された後、「複数 AI に投げるコスト」を意識的に判断するようになった。日常的な設計作業（設計書更新・論点整理）は Claude Code 単独で回す。「大きな判断の前に第三者意見が欲しい」「研究領域の広域探索が必要」という場面では ChatGPT・Gemini を加える。

「並列で投げる」コストは主に時間と認知負荷だ。3 AI の出力を比較・統合する作業は Claude Code 単独より確実に重い。しかしその重さに見合うリターンがある場面（捏造リスクが高い・方針決定が大きい）では積極的に使う価値がある。

## なぜそう判断したか

1 つの AI に依存すると「その AI の特性のクセ」がそのまま設計に乗る。Claude Code は実装パートナーとして優れているが、「大規模な Web リサーチ」や「設計の大局を別視点で検証する」用途では他の AI の方が適している場合がある。

複数 AI の出力を比較することで、自分の判断軸が明確になるという副次的効果もある。「2 AI が同じ方向を推奨したとき」と「2 AI の意見が割れたとき」では、判断の重みが変わる。不一致の箇所が「最も深く考えるべき論点」を指し示す指標になる。

「人間が最終判断する」前提を強固にする運用として、AI 諮問→人間統合判断のフローは TENZU 設計の基本パターンとして定着している。

## 学び（一般化できるノウハウ）

1. **AI を 1 つの黒箱として扱わない** — 各 AI には得意領域と弱点がある。使い分けの地図を持つことが、AI 活用の精度を上げる最短経路だ。

2. **「諮問→統合判断」を自分のフローに組み込む** — 大きな判断ほど複数 AI に投げて比較する。重要なのは AI の答えをそのまま採用しないことで、あくまで判断材料として使う。

3. **Claude Code は「実装パートナー」枠として使い、リサーチは別 AI に分業させる** — Claude Code の強みはコンテキスト保持・ファイル操作・継続的な設計支援だ。広域 Web リサーチや設計の第三者検証には別 AI の方が適している。
