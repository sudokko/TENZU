# スマホ上部を1本の quickbar に圧縮する（実機テストの連続反映と型安全ネット）

## 何が起きたか（要約）

「スマホでメーカーを解くと『グリッドサイズ→もとの図』までが長すぎる、設定表示がごちゃつく」というオーナー指摘を起点に、全10メーカーの編集画面の上部を作り直した。元は上部に3本のバー（グリッド選択／作図設定／タイトル＋メタ＋線数＋アイコン）が積まれ、キャンバスが画面のずっと下にあった。これを **タイトルだけの toolbar ＋新規の `.maker-quickbar`（淡い帯・グリッド select＋小チップ）の2段** に圧縮し、キャンバスを画面のすぐ上へ引き上げた。CSS は共有の `maker.css` に集約して1ファイルで全10メーカーに波及させ、内部9メーカーの本体は並列サブエージェントで一斉展開した。その後の LAN 実機テストで出たオーナーのフィードバックを3バッチにわたり全10メーカーへ即反映した。シミュレーションでは見えなかった課題（折返し・タップ判定・ラベルの可読性）が実機で一気に表面化した。

## 状況・背景

メーカーは公開の `/maker` に加え内部用が9つ、合計10ある（鏡・回転・欠け補完・重ね・折り重ね・分解・拡大・縮小・平行移動）。いずれも同じ編集 UI を共有するが、TENZU のメインターゲットはスマホだ。デスクトップでは気にならなかった「上部3バー」が、スマホの狭い縦幅ではキャンバスを画面外へ押し下げる致命的な邪魔になっていた。確定方針は AskUserQuestion で詰めた——操作 UI はグリッドだけ `<select>`（6択・4択で横幅を食うため）、点と一筆書きは小チップ。タイトル横の `{grid}×{grid}・{用紙}` 表示と「線X本」は削除するだけ。用紙セレクタ自体は詳細設定フォールド内に温存する（B4/A3 は有償プランの売りなので残す）。A4 縦固定はしない。範囲は全10メーカー一斉。

## やり取りの中身

**圧縮の実装**。上部3バーを、タイトルのみの toolbar ＋新規 `.maker-quickbar` の2段に畳んだ。CSS クラス（`.maker-quickbar` とその子）は共有 `maker.css` に新設し、1ファイルで全メーカーへ波及させた。旧バーのルールは残置（未使用化したが無害）。タスク固有の上部コントロールも quickbar へ移設した——拡大の倍率（×2／×3）、縮小の縮小率（1/2・1/3）、欠け補完の F/R モード（完成図／抜く線）と公平性表示。一方で、キャンバスより下にある式の並び枠・回転の角度枠・サイドバー・詳細設定フォールド・出力プレビュー・PDF 生成ロジックは一切触らない。公開版の本体だけが有償プランのロックを保持（option に「（プランで解放）」接尾辞、選択で料金ページへ誘導）し、内部9はロックなし。内部9の展開は並列サブエージェントに任せた。

**実機テスト後の反映（3バッチ）**。LAN（実機をスマホで開く）で確認したオーナーのフィードバックを順次、全10へ反映した。1バッチ目4点——(1) 戻る／進む／全消去を上部 toolbar から「キャンバスと保存ボタンの間」へ移動、(2) 「問題」ラベルは単体ペインでは削除し2ペイン系では残しつつ拡大・濃色・太字化、(3) 「点」→「点の大きさ」に改名し、チップに実サイズ感のドット（4/6/9px の `::before`）を付与、(4) quickbar の各ラベルと操作を `.qb-group`（inline-flex）で括り、折り返してもラベルと選択肢が離れないように。2バッチ目3点——詳細設定フォールドの開閉を accent ピル「ひらく▾／とじる▴」に、「下に並べる」→「上下に並べる」、並びに「おまかせ」を追加。3バッチ目——「おまかせ」を重ね系へ拡張、選択状態の見た目（塗り潰し vs アウトライン）を詳細設定内で統一。

**「おまかせ」並びの型安全な展開**。並びレイアウトに `"auto"` を足すのが3バッチ目の山だった。状態を `"auto" | PairLayout` 型に変え、`effectivePairLayout`（選択した問題が2問以下なら上下／3問以上なら横）を新設して、レイアウトを消費する全箇所——ページ生成・枚数図・プレビュー／印刷の props・サマリ——へ流す。ここで型が効いた。状態を `"auto"` を含む型にすると、`PairLayout` を期待する消費側に生の値を渡した箇所を tsc が弾く。replace_all の取りこぼし（印刷専用コンポーネントの3箇所目）が TS2322 で発覚し、修正できた。「おまかせ」は純粋なレイアウトであるメーカー（写す・欠け補完・回転・拡大・縮小・平行移動、後に重ね・分解も）にだけ入れ、鏡・折り重ねは除外した——これらの並びは鏡軸や折り軸そのものを意味し、問題数で自動的に切り替えると答えが変わってしまうからだ。

## なぜそう判断したか

**CSS を共有ファイルに集約した理由**。10メーカーは同じ編集 UI を共有している。見た目の変更を各メーカーの本体に書くと、10箇所に同じ修正が散らばり、フィードバックのたびに差分が発散する。`maker.css` の1ルールにすれば、開閉ピルもラベルの太字化も選択状態の統一も、1箇所の変更で10メーカーに同時に効く。実機テストの反復が前提なら、波及の単一点を作っておくほど反復が速い。

**実機テストを段取りに組み込んだ理由**。preview の対話系（クリック・スクリーンショット）が本環境で不調で、モバイルの実際の見た目はオーナーの手動確認に頼るしかなかった。だが結果的に、それが正解だった。折り返し時のラベルの離れ、select のタップ感、点チップの実サイズ感、「問題」ラベルの薄さ——どれもシミュレーションでは表面化せず、実機で初めて「ここが読みにくい・押しにくい」と分かった。viewport・タップ判定・折り返しは実機に出さないと見えない。だから最初から作り込みすぎず、土台を出して実機フィードバックで詰める段取りにした。

**型を安全ネットに使った理由**。「おまかせ」は新しい値をレイアウトの流れ全体に通す変更で、消費側が多数ある。手で全箇所を直すと必ず1つ漏れる。状態を `"auto"` 込みの型に変えると、コンパイラが「生の値を期待する箇所に新しい型を渡した」場所を全部挙げてくれる。実際それで印刷専用コンポーネントの漏れが出た。tsc が EXIT 0 になることが、消費漏れゼロの証明になる。

**鏡・折り重ねを「おまかせ」から外した理由**。同じ「並び」でも意味が違う。多くのメーカーで並びは見た目だけだが、鏡と折り重ねでは並びが鏡軸・折り軸そのものを表す。問題数で自動的に並びを切り替えると、出力される答え自体が変わってしまう。見た目の自由度と機能の意味を混同しないために、ここだけ自動化の対象から外した。

## 学び（一般化できるノウハウ）

1. **多インスタンスの見た目変更は共有 CSS の1点に集約する** — 同じ UI を共有する N 個の画面では、見た目の修正を各本体に書くと N 箇所に散る。共有スタイルシートの1ルールにすれば、フィードバックのたびの修正が単一点で済み、反復が速くなる。本体に残るのは構造とロジックだけにする。

2. **モバイル UI はシミュレーションでなく実機テストで詰める** — 折り返し・タップ判定・ラベルの可読性・要素間の実距離は、実機に出すまで表面化しない。最初から作り込みすぎず、土台を出して実機フィードバックを連続で当てるほうが、結果的に速く正しい形に着地する。確認手段が限られても、実機目視を段取りに組み込む価値がある。

3. **状態にユニオン型を足して消費漏れをコンパイラに検出させる** — 新しい値（例：`"auto"`）をデータの流れ全体に通すとき、状態を `"auto" | T` のようなユニオン型にすると、`T` を期待する消費側に生の値を渡した箇所を tsc が全部弾く。手作業の replace_all では必ず出る取りこぼしが型エラーとして可視化され、tsc が通ること自体が「全消費側を直した」証明になる。
