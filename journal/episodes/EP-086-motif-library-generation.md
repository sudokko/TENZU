# 絵柄をモチーフ・ライブラリ方式で自動設計（手設計原型×決定的バリアント展開）

## 何が起きたか（要約）

EP-085 で作った問題データ基盤の上に、絵柄（具象モチーフ）7 巻ぶんの問題を自動設計する仕組みを乗せた。模写（図形）のランダムウォークでは「絵」にならないため、方式を変えた——**手設計したモチーフ原型 × 決定的なバリアント展開**。`motif-shapes.ts` に「いえ・くるま・ヨット・かめ……」といった原型をポリラインで手書きし（最終 90 族）、各原型に「累積ディテール」（いえ＝基本→とびら→まど→えんとつ）と左右ミラーを持たせる。`motif.ts` の `MOTIF_LADDER`（7 巻の難易度帯）に対し、各原型の全変種を seed 決定的に展開・配置して候補を生成する。巻への割り当ては「変種の実測メトリクスがその巻の帯に入るか」で自動的に決まる。生成器レジストリ（`gen/index.ts`）で模写と絵柄を同じインタフェースに束ね、`/atelier` 検品ツールはどちらの方式かを意識せず扱える。監査スクリプト・模写の回帰・`next build` すべてクリーン、7 巻で各 24〜29 候補を確認した。

## 状況・背景

EP-085 の模写ジェネレータは成長型ランダムウォークで、図形の模写には十分だった。しかし絵柄（具象）は「ランダムに辺を伸ばす」と絶対に絵にならない。家にも船にも見えない線の塊が出るだけだ。絵柄は「人が見て家だと分かる形」でなければ商品にならない。一方で、7 巻 × 十数問を一つずつ手で座標入力するのは EP-085 で避けたかったことそのものだ。「手で作る楽しさ」と「自動で量を出す効率」をどう両立するかが論点だった。

## やり取りの中身

採った方式は、原型だけ手で作り、そこからの派生を機械が決定的に展開する、という分担だった。

**ライブラリ（`motif-shapes.ts`）**。各モチーフを `"0,1 2,1 2,2"` 形式のポリラインで手書きする。連続する点ペアが辺になる。ここに二つの増殖軸を足した。一つは「累積ディテール」——基本形に、とびら・まど・えんとつ……を前から順に足していく。足すほど線が増え、メトリクス経由で自然に上位レベルの帯へ移る。もう一つは「ミラー」——非対称な形だけ左右反転を別候補として出す。

**ラダーと適合（`motif.ts`）**。7 巻それぞれに帯（盤面サイズ・傾き規則・線数・交差・構成要素数）を定義した。各原型の全変種を展開し、実測メトリクスがどの巻の帯に入るかで割り当てる。同じ盤面サイズの 2 巻が並ぶ箇所（4×4 の Lv2/Lv3、5×5 の Lv3/Lv4）は、線数帯を重ならないように切り、片方は「非 45°（複雑な角度）を必ず含む」要件で住み分けた。

**巻またぎの重複防止を 3 層で**。ライブラリが有限なので、放っておくと隣の巻と同じ絵が出る。① 盤面占有規則——長辺は盤面いっぱい・短辺も一定以上を要求し、小さい絵が大きい盤面にぽつんと載るのを防ぐ（これが盤面サイズ間のモチーフ流用も自然に切る）。② 同一盤面の 2 巻は帯を非交差にする。③ 変種キー（`house4~m+2` のような文字列）を候補 JSON に記録し、兄弟巻（同タスクの他巻）の candidates と published を走査して、生きている変種は生成から除外する。自分の巻では不採用にした変種も二度と出さない。

**生成器レジストリ（`gen/index.ts`）**。模写（無限ランダムウォーク）と絵柄（有限ライブラリ）は性質が違うが、`/atelier` から見れば「候補を生成する」点で同じだ。`generatorFor(sku)` が方式の違い（線数帯・巻またぎ排他の要否）を吸収し、UI とAPI は統一インタフェースだけを見る。

**検証**。監査スクリプト（`audit-motifs.ts`）で「全変種が必ずどこかの帯に入る」「各巻が十分な母数を持つ」を確認した。最初は 8 件の孤児変種（どの帯にも入らない）が出たが、帯の境界調整とライブラリ追補で解消。`/atelier` で 7 巻を目視し、かめ・くじら・ヘリコプター・もみのき等がちゃんと絵になることを確認した。模写の回帰テストと `next build` もクリーン。

この後の追補で、各巻の候補母数を +8〜13 問に増やすため 32 族を足して 90 族にし、各巻 24〜29 候補にした。

## なぜそう判断したか

ランダムウォークを絵柄に流用しなかったのは、絵柄の本質が「ランダムでは到達できない既知の形」だからだ。家や船は探索で偶然出るものではなく、人が知っている形を再現するものだ。だから原型は手で作るしかない。ただし手作業を「原型 1 つ」に閉じ込め、そこからの量産（ディテール段階 × ミラー × 配置）は機械の決定的展開に任せた。手の仕事と機械の仕事の境界を、創造性が要る所と単調作業の所で引いた。

割り当てを「実測メトリクスが帯に入るか」で決めたのは、難易度を宣言ではなく測定で扱うため。原型に「これは Lv3」と札を貼るのではなく、展開した変種の実際の線数・交差を測って、入る帯に落とす。EP-085 のメトリクス自動算出をそのまま難易度判定に使い回せた。

巻またぎ重複を 3 層にしたのは、有限ライブラリ特有の問題だからだ。無限生成なら類似棄却だけで足りるが、有限だと隣の巻と母集合を共有してしまう。盤面占有・帯の非交差・変種キー記録の三段で、同じ絵が別の巻に現れるのを防いだ。

レジストリで二方式を束ねたのは、検品ツールに方式を意識させないため。`/atelier` は「候補を出して人が選ぶ」道具であって、その候補がランダムウォーク由来か手設計ライブラリ由来かは関心の外だ。差異を `generatorFor` に閉じ込めた。

決定的生成にこだわったのは EP-085 と同じ理由で、検品という人手工程の再現性のため。さらに有限ライブラリでは「もう出せる候補が無い」状態が起こるので、`/atelier` 側に枯れ判定とメッセージを足した（無限のランダムウォークには無い概念）。

## 学び（一般化できるノウハウ）

1. **手の仕事と機械の仕事を「創造性 vs 単調」で割る** — 絵柄のように既知の形が要るものは、原型だけ人が作り、派生（ディテール段階・ミラー・配置）は機械の決定的展開に任せる。手作業を最小単位に閉じ込め、量産は機械化する。

2. **難易度は宣言でなく測定で割り当てる** — 原型に難易度の札を貼るのではなく、展開した変種の実測メトリクスがどの帯に入るかで落とす。生成と難易度判定が同じ計算を共有でき、人の主観的なラベル付けが消える。

3. **有限ライブラリは無限生成と別の防御が要る** — 無限生成は類似棄却だけで足りるが、有限だと隣り合う区分が母集合を共有して同じ出力が漏れる。占有規則・区分の非交差・使用済みキーの記録、という多層の排他と「枯れ」の明示が必要になる。

4. **方式の差はレジストリに閉じ込め、消費側は統一インタフェースで扱う** — 同じ目的（候補生成）の異なる実装（ランダムウォーク／手設計ライブラリ）は、`generatorFor` のような解決層で吸収する。UI や API は方式を意識せず、新方式の追加も消費側を変えずに済む。
