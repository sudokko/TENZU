# 欠け補完メーカーを「完成図∖抜く線」の差集合で生成し公平性をライブ判定する

## 何が起きたか（要約）

欠け補完（fill）タスクのメーカー `/maker-fill`（内部用・noindex）を実装した。模写メーカーは「みほん＝かくマス」で同じ図を写させるが、欠け補完は「完成図の一部が欠けた図を見せ、欠けを補って完成図を復元させる」タスクで、解答（完成図）を出題とは別に持つ。ここで採った構成が **F/R 二モード**だ。F モード＝「完成図を描く」、R モード＝「抜く線を選ぶ」。出題（かくマス）は完成図 F から抜く線 R を除いた差集合 G＝F∖R として描画し、解答（みほん）は F をそのまま見せる。さらに R の選び方によっては「G から元の F が一意に復元できない不公平な問題」が作れてしまうため、編集中にその場で復元可能性を判定する**公平性ライブチェック**を付けた。EP-085 のスキーマで fill を `answerMode: "explicit"`（解答 edges を別持ち）と定義済みだったので、その器にちょうど嵌まる。atelier の EditOverlay にも F/R 編集モードを足し、SkuPrintPreview の fill 描画バグ（みほんとかくマスの取り違え）を修正した。tsc クリーン、F4 本＋R1 本→かくマス G3 本のプレビューを確認した。

## 状況・背景

EP-085 で問題データのスキーマを定義したとき、解答の持ち方を `none`／`derived`／`explicit` の3つに分けた。`derived` は変換（鏡・回転・平行移動・拡大縮小）で解答が計算できるタスク、`explicit` は解答 edges を別に持つタスクだ。欠け補完はこの `explicit` 側にいる。完成図 F が解答で、出題は F の一部を抜いたものになる。

問題は「抜き方」をどう編集 UI に落とすかだった。素朴には「欠けた図を直接描く」やり方もあるが、それだと作者が頭の中で完成図を保ったまま、わざと一部を描かないことになり、解答（完成図）が手元に残らない。解答を `explicit` に保存する以上、完成図そのものをデータとして持たねばならない。

## やり取りの中身

**F/R 二モードで「完成図」と「抜く線」を分離した**。編集はモード切替式にした。F モードでは点を2つクリックして完成図の線を引く（同じ線をなぞると消える）。完成図ができたら R モードに切り替え、完成図の上の線をクリックすると、その線が「抜く線」（子が描き足す欠け）になる。保存される問題は `{ gridSize, edges: F, rEdges: R }` の形で、F と R を両方持つ。

**出題は差集合 G＝F∖R で描画する**。`gapOf(edges, rEdges)` が R の edge キー集合を作り、F から R を引いた残りを返す。みほんペインには F を、かくマスペインには G を描く。子は G を見て、欠けている R を自分で補い、F を復元する。R モードでは完成図 F に無い線は選べない（R は必ず F の部分集合）よう制約した。

**公平性をライブ判定した**。R の選び方が悪いと、欠けが「どこに何をつなげばいいか手がかりが無い」状態になり、G から元の F を一意に復元できなくなる。具体的には、抜く線 R の端点が出題 G 側のどの線にも現れない（孤立点になる）と、子はその点の存在自体に気づけない。`fairness` という `useMemo` で、R の各 edge の両端点が G の点集合に残っているかを毎回チェックし、残っていない（孤立した）R を数える。孤立がゼロなら「公平性 OK」、あれば「つなぐ先が見えない N 本」と編集バーに即時表示する。

**色とフィードバックで二モードを区別した**。編集中の盤面では、R に指定した線を薄色の点線で重ねて表示する（実線の完成図と区別）。クイックバーに公平性メッセージを常時出し、不公平なら赤系で警告する。

**周辺も直した**。atelier の EditOverlay にも F/R 編集モードを追加し、検品時に同じ操作で抜き方を調整できるようにした。SkuPrintPreview には fill のバグがあって、みほん／かくマスの描き分けが取り違っていた（みほんに G、かくマスに F が出ていた）。正しくは**みほん＝F・かくマス＝G＝F∖R** に修正し、API の candidates が `answerEdges`（＝F）の更新を受け取れるようにした。

## なぜそう判断したか

**差集合で生成したのは、解答を一次データにして出題を導出にするため**だ。完成図 F が「正」で、出題はそこから機械的に引き算した結果に過ぎない。もし出題（欠けた図）を直接描かせると、解答 F は作者の頭の中にしか無くなり、`explicit` 解答として保存できない。F と R を持てば、出題 G はいつでも `F∖R` で再計算できる。後で抜き方を変えたくなっても F は壊れず、R だけ差し替えれば済む。導出できるもの（出題）をデータに持たず、源（完成図と抜き方）だけを持つ設計だ。

**F/R をモードで分けたのは、二つの操作の意味が違うから**だ。「線を引く」と「引いた線を抜く対象に指定する」は、対象（点 vs 既存の線）も結果（F が増える vs R が増える）も別物だ。同じキャンバスで混ぜると、クリックが「描く」のか「抜く」のか曖昧になる。モードを明示すれば、R モードでは「完成図の線だけ選べる」という制約も自然に効く。

**公平性をライブ判定したのは、不公平な問題が静かに作れてしまうから**だ。抜く線を選ぶ操作自体は何本でも通ってしまうが、その中には「子が解けない（解が定まらない）」組み合わせが混ざる。これは保存後やプレビューで初めて気づくのでは遅い。編集の各クリック直後に「つなぐ先が見えない N 本」と出れば、作者はその場で抜き方を直せる。生成の正しさを、出力時の検査ではなく入力時のフィードバックに寄せた。

## 学び（一般化できるノウハウ）

1. **解答を別に持つタスクは「出題＝完成図∖抜くもの」の差集合で生成する** — 完成図（解答）を一次データに置き、出題はそこからの引き算で導出する。出題そのものを描かせると解答が手元に残らないが、「完成図 ＋ 抜く指定」を持てば出題はいつでも再計算でき、抜き方の変更にも壊れない。導出可能なものはデータに持たず、源だけを永続化する。

2. **意味の違う二操作はモードで分け、片方を他方の部分集合に制約する** — 「描く」と「抜く対象に指定する」のように対象も結果も異なる操作は、同一キャンバスに混ぜず明示的なモードに割る。モードを分けると「抜く対象は既に描いた線だけ」という部分集合制約が自然に成立し、不正な入力を入口で塞げる。

3. **生成物の妥当性は出力時の検査でなく入力時のライブ判定で担保する** — 「解が一意に定まるか（復元可能か）」のような妥当性は、保存後やプレビューで検査すると手戻りが大きい。編集のクリック直後に成立性を再計算して即時フィードバックすれば、作者はその場で直せる。判定ロジック（端点が出題側に残るか）は数行の `useMemo` で足り、コストも小さい。
