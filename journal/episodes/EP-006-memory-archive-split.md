# MEMORY.md → session-archive.md 分離の経緯と判断軸

## 何が起きたか（要約）

セッションを重ねるごとに MEMORY.md が肥大化し（200 行制限の警告が頻出）、会話開始時の読み込み負荷が問題化した。2026-05-07 以降、詳細な過去セッション記録を `session-archive.md` にオフロードし、MEMORY.md は「最新フェーズ情報＋直近セッション 2-3 件＋主要決定事項一行サマリ表＋ファイルマップ」のみに整理した。「常時ロードするもの」と「必要時だけ読むもの」の分離が運用の核心だ。

## 状況・背景

TENZU プロジェクトは 2026-03 に開始し、GTM 設計・競合分析・問題パック設計・サービスブループリント・コンテンツ設計と複数のフェーズが積み上がった。各セッション終了時に「今日の決定事項」をまとめて MEMORY.md に追記する運用だったため、セッション数が増えるにつれて MEMORY.md が縦に伸び続けた。

MEMORY.md の役割は「次のセッション開始時に Claude が読んで、すぐに文脈を取り戻せるようにする」ことだ。しかし内容が膨らむほど、「今必要な情報」と「過去の経緯」が混在し、本当に必要な情報にアクセスするコストが上がる。200 行制限警告が出た段階で、構造的な解決が必要と判断した。

## やり取りの中身

### 分離の設計

分離後の 2 ファイルの役割を明確に定義した。

| ファイル | 役割 | 内容 |
|---|---|---|
| `MEMORY.md` | 索引＋最新状態 | プロジェクト概要・設計原則・今ここ（最重要）・直近セッション 2-3 件・主要決定事項一行サマリ表・ファイルマップ |
| `session-archive.md` | 時系列詳細アーカイブ | 過去セッションの詳細議論・撤回された判断・経緯・不採用記録 |

MEMORY.md は「常時ロード」が前提だ。Claude がセッション開始時に読む情報なので、コンパクトに保つことが最優先。一方 session-archive.md は「必要になった時に初めて読む」前提で、詳細が全て残っている。

### オフロードの判定ルール

MEMORY.md の「直近セッション」セクションに新しいセッション記録を追加し、2-3 セッション分溜まったら古い方を session-archive.md にオフロードする。MEMORY.md の「主要決定事項一行サマリ」表には 1 行（日付・テーマ・要点）だけ残す。

「どこまでが直近か」の判断は 2 軸で行う。1 つは時間軸（2-3 セッション前より古いものはアーカイブ候補）。もう 1 つは参照頻度（現在の作業で毎回参照するかどうか）。現在の課題に直接影響しないセッション記録は積極的にアーカイブに移す。

### session-archive.md の構造

session-archive.md には日付ごとのセクションを設け、各セッションの詳細を記録した。内容は以下を含む。

- その日のセッションの目的・流れ
- 各論点のクローズ内容と決定事項
- 撤回された判断とその理由
- 次セッションへの申し送り
- 設計書の更新記録

2026-04-15 以降の全セッション記録が蓄積されており、「なぜある設計がそうなっているか」を遡る際に参照する。特に撤回記録（HO-B2-25 撤回、仕上げ編廃止等）は「なぜ一度確定した設計が変わったか」の文脈を保持するために重要だ。

### MEMORY.md の 200 行ガイドラインとの関係

Claude Code の MEMORY.md には 200 行制限のガイドラインがある（超過時に警告が出る）。この制限は「常時ロードするファイルは軽くあるべき」という設計思想を反映している。分離後は MEMORY.md を 200 行以内に保つことを意識しながら、session-archive.md は制限なしで詳細を記録するようになった。

## なぜそう判断したか

「全文常時ロード型の MEMORY は、長期プロジェクトでスケールしない」という構造的な問題に気づいたことが判断の出発点だ。プロジェクトが続く限り記録は積み上がり続けるが、「今のセッションに必要な情報」は全体の一部に過ぎない。

「今ここ」と「過去の経緯」は参照頻度が根本的に違う。プロジェクトの最新フェーズ・現在の課題・直近の決定事項は毎セッション必要だが、2 ヶ月前の設計議論の詳細は「特定の論点を遡る時だけ」必要になる。参照頻度に応じてストレージを分けるのは、情報設計の基本原則だ。

session-archive.md は「なぜそうなったか」という設計判断の経緯を保存する装置でもある。特に撤回された判断（HO-B2-25 撤回・仕上げ編廃止等）は削除してしまうと「同じ議論を再び行う」非効率につながる。アーカイブとして残すことで、過去に踏んだ道を再度踏まずに済む。

## 学び（一般化できるノウハウ）

1. **memory 設計は段階進化させる** — 初期は単一ファイルで十分。肥大化の兆候（200 行超・読み込みが重くなる感覚・「どこに何が書いてあるか」の迷い）が見えたら役割分離を検討する。最初から複雑に設計しすぎないことも重要。

2. **「常時ロード」と「必要時ロード」を分ける** — MEMORY.md（常時ロード）は最新状態の保持に絞り、過去経緯は session-archive.md（必要時ロード）に切り出す。この 2 階層により、日常的なセッションの読み込みコストを一定に保ちながら、詳細な過去経緯の参照も可能になる。

3. **オフロード時に「一行サマリ」を残す** — 詳細をアーカイブに移す際、MEMORY.md の主要決定事項表に 1 行（日付・テーマ・要点）だけ残す。これが「索引からアーカイブへの導線」になり、「あの時の議論はどこ？」という問いに即答できる。
