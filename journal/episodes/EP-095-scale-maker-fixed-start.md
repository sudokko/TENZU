# 拡大メーカーの固定点を「機械が選ぶ」から「描き始めた点」へ

## 何が起きたか（要約）

回転・鏡に続く変換系メーカーとして、拡大メーカー `/maker-scale` を実装した。拡大は「固定点（不動点）まわりの整数倍（×2/×3）」で、図形の全頂点が格子点に乗る。最大の論点は固定点をどう決めるかで、ここを設計しては作り直すことを繰り返した——初版は外接矩形の隅を機械が自動選択（空いた角に★が浮くバグ）、案 A で隅＋図形上の点を優先、案 A 改で全頂点を候補にして中央寄せの fallback（V 字図形対応）と賢くしていった。しかし最後にオーナーが「星が図形の位置で自動的に切り替わるのは直感に反する／元の明快な仕様がいい」と判断し、自動選択を全廃。固定点を「最初に描いた点（`edges[0].a`）」に固定する仕様で着地した。自動補正もなくし、始点が悪くて枠をはみ出すなら `fits:false` で警告を出すだけにした。始点を大きな★と「きてん」ラベルで強調表示する。回転メーカーを雛形に複製し、新規 2 ファイルのみ、`print.ts` などは無改修。tsc・幾何アサーション 11/11・全ルート 200 がクリーン。

## 状況・背景

メーカーは 9 タスク（模写・鏡・回転・欠け補完・拡大・縮小・重ね・折り重ね・平行移動）を順に作っており、拡大はその変換族の一つだ。回転メーカー `MakerRotateApp.tsx` が既にあったので、それを雛形に複製した。グリッドは元図も結果も同じ n×n の「同一グリッド方式」とし、元図を小さく描いて余白方向へ拡大、枠に収まるかを自動判定する。倍率は ×2/×3（×4 は廃止、×3 も「怪しい」が一旦残す）、グリッドは 5/6/7/8 とした。

拡大という変換は「ある一点を動かさず、その点からの距離を整数倍に伸ばす」ことで定義される。この動かない一点＝固定点（不動点）をどこに取るかで、同じ図形でも結果が変わる。問題は、この固定点を「誰が、どういう規則で決めるか」だった。

## やり取りの中身

核の幾何は純粋関数 `scalePoint(p, factor, anchor) = anchor + factor·(p − anchor)`。anchor が不動点で、各点をそこから factor 倍の位置へ移す。問題はこの anchor の決め方で、ここを四段階で作り直した。

**① 初版＝外接矩形の隅を機械選択。** 図形の bounding box の角を固定点に取った。だが図形が角に接していないと、空いた角にぽつんと★（固定点マーカー）が浮いて見え、「なぜそこが動かない点なのか」が直感に反した。

**② 案 A＝隅＋図形上の点を優先。** 浮きを直すため、固定点候補を図形の頂点に寄せた。

**③ 案 A 改＝全頂点を候補にして中央寄せ fallback。** V 字のような図形でも自然な固定点が出るよう、全頂点を候補にしてランク付けし、決まらなければ中央寄りを選ぶようにした。`uniqueVerts` / `centerDist` / `cmpRank` / `bbox` / `placementLabel` / `growDirLabel` といった補助を積み上げ、賢くなっていった。

**④ オーナー決定＝始点固定（現行）。** ここでオーナーが方針を反転させた。「星が図形の位置で自動的に切り替わるのは直感に反する。元の明快な仕様がいい。始点の重要性を強調してほしい」。これを受けて自動選択ロジックを全廃。固定点を `start = edges[0].a`（最初に描いた線の始点＝最初に置いた点）に固定した。②③で積んだ `uniqueVerts` 等の補助関数はすべて撤去した。

現行の `computeScale(edges, factor, n)` は単純だ。`start = edges[0].a` を不動点に `R = scaleEdgesOf(edges, factor, start)` を計算し、`fits = inGrid(R, n)` を判定して `{ edges: R, star: start, fits }` を返す。図形の位置で固定点を自動選択しない。始点が悪くて枠を超えるなら `fits:false` で警告を出すだけで、自動では動かさない——人が始点・倍率・グリッドのどれかを調整する。

始点の強調表現は別途実装した（widget で「今／A／B／C」の候補を提示しオーナーが A を選択）。大きな★と「きてん」ラベルを、もとの図ペインと拡大図ペインの両方に表示する。画面では teal に薄いハロー、PDF と印刷プレビューでは単色のインクで描く。

## なぜそう判断したか

賢い自動選択を捨てて素朴な「始点固定」を採ったのは、最適化の対象がそもそも違っていたからだ。機械が固定点を選ぶ設計は「結果図が枠に最もよく収まる固定点」を探していた——出力の質を最適化していた。だが①で露呈した「空角に★が浮く」問題が示すのは、子どもにとっての一番の価値が「結果が枠に収まること」ではなく「なぜその点が動かないのかを理解できること」だという点だ。固定点が図形の位置に応じて勝手に切り替わると、子は「動かない点」のルールを学べない。

「最初に描いた点が動かない点」という規約は、結果の最適性を犠牲にする。始点が悪ければ枠をはみ出す。しかしこの規約には、機械の選択にはない美点がある——子が固定点の位置を完全に予測でき、自分で制御できることだ。同じ図形でも、描き始める点を変えれば固定点が変わる。これは「バグ」ではなく、子が操作の主導権を握れる仕様だ。だから自動補正もしない。はみ出しを機械が黙って直すと、また「なぜそうなったか分からない」状態に戻る。正直に `fits:false` と警告し、調整を人に委ねる。

固定点を per-problem（問題ごと）に保存する設計も同じ思想だ。回転の rotateDeg は大域だが、拡大の固定点は fit 判定と結合するため、保存時に「収まること」を検証して問題ごとに確定させる。

## 学び（一般化できるノウハウ）

1. **機械の最適化より「子が理由を理解できる規約」を優先する** — 「結果が最もよく収まる固定点を機械が選ぶ」は出力品質の最適化で、技術的にはより賢い。だが教育プロダクトでの価値は出力の質ではなく「なぜそうなるかを学習者が理解・予測できること」にある。「最初に描いた点が動かない」という素朴な規約は、結果の最適性を捨てる代わりに、子に完全な予測可能性と制御を与える。賢さが理解しやすさを損なうなら、賢さを捨てる。

2. **自動補正は「予測可能性」とトレードオフになる** — 始点が悪くてはみ出すとき、機械が黙って固定点を動かして直すこともできた。だがそれは「なぜこの結果になったか」を再び不透明にする。自動補正をやめて `fits:false` の警告に留め、調整を人に返す方が、規約の一貫性を保てる。便利さが規約の透明性を壊す場面では、不便でも透明を採る。

3. **設計の進化方向が逆を向くことがある——「賢くする」から「素朴に戻す」へ** — ①→④は「より賢く」の方向に三段進んだ後、最後に出発点近くの素朴な仕様へ反転した。積み上げた補助ロジック（全頂点候補・中央寄せ・ランク付け）は全部撤去した。賢さを足し続けた結果が必ずしも正解ではなく、ユーザー（ここでは子と親）の直感に照らして素朴解に戻すのが正しいこともある。撤回時は中途半端に残さず、不要になったロジックを一掃する。
