# GTM 4段階公開計画の組み立て——コンテンツの「出し順」を設計する

## 何が起きたか（要約）

B-2（コンテンツ設計）の後半で、全48本の記事をどの順番・タイミングで公開するかを設計した。「全記事を一気に公開するのではなく、目的別に4つのフェーズ（段階）に分けて出す」という GTM 4段階公開計画を確定した。Phase 0（アプリ先行・初期記事10本）→ Phase 1（商品ページ連動・先行モニター期間）→ Phase 2（FAQ追加）→ Phase 3（全記事本公開）という構成で、集客・ブラッシュアップ・本リリースを段階的につなぐ計画になった。

## 状況・背景

2026-05-05 のセッション時点で、B-2 Block 1 の成果物として「全48本の記事リスト・URL・テーマ分類」が確定していた（EP-022）。しかし「全部作って全部いっぺんに公開する」設計では、次の問題が生じる：

- コンテンツの準備が全部揃うまでリリースできない（個人開発者の実装が詰まる）
- 保護者の反応を見ながら記事を改善する「フィードバック駆動」の機会が失われる
- 先行モニター制度（EP-033）と記事公開のタイミングが整合しない

「何を・いつ・なぜ出すか」を明示的に設計する必要があった。

## やり取りの中身

まず記事を「役割」で3タイプに分類した：

| タイプ | 内容 | 公開タイミングの性質 |
|---|---|---|
| **ハブ型（A）** | Pillar 3本（入門ガイド・中受版・苦手な子向け） | ブランドの基幹。早く出すほど SEO 蓄積が始まる |
| **SEO種まき型（B）** | 症状ベース・ノウハウ系 Cluster | 検索流入の入口。長期的な集客基盤 |
| **販売連動型（C）** | 商品ファミリー記事・FAQ long | 商品ページが開く Phase 1 以降に必要 |

この分類を軸に、4段階のフェーズを設計した（`content-design-clusters.md §8` / `launch-plan-phases.md §3〜§6`）：

**Phase 0（アプリ先行・1〜2週）**：10本を公開。アプリ+最小LP+初期記事だけで動かす。
- アプリ紹介記事1本（SEO非依存・インフルへの紹介素材）
- Pillar A「入門ガイド」1本（エンティティ権威化を早く始める）
- 症状ベース Cluster 5本（「板書が苦手」「斜め線が書けない」等の検索流入記事）
- ノウハウ系 Cluster 3本

**Phase 1（先行モニター期間・4〜6週）**：4本追加。商品ページ・モニター応募窓口が開く。
- 商品ファミリー記事 4本（先行 SKU に連動する模写・欠け補完・立体模写・線対称）

**Phase 2（修正期間・4〜6週）**：3本追加。フィードバック反映後の補強。
- Lv 選び方記事（フィードバックで需要が確認されたら）
- FAQ long 2本（「返金は？」等の問い合わせが来たら整備）

**Phase 3（本リリース）**：残り31本を一気に公開。
- 残り商品ファミリー5本（Phase 1 未公開タスク）
- Pillar B/C・比較記事・中受記事・残り Cluster 全て

Claude がフェーズ分けの意図を一言でまとめた：

> 「Phase 0 は『集客の種を撒く』。Phase 1 は『価値を確認してもらう』。Phase 2 は『フィードバックで直す』。Phase 3 は『全量出して本格稼働』。各フェーズの目的が違うから、出す記事の種類も変わる。」

## なぜそう判断したか

4段階に分けた最大の理由は「フィードバック駆動型リリース」（EP-013）との整合だ。先に集客記事を公開して保護者の反応を見てから、商品連動記事・FAQ を整備するという順番が、リリース戦略の方針と一致する。

Phase 0 に Pillar A を入れた判断（論点③）は「SEO の複利効果を早く始める」という理由だった。Pillar 記事は月産の Cluster 記事より被リンクを集めやすく、早期公開がドメイン権威の蓄積につながる。「本リリース前に公開できるコンテンツは早めに出す」のが合理的だった。

Phase 3 に31本を一気に出す設計は「保守的な見通しより速い本番稼働」を優先した。全記事を分散公開すると、Google のインデックスが分散し、アルゴリズム評価のタイミングが読みにくくなる。コンテンツが揃った段階で一気に出す方が、SEO 立ち上がりとして有利だという判断だった。

## 学び（一般化できるノウハウ）

1. **コンテンツは「全量・一気」より「目的別・段階的」に出す** — 記事の役割（集客・価値確認・販売連動）によって最適な公開タイミングが違う。全部揃えてから出す設計より、役割ごとに出し順を決める設計の方が、フィードバックと整合しやすい。

2. **「出し順」はリリース戦略と連動させる** — コンテンツ設計と GTM 計画を別々に作ると、「記事は揃ったのに商品ページが開いていない」という不整合が起きる。記事の役割とリリースフェーズを同じ設計の中で扱う。

3. **SEO 蓄積が必要なコンテンツは早めに公開する** — Pillar 記事のようなドメイン権威化に寄与するコンテンツは、商品が揃う前でも公開できるなら早めに出す。長期的な複利効果が始まる。
