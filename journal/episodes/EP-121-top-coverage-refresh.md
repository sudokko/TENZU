# TOP 品ぞろえ実演9種の刷新（線分単位 WAAPI と headless 検証の罠）

## 何が起きたか（要約）

TOP の品ぞろえセクションにある9タスクのミニ実演 SVG を、実物紙面に準拠した構図へ全面刷新し、線分単位で1本ずつ描き上げる Web Animations API（WAAPI）アニメーションに作り替えた（コミット cd5f876）。あわせてセクション順を再編し、セクション⑥「家庭での続け方」を「はじめ方（購入の流れ5ステップ）」へ改修、TOP 記事枠のダミー4本を実記事への動的配線に置き換えた（df53b1a）。同日は「プリントを探す」プルダウンを軸にしたヘッダーナビ再編・フッターの死にリンク一掃も先行しており、TOP の導線を一日で通しで作り直した形になる。検証では headless Chrome の罠5点と、共有モジュールへの node:fs 混入事故という知見が残った。

## 状況・背景

TOP はストアフロント化以降、9タスクの中身を SVG アニメで実演する品ぞろえセクションを持っていたが、旧仕様は実物の紙面から乖離していた——欠け補完は欠け線が1本だけ、立体はお手本が平面、折り重ねは対称形で折る意味が伝わらない、といった具合である。「中身が見える」ことを差別化の本丸に置く店の看板として、実演が実物を裏切っている状態だった。刷新にあたりオーナーからは「一気に書かずに1本ずつ・時間がかかってOK」という要望が出た。子どもが鉛筆で1本ずつ線を引く時間感覚の再現である。

## やり取りの中身

**構図はメーカー紙面準拠、アニメは SMIL→CSS→WAAPI と2段移行**。9種の構図を実物紙面の部品（maker-figs.tsx）準拠に作り直し、2ペイン=みほん→かく（写す・立体・欠け補完・鏡・移動・回転）／3ペイン=A±B=かく（重ね・分解・折り重ね）、viewBox は全タスク共通（340×172）で統一した。描き上げはポリラインを toSegs() で線分に分解し、1 path=1本として順に描く。まず SMIL で組んだが、values/keyTimes の組み合わせで Chromium に末尾の線が欠ける挙動があり撤退。次の CSS アニメは keyframe の % が線分本数ごとに異なるため共通 keyframes に載らない。最終的に、キーフレームを JS で計算して要素ごとに与えられる WAAPI へ着地した。周期は線分本数に比例し、箱の12本で約11.6秒になる。`.cs-seg` は CSS 基底で非表示にし、reduced-motion 環境では完成形の静止表示へ切り替える。

**セクション再編と「はじめ方」への改修**。新順序は品ぞろえ実演→「レベルで選ぶ」（CTA はレベル選びガイド）→「自分で作る」（工房挿絵）→続け方→記事。挿絵は2案を HTML モックで提示し、採択案以外は削除した。同日後半にセクション⑥を見直した。見出しは「家庭での続け方」なのに中身は実質購入フローで、STEP 01 は未実装機能への言及だった。新形は「はじめ方」5ステップ＝①レベルを選ぶ→②中身をたしかめる（SKU 詳細 #preview の紙面プレビュー）→③購入する→④印刷して机の上へ→⑤気が向いた日に次の一枚。購入の独立ステップ化はオーナー指示である。

**記事枠の実配線と fs 混入事故**。ハードコードのダミー記事4本を、新設の ArticlesSection.tsx へ分離し、slug 固定×タイトルは frontmatter に動的追従する形で実記事4本に配線した。この際、catalog.tsx に node:fs を使う articles-data.ts を import させたところ全ページが 500 になった。catalog.tsx は client component（CoverageStudio）からも import される共有モジュールだったためである。fs 依存をサーバー専用ファイルへ分離して解消したが、Turbopack が分離後も古いモジュールグラフを引きずり、dev サーバーの再起動まで必要だった。

**headless 検証の罠5点**。(1) ブラウザペイン非表示で requestAnimationFrame が凍結し、スクリーンショット系が全てタイムアウトする——JS 実行と DOM 計測は生きるので検証は JS で行う。(2) headless=new は stroke-dashoffset などメインスレッド系プロパティを再ペイントせず、computed 値は正しいのに絵が古いまま残る——絵の検証は値を焼いた静的 SVG を serialize して撮る。(3) 環境により prefers-reduced-motion が強制 true になる。(4) --window-size は最小幅制約で 390px にならず、CDP のデバイスエミュレーションが要る。(5) --virtual-time-budget は hydration 前にキャプチャされることがあり、実時間ポーリングが確実。

## なぜそう判断したか

**WAAPI を選んだ理由**。線分ごとに開始・終了タイミングが異なるため、keyframe の % はセグメント本数の関数になる。静的な CSS keyframes では図形ごとに定義を量産するしかなく、SMIL は実装バグを踏んだ。キーフレームを実行時に計算できる WAAPI が、この構造への素直な解だった。

**「レベル診断」と呼ばなかった理由**。オーナー自身は口頭で「レベル診断」と呼ぶが、画面文言は「レベルで選ぶ」とした。診断語彙は TENZU では概念レベルの Anti-Brand であり、社内の口語とブランド語彙を意識的に切り分けた。

**STEP 01 を書き換えた理由**。「代表1枚を無料公開」はサンプル閲覧プレビュー未実装のまま残っていた文言で、brand.md §8.3（未実装機能の外向け表示禁止）に抵触していた。新5ステップは各ステップの実装の裏付けを確認してから書き、実導線（ガイド結果→#preview）と順序を一致させた。

## 学び（一般化できるノウハウ）

1. **要素ごとにタイミングが変わるアニメは WAAPI で組む** — keyframe の % が要素数に依存する時点で静的 CSS には載らない。SMIL は実装バグの地雷が残る。キーフレームを実行時に計算して要素単位で適用できる WAAPI が、生成的アニメーションの安定した実装先になる。

2. **headless ブラウザの描画結果は検証のソースにしない** — 再ペイント省略・reduced-motion 強制・最小ウィンドウ幅など、headless は「実際の絵」と系統的に乖離する。状態は JS で computed 値を読む、絵は値を焼き込んだ静的出力で撮る、モバイルは CDP エミュレーションと、検証対象ごとに手段を分ける。

3. **共有モジュールに依存を足す前に import グラフを見る** — server/client 双方から import されるファイルにサーバー専用依存（node:fs 等）を足すと全ページが落ちる。データ取得はサーバー専用ファイルへ分離し、UI には結果だけを渡す。バンドラが古いモジュールグラフを保持することがあるため、分離後は dev サーバー再起動まで含めて確認する。
