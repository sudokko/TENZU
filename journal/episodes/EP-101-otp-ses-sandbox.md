# OTP 6桁認証の実装と SES サンドボックス診断（「成功に見えて届かない」を突き止める）

## 何が起きたか（要約）

認証方式の 3AI Deep Research（EP-098）で決めた「当面メール一本・メーカー＝OTP／商品＝マジックリンク」の実装編。メール OTP（6桁）をマジックリンクと両建てで実装し、ストア抽象（本番 Upstash／dev はメモリ）・列挙対策・試行ロック・単回使用まで含めて tsc と curl 8ケースで検証を通した。その後のオーナー実機テストで「届く端末と届かない端末がある」不達が発覚。診断スクリプト check-ses.mjs を新設して真因を SES サンドボックス（検証済みアドレス以外は送信拒否）と確定し、サンドボックス脱出をローンチ前必須のオーナー作業として残務に固定した。直後の買い切りピボット（§4.7）で OTP はログイン概念ごと撤回されたが、SES 診断と到達性の地固め課題はマジックリンク復元のために生き残った。

## 状況・背景

前段の 3AI DR では「マジックリンク単独の長期運用は不可・メール OTP フォールバック必須」が3者一致し、オーナーは Google/LINE と DB の導入を先送りして「当面メール一本」を選んだ（EP-098）。ロードマップの梅スコープ＝OTP 主役＋リンク fallback＋最小 KV（Upstash）が今回の実装範囲である。土台は既にある。会員マスタは持たず Stripe が台帳、ログイン状態は HMAC 署名 cookie 自身が持つ DB レス構成（EP-087）で、email が唯一のキー。リンクは商品 DL・会員申込直後・会員再ログインの3種に整理され、OTP が受け持つのは再ログインのみ。OTP の状態は会員台帳ではなく、総当たり対策のために TTL 付き最小 KV を要する「半分 DB 不要」の存在と位置づけた。

## やり取りの中身

**ストア抽象と2本の API**。新規は3ファイル。otp-store.ts に OtpStore 抽象を置き、Upstash 実装とメモリ実装を env の有無で自動切替にした＝Upstash アカウントがなくても dev が完結する。request-otp は非会員にも {ok:true} を返す列挙対策・60秒の送信スロットル・1時間5回の上限。verify-otp は試行5回ロック・成功時削除の単回使用・timingSafe 照合。コードは crypto.randomInt の6桁、ハッシュは email をソルトにした HMAC、メールは件名にコードを載せず有効10分とした。

**既存セッションへの無改修接続**。verify-otp が成功時に発行する cookie を既存 sessionCookie と完全同形にし、/api/me・MakerApp・AuthContext・capabilities という下流を一切改修せずに済ませた。curl 8ケース（不正・非会員・期限切れ・誤コード・成功・再使用など）で Set-Cookie の中身まで見て、「下流無改修の生命線」を実測で証明した。UI は /login を email→code の2段階に作り替え、再送60秒クールダウンと inputMode=numeric・one-time-code を付けた。

**「届かない」の診断**。06-25、オーナー実機で「届く端末/届かない端末がある」不達が出た。端末差に見える症状だが、切り分けに check-ses.mjs（GetSendQuota＋ListVerifiedEmailAddresses）を新設して確定した真因はアドレス差＝SES サンドボックスだった。送信上限200通/日・検証済みはオーナーのアドレス1件のみで、未検証宛は SES が拒否する。しかも request-otp は列挙対策で例外を握り潰して {ok:true} を返すため、「成功に見えて届かない」が仕組みとして完成してしまっていた。本番で起きれば事故なので、サンドボックス脱出を最優先のオーナー作業に格上げした。

**列挙対策と親切さの両立**。オーナーから「届かないのに成功に見えるのは UX 的にどうか」という指摘が出た。採った答えは「会員かどうかは漏らさず、届かないときのセルフヘルプを厚くする」。コード入力画面の文言を「ご登録のメールアドレス宛にお送りしました」と婉曲に登録要件を示唆する形にし、迷惑メール・申込時アドレスの確認導線を添えた。「非会員なので送れません」と明示する案は列挙対策を壊すため不採用とした。

## なぜそう判断したか

**ストアを抽象化した理由**。OTP の状態は TTL で自己消滅する一時キャッシュであり、DB レス思想を壊さない。ただし本番は Lambda 分散なので共有 KV が必須で、dev はメモリで十分。インターフェイスを1枚挟めば、Upstash アカウント調達というオーナー作業を待たずに実装と検証を先に終えられる。

**cookie 同形を守った理由**。認証の追加は影響半径が広がりやすい。出口を既存セッションと同形に固定すれば変更は「入口の増設」に閉じ、下流の回帰確認が最小で済む。無改修で温存する対象を先にリスト化してから実装した。

**{ok:true} の握り潰しを維持した理由**。列挙対策は「会員アドレスかどうかを外から観測させない」ための意図的な嘘で、SES 拒否まで隠れたのは副作用である。嘘をやめれば UX は素直になるが攻撃者にも素直になる。だから嘘は維持し、運営者だけが真実を見られる裏口（check-ses.mjs）と利用者向けセルフヘルプで補った。

**撤回を受け入れた理由**。06-26 の買い切りピボットの帰結として、翌日にはログイン概念そのものが廃止され（§4.7）、OTP 一式は削除対象になった。買い切りの entitlement は永続で「守るべき状態」がなく、再ログイン自体が消えるからだ。これは実装の失敗ではなく前提の変化で、SES サンドボックス脱出・SPF/DKIM/DMARC の地固め・診断スクリプトはマジックリンク復元のために残った。

## 学び（一般化できるノウハウ）

1. **意図的に「成功に見せる」設計には診断の裏口をセットで作る** — 列挙対策の {ok:true} のような意図的な嘘は、実障害（今回は SES 拒否）まで隠す。嘘を仕込むと決めた時点で、運営者だけが真実を照会できる診断手段を同じ変更の中で用意しておく。

2. **「端末で違う」症状はサービス側の契約状態から疑う** — 届く/届かないが端末差に見えても、真因はアドレスごとの検証状態だった。推測で潰さず、quota や検証済みリストを API で直接照会して、分類軸（端末か・アドレスか）ごと確定させる。

3. **認証機構の寿命は課金モデルに従属する** — サブスク前提で必須だった OTP は、買い切り転換で概念ごと消えた。モデルが揺れている間の認証は撤回可能な形（抽象ストア・既存 cookie 同形・下流無改修）で作ると、撤回時にも診断ツールと基盤だけが資産として残る。
