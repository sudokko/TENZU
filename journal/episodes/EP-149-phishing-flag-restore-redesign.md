# Chrome が赤い全画面を出した（フィッシング判定と、権限を渡す経路の再設計）

## 何が起きたか（要約）

開店前日、メーカー買い切りの復元リンク `https://tenzu.jp/api/auth/verify?token=…` を Chrome が**赤い全画面の「危険なサイト」**でブロックした。Google Safe Browsing の**ソーシャルエンジニアリング（フィッシング）判定**で、警告文は「パスワードやクレジットカード番号などを開示させる可能性」。URL の**形**が撃たれたと診断し、**人が読めるページ `/restore` を挟んで、説明を読ませてからボタンで権限を発行する**経路へ組み替えた。同日デプロイし、翌朝には判定が解除されていることを実ブラウザで確認した（decisions §3.114）。

## 状況・背景

メーカー（¥980）は「作る道具を使う権利」の買い切りで、所有はブラウザの署名 cookie が持つ。別端末で使うときだけ、メールのマジックリンクから所有を再発行する。この復元リンクが撃たれた。

きっかけはオーナーの指摘だった——「購入した人からすると正直いって分かりにくい」。**権利を買っていること・端末に紐づくこと・他の端末では復元が要ること**が、どこにも書かれていなかった。その指摘を受けて説明を足そうとしていた矢先に、警告が出た。

## やり取りの中身

**4 つの要因が重なったと診断した**。①**評判ゼロの新規ドメイン**（接続から 2 週間）②`/api/…` の下に**長い不透明トークン** ③**開いた瞬間に権限が発行される**（GET で cookie を mint）④リンク元が**迷惑メール判定されたメール**（EP-148）。この 4 つは資格情報フィッシングの構造そのもので、**中身ではなく形が判定される**。

**切り分けでは範囲の確定が要点だった**。Search Console の「手動による対策」は別レポート（スパムに対する人手のペナルティ）で、見るべきは「セキュリティの問題」。そこに「不正なページ」1 件が出ていた。「URL の例：該当なし」は個別 URL に限られた証拠ではなく、**フラグされた URL がインデックスされていない API URL だから例示できていない**と読むのが自然だった。

**紙の DL リンクと非対称な理由を言語化した**。紙（¥200）のメールに載る URL は永続でよい——漏れても「その PDF が落ちる」だけ。復元リンクは**所有権そのものを発行する**ので、転送・盗み見でそのまま権利が渡る。だから 30 分で切れる。この非対称は意図的なものだった。

**組み替えは 3 点**。①`/restore?t=…`（新設）へ着地させ、何が起きるかを読ませてからボタンで `POST` する ②GET でトークンを消費しない ③旧 URL は互換で残すが、発行はせず `/restore` へ受け流すだけ。Stripe からの復帰（`GET ?session_id=`）は**リダイレクト着地なので従来どおり**——メールに載らず、不透明トークンでもない。

**メール本文の順序も入れ替えた**。旧文は「30 分間有効」しか書いておらず、**なぜ 30 分なのか・切れたらどうするか**が無かった。新文は ①買った端末ではもう使える（メールを開く必要すらない）②別の端末で使いたいときだけこのボタン ③切れても再送できる、の順。**リンクを「必須の関門」ではなく「任意の道具」として見せる**。

## なぜそう判断したか

**警告への対処と UX の改善が、同じ 1 つの修正に収束した**。フィッシングらしさの 3 要素（API パス・自動実行・説明ゼロ）を消す作業は、そのまま「購入者に何を買ったか伝える」作業だった。**別々の問題に見えたものが、同じ原因（説明のない自動処理）から出ていた**。

**30 分を延ばさなかった**。警告を避けるだけなら有効期限を延ばして摩擦を減らす手もあるが、それは権限発行リンクの寿命を延ばすことで、リスクの方向が逆である。短命のまま**再送で運ぶ**設計を維持した。

**残った宿題も書いた**。トークンは `base64url(JSON)＋HMAC` なので**戻すと購入者のメールアドレスが読める**。署名で改ざんは防げているが、URL に個人情報が乗っている。暗号化は開店後に回した。

## 学び（一般化できるノウハウ）

1. **URL は「形」で評価される** — 中身が正当でも、`/api/` 配下・長い不透明トークン・開いた瞬間に処理、という組み合わせは攻撃者の典型パターンと一致する。**利用者に説明できない URL は、機械にも説明できない**。

2. **権限を発行する操作に、人間の明示的な一手を挟む** — GET で副作用を起こさない原則は、セキュリティだけでなく信頼の問題でもある。説明ページ 1 枚が、警告の回避と UX の改善を同時に果たした。

3. **「分かりにくい」という指摘は、たいてい構造の問題を指している** — 文言を足すだけでは解けないことがある。今回は経路そのものを変えたことで、説明の置き場所が自然に生まれた。
