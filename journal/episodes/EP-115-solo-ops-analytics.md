# ソロ運転計画（週3ブロック・縮退設計）と GTM 計測配線

## 何が起きたか（要約）

「ローンチ後にひとりで回るか心配」というオーナーの相談（2026-07-07）を起点に、開店後の運用を束ねる統合運転レイヤーを新設した。中核は①週3ブロック制（B1 運転席／B2 記事／B3 量産バッチ・計3.5〜4.5時間/週）、②忙しい週にどこまで落とすかを事前に決める縮退設計、③計測配線を開店前の必須ゲートに置く段取り、の3点。SSOT は launch/operations.md に置き、Notion ダッシュボードにも同内容を併設した。続けてツール整備ロードマップ6件を消化し、B1 を対話1回で終わらせる weekly-ops スキルなどを整備。並行して GTM/GA4 の計測配線（dataLayer 方式・tool_start／generated_pdf／purchase の3イベント）を実装し、07-13 にコミット fd0d0e4 として確定した。残るは GA4/GTM コンソール設定（約1時間）・プライバシーポリシーの外部送信記載・Canva テンプレ作成という人間側の作業のみとなった。

## 状況・背景

TENZU はオーナーが本業の傍らで運営するソロ副業である。設計上のピーク負荷を積み上げると週7〜9時間になり、これは常態化できない。しかも開店後は記事・SNS・DM・計測・問題量産が同時に走る。この時点の基準線では T=0（開店）を2026年11月中旬に置き、1月の春 LP→2〜4月の入学準備スパイクへ直結させる想定だった（のちの 07-11 ローンチ体系ピボットで T=0 は 2026-08-30 の単一開店へ前倒しされたが、ここで作った運転構造自体は引き継がれた）。計測については funnel 側に GTM 前提の設計だけがあり、コードはゼロ。「計測してから開店する」を先回りで済ませるのがこのセッション群の狙いだった。

## やり取りの中身

**週3ブロック制と縮退設計**。運用を B1 運転席（数値確認・週次プラン・SNS 草稿）、B2 記事、B3 量産バッチの3ブロックに畳み、曜日固定は廃止した。縮退設計は「忙しい週に何を削るか」の順序を事前に決めるもので、削る順は IG→note→DM→X、絶対に守る3つは記事隔週・Pinterest 予約・計測と定めた。SSOT は launch/operations.md に置き、Notion「TENZUリリース後にやること」ページへ同内容を併設、設計変更時は両方更新する運用とした。

**ツール整備ロードマップ6件**。①計測配線②weekly-ops 週次コックピット③IG カルーセル生成④X 草稿ジェネレータ⑤DM 運用キット⑥週次レポート自動化、の優先順で着手した。weekly-ops は B1 を対話1回で終わらせるスキルで、GA4 開通前は「数値なしモード」で動き、運転ログは launch/ops-log.md へ追記する。④は②へ統合して欠番、⑥は GA4 実データ2週間分と手動運用2〜3回を前提条件に方針のみ確定で止めた。DM キットには週5件枠・14日期限・送信は100%人間という制約を内蔵させ、ロードマップは全6件をクローズした。

**GTM 計測配線の実装**。コードは dataLayer に push するだけとし、GA4 や広告タグは GTM コンソール側で管理する方式にした。NEXT_PUBLIC_GTM_ID 未設定なら全計測が no-op になり、dev 環境はそれが正。実装は analytics.ts（track 関数・GTM ゲート・purchase の localStorage 二重送信ガード）と Gtm.tsx・TrackPurchase.tsx。イベントは tool_start（メーカー編集画面ヘッダーのマウント・全11メーカーをパスから導出）、generated_pdf（PDF 書き出しの save 直後）、purchase（紙は /checkout/success、メーカーは /maker-thanks）の3つだけで、発火点はすべて単一箇所に寄せた。メーカーのアタッチ率（紙購入者のうちメーカーも買った率）は purchase の purchase_kind／item_category で paper と maker を区別し、GA4 探索のセグメント重複で集計できるため専用実装は不要と判断。イベント定義・UTM 命名規則・コンソール設定手順は engineering/analytics.md を SSOT にし、tsc と dev 実機での dataLayer push を確認して確定した。

## なぜそう判断したか

**縮退の順序を事前に決めた理由**。ピーク7〜9時間/週はソロ副業では続かない。忙しい週に「何を削るか」をその場で考えると、判断自体が負荷になり、罪悪感で削れもしない。最低運転と拡張レイヤーを分離し、削る順番と死守ラインを事前に文書化しておけば、当日の判断コストはゼロになる。

**タグ管理を GTM コンソールへ寄せた理由**。Phase 1 で Meta Pixel や Google 広告タグを足すことが既に見えている。タグをコードに書くと追加のたびにデプロイが要るが、コード側の責務を dataLayer への push に限定すれば、タグ追加は GTM コンソールの操作だけで完結する。funnel 側の設計とも一致する。

**イベントを10個から3つに絞った理由**。operations.md の「最初から全部やらない」方針に従った。開店直後に答えるべき問いは「ツールは使われたか・PDF は出たか・買われたか」で、ファネルの根幹はこの3イベントで引ける。網羅性より配線の確実さを優先し、細かいイベントは運用が回ってから足す。

**アタッチ率に専用実装を作らなかった理由**。purchase の属性に paper/maker の区別を持たせれば、GA4 の探索機能がセグメント重複として算出してくれる。集計ロジックを自前で持つより、送信データの設計で解決するほうが保守物が増えない。

## 学び（一般化できるノウハウ）

1. **縮退は事前に設計しておく** — ソロ運用の計画は「理想の週」ではなく「忙しい週」を基準に作る。削る順番と絶対に守る最低ラインを先に文書化しておくと、繁忙時の判断コストがゼロになり、計画が現実に耐える。

2. **定型運転は対話1回の道具に畳む** — 毎週繰り返す運用ブロックは手順書として覚えるのではなく、1回の対話で完了する道具（スキル）にする。前提が揃う前でも動く縮退モード（数値なしモード）を用意すれば、道具は初日から回り始める。

3. **計測コードは push だけにしてタグ運用を外部コンソールへ寄せる** — 計測は開店前の必須ゲートに置きつつ、コード側の責務を dataLayer への push に限定する。ベンダータグの追加・変更がデプロイ不要になり、イベント数を開店直後の問いに答える最小本数へ絞ることで配線の確実さも保てる。
