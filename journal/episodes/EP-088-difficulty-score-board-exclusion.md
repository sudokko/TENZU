# 難易度スコアから盤面項を外す（Lv と巻内散らしの責務を分離する）

## 何が起きたか（要約）

模写（図形）の難易度評価を「多次元 band（線数・斜め・交差・構成要素のレンジ）」から「スカラ D ＋種類ゲート」へ再設計し、最終的に **D の式から盤面（grid size）項を完全に外した**。確定式は `D = 線本数 + 1.5·交差 + 12·[非45°あり]` の3項のみ。旧実装は盤面を `6·(n−2)` で盛っていたが、オーナーが32枚を目で格付けして取った回帰（ρ=0.878）では盤面の係数は非45°の0.16倍ほどしか効かず、盛りすぎだった。核心の転換は、**「Lv（巻の難度）＝盤面サイズ」と「D（巻内12問の散らし）」の責務を完全に分けた**こと。盤面の難しさは既に Lv が背負っているので、巻内では盤面は一定＝D には寄与ゼロが正しい。同じ盤面に2巻が並ぶ箇所はゲート（種類制限）で住み分けた。振り分けは盤面項除外の前後で完全一致（スコアと窓から同じ定数を引いただけ）し、atelier の表示も D 昇順へ作り直した。

## 状況・背景

模写のレベルは Lv×Vol の8段で、現行の `COPY_LADDER`（[copy.ts](C:\dev\TENZU\web\app\products\problems\gen\copy.ts)）は各巻に多次元の band（lines/diag/cross/comp のレンジ）を割り当てていた。機械的には逸脱ゼロで守られていたが、band が広すぎて隣接巻と重なり、巻内のばらつきが9倍に開き、難易度の逆転（lv4-vol1 の中央値 < lv3-vol2）まで起きていた。「同じ巻の12問なのに、易しいのと難しいのが極端に混ざる」「上の巻より下の巻が難しく見える」状態である。難易度を一つのスカラで素直に表せないか、というのが出発点だった。

## やり取りの中身

まず校正をやり直した。オーナーが32枚の図形を目で見てティア付けし、メトリクス（線数・斜め角・交差・構成要素数・盤面）を説明変数に最小二乗で回した。出た生フィット係数は、切片0.93／盤面0.182／線0.110／斜め−0.034／交差0.146／構成要素−0.066／非45°1.162。**非45°が断トツのドライバー**で、線を1.0 にスケールし直すと盤面≈1.65・交差≈1.33・非45°≈10.6 になる。斜めは効かず（≈0）、構成要素は符号が不安定だった。

ここから素直に丸めて `D = lines + 1.5·crossings + 12·hasNon45` を組んだ（交差1.33→1.5・非45°10.6→12）。斜めと構成要素は D から落とした。非45°は `hasNon45` フラグで測る——旧来の `diagonalAngleKinds>1`（斜め角の種類が複数）では「45°でない角が1種類だけ」を取りこぼす誤りがあったので、`schema.ts` の `ProblemMetrics` に `hasNon45:boolean` を足し、`metrics.ts` の角度集合から算出するようにした。

問題は盤面項だった。生フィットでは盤面≈1.65/段だが、旧実装は `6·(n−2)`＝約3.6倍に盛っていた。これは過去にオーナーが「Lv＝盤面サイズという分かりやすさを優先する」と意図的に選んだ盛りだった（データ忠実だと直感が崩れる、と提示した上での選択）。今回それを **完全に外した**。

そして同じ盤面サイズに複数の巻が乗る箇所——4×4 の Lv2/Lv3、5×5 の Lv3/Lv4——は、D の窓ではなく**種類ゲート**で住み分けた。4×4 は「交差の壁」（片方は交差あり必須）、5×5 は「非45°の壁」（片方は非45°必須）。盤面が同じでも、許す図形の種類で巻の性格を分けた。`COPY_LADDER` は band レンジを捨て、`slopes/fullGrid/requireNon45/requireDiag45/cross[zero|some|any]` のゲート＋D の狭い窓へ全置換した。

検証で重要だったのは、**盤面項を外しても振り分けが一切動かなかった**ことだ。各巻の D 窓も旧値から盤面ぶん（巻内で一定の定数）を引いた値に直したので、「スコアと窓の両方から同じ定数を引いた」だけになり、test-gen の供給数は改修前と完全に一致した。atelier 側は各設問カードの外に D と略式内訳（線+交差+非45°）を出し、候補を D 昇順の一枚壁に並べ替えた（旧来の線数バケツ・エンジン分割は撤去）。

## なぜそう判断したか

盤面項を外した理由は、**難易度の二つの軸を一つのスカラに混ぜていたから**だ。一つは「この巻はどれだけ難しいか」という巻間の軸。もう一つは「この巻の12問の中で、どれが易しくどれが難しいか」という巻内の軸。盤面サイズは前者を決める主役だが——巻が決まれば盤面は固定なので——後者には一切効かない（12問はすべて同じ盤面だから）。だから D の役割を「巻内の散らし」に限定すると、盤面は定義上寄与ゼロであるべきで、入れること自体が論理的に誤りだった。

校正データもそれを裏づけていた。盤面の生係数は非45°の0.16倍ほどしかないのに、旧実装はそれを3.6倍に盛っていた。「Lv＝盤面の分かりやすさ」を D に背負わせると、巻内の散らしが盤面の盛りに飲まれて潰れる。盤面の難しさは Lv が既に表現しているのだから、D で重ねるのは二重計上にすぎない。**責務を分ければ、盤面は Lv に、散らしは D に、と自然に置き場所が決まる。**

ここには「データ忠実（案A）」と「直感の分かりやすさ（案B）」の衝突があった。過去のオーナー判断は案B（盤面を盛って Lv の体感を作る）だったが、今回それを案A 寄りに戻せたのは、衝突を「どちらを選ぶ」問題でなく「責務分離」で解いたからだ。Lv の分かりやすさは巻のゲート設計で担保すればよく、D はデータ忠実な巻内スコアに徹せられる。別の場所に置けば、片方のために片方を歪める必要が消える。同じ盤面の2巻をゲートで分けたのも同じ思想で、「交差を許すか」「非45°を許すか」という種類の壁を立てれば、盤面に頼らず巻の手触りを変えられる。盤面以外の軸で差別化できると分かったことが、盤面を外す前提条件にもなった。

## 学び（一般化できるノウハウ）

1. **一つのスコアに「区分間の軸」と「区分内の軸」を混ぜない** — 難易度のような量は「どの区分（巻・レベル）か」と「区分の中での相対位置」の二層で効くことが多い。両方を一つのスカラに足し込むと、区分が固定された時点で寄与ゼロのはずの項（ここでは盤面）が、区分内のばらつきを飲み込んで潰す。スコアの役割を「区分内の散らし」に限定するなら、区分で固定される変数は定義上そのスコアから外すのが正しい。区分間の差は別の仕組み（ゲート・レベル定義）で担保する。

2. **「データ忠実 vs 直感」の衝突は、責務分離で解けることがある** — どちらを採るかの二択に見える対立は、しばしば「一つの式に二つの目的を背負わせている」ことが原因だ。目的を別の場所に分ければ、直感のための歪め（盤面を3.6倍に盛る）でデータ忠実を犠牲にする必要が消える。直感は区分設計（巻のゲート）で、忠実さは区分内スコアで、と置き場所を分ける。

3. **係数は目視ティア付け＋回帰で取り、断トツのドライバー以外は落とす** — 主観的な難易度を、人が並べた順位を正解データにして回帰で数値化できる。ただし出た係数を全部使うのではなく、効きが小さい項（斜め≈0・構成要素は符号不安定）は落として式を3項に絞った。少数の効く項だけにすると、後で値を手で調整するときも見通しがよい。

4. **再設計が「振り分けを変えない」ことを示せると安全に入れられる** — 式と窓の両方から同じ定数（区分内で一定の項）を引けば、出力の振り分けは数学的に不変になる。test-gen の供給数が改修前と完全一致することを確認したので、「式は綺麗になったが結果は変わっていない」と証明できた。大きな再設計を、挙動を保ったまま入れる手筋になる。
