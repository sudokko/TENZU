# マイページ廃止→自前マジックリンクへ

## 何が起きたか（要約）

当初は AWS Cognito とマイページ（購入履歴・設定・プロフィール表示）を想定していたアカウント機能を、ダウンロードページ最小機能＋自前マジックリンク（Lambda 2個 ＋ DynamoDB tokenテーブル ＋ SES、15分期限・1回使い切り）に大幅削減した。2026-04-26 の C-3 サービスブループリント設計セッションで「会員登録なし哲学」との矛盾に気づいたことが引き金だった。

## 状況・背景

TENZU は設計当初から「会員登録なし哲学」を掲げていた。購入のたびにアカウント作成を求めると、教育商材を探す保護者が直前で離脱するリスクがあるという判断だった。Stripe Checkout は決済時にメールアドレスだけを取得し、その後の PDF ダウンロードも基本的には Stripe 標準のメールリンクで完結させる方針だった。

しかし C-3 設計のフェーズに入ったとき、「購入後に自分の購入履歴を確認したいユーザーのためにマイページが必要では」という論点が浮上した。マイページを設けるためには、ユーザーを識別するためのログイン機構が必要になり、候補として AWS Cognito が検討対象に挙がった。

この段階で当初の「会員登録なし」と「マイページ有り」の間に深刻な矛盾があることが議論の中で明らかになった。

## やり取りの中身

### 「マイページ」という UX 用語の問題

「マイページ」という言葉を聞いた瞬間にユーザーが想起するのは、「会員登録して、IDとパスワードを作って、ログインする」という一連の体験だ。教育商材サービスでこのフローを設けることは、「試しに ¥200 で買ってみる」という軽い入口を分厚いバリアで塞ぐことになる。

この観点を整理すると、「会員登録なし哲学」と「マイページ有り」の同居は構造的に成立しない。マイページそのものを廃止し、「購入後にダウンロードできる最小限のページ」だけを設ける方向に転換した。

### 削減した機能と残した機能

**廃止したもの**
- 会員登録フロー（メールアドレス＋パスワード設定）
- マイページ（購入履歴閲覧・プロフィール・設定画面）
- AWS Cognito の Custom Auth Challenge

**残したもの**
- 購入後のダウンロードページ（最小限の機能）
- 自前マジックリンク（15分有効・1回使い切り）
- 解答ページの公開化

### Cognito を外して自前実装を選んだ理由

Cognito はユーザー認証の総合サービスであり、本来はメール認証・MFA・ソーシャルログイン・ユーザープール管理など多くの機能を持つ。TENZU が必要としていたのは「購入者に一時的なダウンロードリンクを届ける」という単機能だけだった。

この単機能のために Cognito を導入すると、月額固定費・設定の複雑性・Cognito に依存したアーキテクチャが全て発生する。一方で Lambda 2個（リンク生成用・検証用）＋ DynamoDB tokenテーブル＋ SES での自前実装であれば、ほぼ従量課金ゼロで同等の機能が実現できる。個人運営の基準は「運用しきれる複雑度」であり、Cognito はその基準を超えていた。

### 連鎖的な簡略化

マイページ廃止は他の設計にも連鎖した。

購入履歴の「長期保持・ユーザー側での参照」要件が消滅したため、セッション管理の複雑性が大幅に低下した。また、マイページがなくなると「ユーザーごとにカスタマイズされた PDF 生成」の動機も薄れ、PDF はレイアウトパターン別の事前生成（2問/3問/4問/6問/12問ページ、計 745 ファイル程度）に切り替えることができた。

さらに「解答ページの公開」との組み合わせにより、当初マイページが担う予定だった「問題の確認・復習機能」も不要になった。解答ページを公開することで、購入者は URL さえ知っていればログインなしで丸つけができ、未購入者にとっては質の確認ができるという設計が成立した。

## なぜそう判断したか

機能名称がユーザーの心理モデルを決める。「マイページ」という言葉は、設計者には「購入後のサポート機能」に見えていても、ユーザーには「会員登録が必要なもの」に映る。TENZU の「会員登録なし哲学」は、このユーザー心理との整合を要求していた。

マネージドサービスの採用基準は「使えるから使う」ではなく「その機能が自前実装の難易度を上回るか」だ。Cognito が提供する機能群の大半は TENZU では不要であり、必要な単機能だけを最小コストで実現できる自前実装の方が合理的だった。

個人運営では「削れるものを削る」の連鎖が設計の最適化を生む。マイページを外すことで、認証・セッション・PDF生成・履歴保持の各設計が軽くなり、全体として実装コストが大幅に下がった。

## 学び（一般化できるノウハウ）

1. **UX 用語の選択が顧客心理を左右する** — 「マイページ」は登録と同義に感じられる。機能の中身よりも呼び名がユーザーの認知コストを決める場合がある。

2. **機能削減は連鎖最適化を生む** — 一つの機能を削ると、その機能に依存していた他の要件も消え、簡略化が連鎖する。最初に「本当に必要か」を問うことが設計全体の軽量化につながる。

3. **マネージドサービスの過剰利用を避ける** — 1機能のために重い基盤を入れない。必要な機能の最小単位で自前実装できる場合は、コスト・複雑性・依存関係の観点で自前の方が有利なことが多い。
