# Storybook/Chromatic不採用——Amplify Preview で UI 確認を完結させる判断

## 何が起きたか（要約）

UI コンポーネントの確認・管理ツールとして「Storybook + Chromatic（ビジュアルリグレッションテスト）」の導入を検討したが、不採用とした。代わりに「AWS Amplify の PR プレビュー環境」を使って、実際の動作環境でのビジュアル確認を行う方針を確定した。Storybook は確かに強力なツールだが、個人開発者が維持するオーバーヘッドに比べて得られるメリットが小さいと判断した。

## 状況・背景

2026-04-22 のセッション、C-4（Priority Guides 設計）に向けた技術的な準備の議論の中で、「UI コンポーネントをどうやって確認するか」という問いが生まれた。

フロントエンド開発（Next.js + shadcn/ui）では、コンポーネントの表示確認に2つのアプローチがある：

1. **コンポーネントカタログ方式（Storybook）**: 各コンポーネントを独立して表示・確認・管理する専用ツール
2. **実動作環境確認方式**: 実際のアプリを動かして確認する

TENZU のような個人開発プロジェクトでは、どちらが適切かが論点になった。

## やり取りの中身

Storybook の採用を検討した背景は「チームでの UI 変更レビュー」の必要性だった。しかし Claude がすぐにコンテキストの問題を指摘した：

> 「Storybook が最も価値を発揮するのは、複数人のフロントエンドエンジニアがコンポーネントを並行して開発する時。デザイナーと開発者が別にいて、コンポーネントカタログでコミュニケーションする時。1人で開発するなら、Storybook を維持するコストの方が大きくなる可能性がある。」

Storybook 導入の具体的なコストを整理した：
- 各コンポーネントに `.stories.tsx` ファイルを書く必要がある
- Chromatic（ビジュアルリグレッション）は月額課金が発生する
- Storybook のセットアップと Next.js の設定を維持する手間がある
- コンポーネントが変更されるたびに stories ファイルも更新が必要

これらに対して、TENZU が必要とする「UI 確認」の実態は：
- 「PR をマージする前に、実際のページがどう見えるか確認したい」
- 「デザイン変更がモバイル・タブレット・デスクトップ全幅で崩れていないか確認したい」

この目的は Amplify の PR プレビュー環境で完全に満たせることが分かった：

> 「Amplify は PR が作られると自動でプレビュー環境を生成してくれる。実際の Next.js アプリが本番と同じ設定で動く環境が URL として発行される。そこで全デバイス幅を確認すれば、Storybook と Chromatic でやっていたことと実質同じことができる。しかも実際のデータフローの中での表示も確認できる。」

確定した設計：
- **Storybook/Chromatic**: 不採用
- **UI 確認手段**: Amplify Preview（PR ごとに自動生成される本番同等の確認環境）
- **ビジュアルリグレッション**: Amplify Preview URL で手動確認

## なぜそう判断したか

判断の核心は「ツールが解決する問題が TENZU には存在するか」という問いだった。

Storybook は「コンポーネントを独立して開発・テストする必要がある」という前提で価値を持つ。複数人開発では「このコンポーネントは誰が変更したのか」「このコンポーネントのインターフェースは何か」というコミュニケーション問題が生じる。Storybook はその問題を解決する。

しかし TENZU は1人開発だ。コンポーネントの変更履歴は Git で管理できる。インターフェースは自分が書いたコードだから自分が知っている。Storybook が解決する「チームコミュニケーション問題」が存在しない環境に Storybook を入れても、維持コストだけが増える。

Amplify Preview を代替にする判断は「目的に対して最小のツールを使う」という個人開発の原則と一致する。「本番と同じ環境で確認できる」という意味ではむしろ Storybook より信頼性が高い（Storybook では本番のデータフローや API 統合は確認できない）。

## 学び（一般化できるノウハウ）

1. **ツールが解決する前提問題を確認する** — Storybook は「チームのコンポーネント管理問題」を解決するツール。その問題が存在しない1人開発で導入しても、コストだけが生まれる。ツールの採用前に「このツールが解決する問題は自分にあるか？」を問う。

2. **インフラが提供する機能で代替できないか確認する** — Amplify Preview はすでに使うインフラに付随する機能だった。追加ツールの前に「今持っているものでできないか」を確認することで、スタック複雑化を防げる。

3. **「1人開発」は制約ではなくスタック削減の正当化理由** — チームツールを個人が使う理由は「将来チームになる可能性」だけだ。MVP フェーズでその投資を正当化できるかを厳しく問う。
