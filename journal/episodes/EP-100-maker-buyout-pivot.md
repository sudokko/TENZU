# メーカー有償化をサブスクから per-maker 買い切り ¥980 へピボットする（実装直後の自己撤回とクロスセルの旗）

## 何が起きたか（要約）

2026-06-21 に設計・実装し 06-23 にコミットまで済ませたメーカーの2段階サブスク（スタンダード ¥480／フル ¥980 月額）を、06-26 に自ら撤回した。きっかけはオーナーが持ち込んだ「メーカーを主役に全面ピボット＋サブスク化」案で、3AI 合議（Claude 反証担当／Gemini／ChatGPT）で検証した結果、全面ピボットは見送り、同時にサブスクモデル自体も廃止になった。確定したのは per-maker 買い切り ¥980・無期限（模写は無料）。主役はあくまで ¥200 のレベル別 PDF プリントで、メーカーは「¥200 を買った人へのクロスセル商材」かつ「自分で作れる工房付きの唯一の点描写プリント店」という差別化の旗に位置づけ直した。有料ゲートは PDF 書き出し1点に置き、メーカー自体は誰でも触れる。決定は decisions §4.6 に新設し、§4.4/§4.5 のサブスク tier を撤回した。

## 状況・背景

メーカー有償化は 3AI 合議で「2層会員・種類課金」まで詰め、オーナー判断で ¥480/¥980 の2段階サブスクを初手採用した経緯がある（EP-094）。06-21 に決済・認証・entitlement 基盤と tier ゲートを一気通貫で実装し、Stripe テストモードで申込→Checkout→ログインメール→tier 反転まで実証。06-23 に tier 名をスタンダード/フルへ確定しコミットした。ただしこの実装は最初から「戻れるようになる前提で一回実装しちゃってみて」というオーナー指示で走らせており、decisions や pack-design への SSOT 反映は「オーナーがこれでいくと決めてから」と意図的に保留していた。そこへオーナーから「メーカーを主役に全面ピボット＋サブスク化」の検討が持ち込まれた。

## やり取りの中身

**3AI 合議での検証**。ピボット案を Claude（反証担当）・Gemini・ChatGPT の3者で評価し、4点で全社一致した。①この事業の堀は9操作のメーカー機能ではなく、編集眼・難易度設計・カリキュラム＝「良問しか作れない」状態にある。②検討線上にあった ¥200/週のような少額継続課金は買い切りを食うため廃止。③9メーカー個別売りは作り手目線であり、見せ方は「伸ばす力」軸で束ねる。④需要未検証のままの全面ピボットは危険で、クロスセルのアタッチ率こそが実銭の需要検証になる。3社一致のみを確定として扱う運用は EP-098 と同じである。

**確定モデル**。価格は per-maker 買い切り ¥980・無期限。9メーカー個別販売（全部で約 ¥8,820 相当）、模写メーカーだけは無料で実用に足る形を残す。有料ゲートはページ入室ではなく PDF 書き出しに置き、誰でも全メーカーを触ってプレビューできる。スクショ対策は軽い透かしにとどめ過剰防御しない。entitlement は「tier ランク」から「所有メーカーの集合」へ変わる。宣伝面ではインフルエンサーへ全メーカーを無料付与し、追跡割引コードでチャネル化する設計も添えた。

**ログイン廃止への連鎖**。翌 06-27、買い切り化の帰結として「ログイン」概念そのものを廃止した（§4.7）。サブスクは解約で契約状態が変わるため本人追跡と 24h の Stripe 再照会が要ったが、買い切りの所有は永続で取り消されない。購入時の Stripe Checkout がメール取得を兼ね、success リダイレクトで所有メーカー集合を署名 cookie に mint する＝この瞬間がログインの代替になる。06-27〜28 のコード再設計で capabilities.ts を tier→所有判定へ作り替え、subscribe・billing-portal・OTP 系の API を削除し、9メーカーの書き出し処理冒頭に所有ゲートを差した。tsc・build とも緑で、/api/maker-checkout が実 Stripe Checkout URL を返すことまで確認した。

## なぜそう判断したか

**全面ピボットを見送った理由**。メーカーへの需要はまだ1円も検証されていない。主役の入れ替えを支えるのは「面白いものができた」という作り手の手応えであって、市場の証拠ではない。クロスセルなら、プリント購入者へのアタッチ率という形で需要が実銭で測れる。閾値を超えたら本格投資すればよく、ピボットの選択肢も失われない。

**サブスクから買い切りへ替えた理由**。合議の核①が効いている。堀が9操作の機能でなく編集眼とカリキュラムにあるなら、機能への月額課金は据わりが悪く、メーカーは「道具を1つ買い切る」型が商材の性質に合う。少額継続課金は買い切りと共食いするため共存できない（②）。さらに買い切りは entitlement が永続になり「守るべき状態」が消えるため、ログイン・再照会・解約追跡という重い装備が丸ごと不要になる（§4.7）。

**作りたてを実装ごと捨てられた理由**。06-21 の実装が「戻れる前提」で走り、SSOT を確定まで汚していなかったことが効いた。撤回で巻き戻す対象はコードだけで、設計書群の書き換え合戦は起きなかった。サンクコストは数日分の実装だが、サブスク運用を始めてからの撤回は顧客への返金・告知を伴う。撤回コストが最小の今が最後の変え時だった。

## 学び（一般化できるノウハウ）

1. **試行実装は「戻れる前提」を宣言し SSOT 反映を確定まで遅らせる** — 動くものを作って判断材料にしつつ、設計書という共有の正には確定まで書かない。「実装した」と「決めた」を別イベントとして扱えば、実装済みの設計でも数日で捨てられる。

2. **全面ピボットの前にクロスセルでアタッチ率を測る** — 主役の入れ替えは需要の証拠が出てからでいい。既存動線に新商材を従属配置すれば、アタッチ率という実銭の需要検証が安く手に入り、ピボットの選択肢も温存される。

3. **課金モデルが認証の複雑さを決める** — サブスクは「解約され得る状態」を守るため本人追跡・再照会・ログインが必須になる。買い切りは所有が永続なので、購入イベント自体を認証にでき、ログイン概念ごと消せる。認証設計は課金モデルの従属変数として、モデル確定後に引き直す。
