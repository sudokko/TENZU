# 問題データ基盤を schema v2 で再構築する（atelier 検品とかぶり除外）

## 何が起きたか（要約）

06-11 にパイロットとして立ち上げた問題データパイプライン（EP-085）を、6月末の基盤確定ウィーク（06-26〜07-01）で第二世代へ再構築した。スキーマは難易度と作問出自（provenance）を一級市民へ昇格させ、盤面を discriminated union 化して立体模写まで同じ型体系に収容。検品場 /atelier は「基準を編集」を全タスク＋グリッド編集へ拡張し、レベル定義をデータ駆動で回せる基準エディタにした。仕上げに gen/dedupe.ts を新設し、模写で公開済みの図形が fill・鏡・モチーフ注入へ再登場する「かぶり」を形シグネチャで除外（§3.60）。自動生成→検品→採用→publish が商品製造ラインとして固まった。

## 状況・背景

第一世代は schema.ts（型 SSOT）・決定的ジェネレータ・dev 限定 /atelier・published への静的レジストリ出力という骨格で、模写1巻のパイロットを通していた。その後の半月で前提が変わる。難易度スコア D の再校正が繰り返され（EP-088）、fill・鏡・モチーフ・立体と参加タスクが増え、複数タスクが同じ形ライブラリ（allVariants()）から素材を引くようになった。結果、①レベル定義の較正のたびにコード定数を書き換える運用は回らない、②盤面サイズが生成・表示・カタログで食い違い得る、③同じ図形が別タスクの商品に再登場し得る、という三つの問題が出た。

## やり取りの中身

**スキーマの v2 刷新**。難易度を Difficulty 型として一級市民化した。機械算出 auto と人手 override の manual を別フィールドで持ち、実効値 value は manual ?? auto。作問出自は旧 gen フィールドを Provenance union（ai／blank＝白紙作問／ai-edited）へ統合。盤面は SquareGrid | SolidGrid の discriminated union にし、立体模写の矩形格子を既存 JSON を壊さず収容した。union 化で p.grid.n の無ガード参照は tsc が全件列挙し、取りこぼしゼロで改修できた（§3.56）。

**atelier をデータ駆動の基準エディタへ**。編集可能フィールドの SSOT を ladder-schema.ts（LADDER_FIELDS 記述子・検証・stale キー除去）に新設し、UI と API が同じ記述子を共有する。三重管理だったグリッドは catalog-extra.json の patches[] 上書きレイヤで表示を同期し、data.ts を触らず drift を解消。グリッド変更時は既存候補との不整合を警告し再生成を促す。

**かぶり二層の除外**。id のかぶりは 06-15 に発覚済み＝追記式採番で87件が衝突し、id 一致の採用・保存が双子へ誤適用された。振り直しで解消し、生成ルートは既存最大連番からの継続採番へ直した。今回はその上の「形のかぶり」。fill と鏡は copy と同じライブラリから図形を引くため、模写で公開済みの図形が別タスクの候補へ再登場する。オーナーの線引きは「公開済みのかぶりは省く・公開済み以外のかぶりは許容」。gen/dedupe.ts が published/copy-* の全図形から原点寄せ（平行移動不変・盤面サイズ非依存）の形シグネチャ集合を作り、fill・鏡のプールとモチーフ注入から除外。鏡は答えペインに印字される鏡像側も照合する。掃除で14件を削除、採用済みへの衝突はゼロ。

**枯渇への調整**。3×3 はライブラリの大半が模写 Lv.1-2 の公開に使われ、除外後のプールが構造的に薄い。鏡 Lv.2 は閉路ゲートを 3×3 で緩和し（鏡は「裏返して写す」が本質で閉じた骨格は必須でない）、帯を入門仕様へ寄せて9問まで回復。12問への残りは白紙作成で補完する。

## なぜそう判断したか

**難易度と出自を一級市民にした理由**。難易度メタデータの厳選公開はこの店の差別化の本丸で、表示にも生成にも使う中核データを問題自身に背負わせる必要がある。auto/manual の別持ちは、式の再校正で機械値が変わっても人手のティア付けと理由が消えないようにするため。出自の union 化は、ライブラリ生成（兄弟巻の重複排除対象）と白紙作問で後続処理が分岐するのを型で表すためだ。

**「公開済みだけ弾く」線引きにした理由**。候補プール内のかぶりまで弾くと、変種が有限の小盤面ではプールが枯渇する。客の目に見えて問題になるのは「買った商品と同じ図形が別の商品にも載っている」ことだけなので、基準線を published に置いた。3×3 の枯渇はその判断の実証でもある。

**シグネチャを原点寄せにした理由**。同じ形が別の位置・盤面サイズに出ても客には同じ絵である。平行移動と盤面を捨象しないと、ずらしただけの再登場を見逃す。

**基準エディタをデータ駆動にした理由**。D 窓の再較正はこの後も続くと分かっていた（実際 06-30・07-01 にも改訂）。コード定数の書き換えを挟む運用は、検品しながら回すオーナーの速度に合わない。ladder.json を UI から編集して生成が追従すれば、較正は検品作業の一部になる。

## 学び（一般化できるノウハウ）

1. **共有ライブラリから複数商品を作るなら「公開済み除外層」を生成器の手前に置く** — 既販品と同じ素材の再登場は必ず起きる。客が同一視する差（位置・スケール）を捨象した正規化シグネチャで公開済み集合を弾き、基準線は「客の目に触れる範囲」に絞ってプール枯渇を避ける。

2. **機械算出と人手 override は別フィールドで持ち実効値を導出する** — 人手判断を機械値へ上書きで混ぜると、再計算で人手が消えるか再計算を恐れるかの二択になる。auto／manual／value=manual ?? auto の三点構造なら両者が共存し、override に理由メモも義務づけられる。

3. **繰り返し較正されるパラメータはコードから JSON へ、編集可能性は記述子で共有する** — 較正が運用になる値をコード定数に置くと調整のたびにビルドが要る。データファイル＋フィールド記述子（UI/API 共有）なら検証つき編集画面が安く立ち、較正は道具の中で完結する。
