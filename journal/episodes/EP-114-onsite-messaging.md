# オンサイトメッセージの自前実装（生涯1回・モーダル禁止）と DynamoDB 移行

## 何が起きたか（要約）

サイト内で来訪者に小さなカードを出す Web 接客（オンサイトメッセージ）を、外部 SaaS を使わず自前実装した。設計の核は抑制——同一メッセージは生涯1回・モーダル禁止・1PV 1件。2026-06-12 に SaaS 不採用と自前設計を決め（decisions §5.7）、07-11 に campaigns.ts ハードコード方式で初回実装。翌 07-12、オーナーの要望（画像・計測・ブラウザから編集したい）を受け、キャンペーン定義の SSOT を DynamoDB へ移し、本番管理画面 /admin/onsite と first-party 計測・画像対応まで実装した（§5.15・コミット 85fe395）。表示ガードレール G1〜G7 とトリガー3種の挙動は不変のまま、運用面だけを作り替えた移行である。

## 状況・背景

CRM ツールベンダーで営業12年のキャリアを持つオーナーにとって、Web 接客は本職の領域である。SaaS を入れれば機能は揃うが、モーダル・ポップアップ連発・執拗な再表示という業界の標準挙動は、ブランドの「広告で邪魔しない」という価値観と正面衝突する。必要なのはごく小さなカードを静かに1回出す機能だけ——専門知識が「何を作らないか」を先に決めた領域だった。07-11 のローンチ体系ピボットの反映作業中に Web 接客が設計のみで未実装と判明し、Claude が同日実装。翌日オーナーから、文言修正のたびにデプロイが要る方式では運用が回らないという要望が出た。

## やり取りの中身

**方針転換の切り分け**。オーナーの要望で覆したのは「管理画面は持たない」という一点だけで、§5.7 の自前実装方針は不変とした。キャンペーン定義の SSOT は campaigns.ts から DynamoDB の1テーブル（PK/SK・オンデマンド・GSI なし）へ移し、campaigns.ts は型定義と初期シード（冪等投入）へ降格。配信側 OnsiteMessenger はマウント時に active なキャンペーンだけを API から取得し、取得失敗や環境未設定のときは「出さない側」に倒す。既読は localStorage による生涯1回のまま、/admin・/atelier 配下では動かない。

**管理画面と語彙ガード**。/admin/onsite は合言葉 ADMIN_SECRET → HMAC 署名 cookie（30日・購入認証の auth.ts を流用）で守り、一覧（active トグル・直近7日小計・プレビューリンク）・編集フォーム・統計タブ・シードボタンを備えた。編集フォームには voice-tone の表現置換ルールと同期する NG 語彙警告（弱点診断・処方箋などを検出）を組み込んだ。ブラウザから文言を変えられるようになる分、語彙ガードを入力口へ前置した形である。画像はクライアント側で 512px WebP へ縮小して S3 に置き、カード表示は 64px サムネ固定でガードレールと整合させた。

**GTM ゲートの外の first-party 計測**。表示・クリック・非表示の計数は sendBeacon → 自前 API → DynamoDB へ JST 日付×キャンペーン単位で ADD 加算する first-party 経路にした。GA4/GTM が未接続でも数字が貯まり、プレビュー閲覧だけは計数から除外する。判断指標は show→click 率5%目安と先に決めた。

**AWS レスでの検証と残務の明示**。ローカルには AWS リソースがないため、未設定時に安全に degrade すること自体を検証対象にした——ビルド成功・ログイン 401/成功・一覧空表示・シード 503 エラー表示・NG 語彙警告・配信 API 200・管理 API 401 ガード・TOP カード非表示。実データ E2E（シード書き込み→カード実表示・画像アップ・統計・カート放置トリガー）は、オーナーの AWS リソース作成（DynamoDB 2テーブル・S3 バケット・IAM 権限追加・Amplify env 5件・約30分）待ちとして phase-1-todo §1.1 に手順化した。

## なぜそう判断したか

**SaaS を使わなかった理由**。要件が「静かに1回だけ出す」という引き算の仕様である以上、足し算で作られた SaaS は過剰機能とブランド毀損リスクの塊になる。オーナーは CRM ツールを売る側の経験から、接客ツールの標準挙動がどう鬱陶しさへ転ぶかを知っており、機能比較でなく「作らない機能の指定」から入った。抑制が仕様の中心なら、自作のほうが仕様に忠実である。

**ハードコードをやめた基準**。文言調整は開店後に高頻度で回る運用作業で、そのたびにコミットとデプロイを挟むのはひとり運営の回転を殺す。運用頻度の高い可変部（文言・画像・on/off）だけをデータベースへ出し、挙動を決めるガードレールとトリガーはコードに残した。

**計測を GTM の外に置いた理由**。オンサイトメッセージの成否判断は開店直後から要るが、GTM/GA4 の接続はオーナー作業待ちで時期が読めない。外部タグの開通に依存しない first-party 経路なら、計測の開始を自分の実装だけで確定できる。

## 学び（一般化できるノウハウ）

1. **抑制が仕様の中心なら自作が SaaS に勝つ** — 「出さない・繰り返さない・邪魔しない」という引き算要件は、汎用ツールの設定で再現するより自前の小実装のほうが忠実で速い。ドメイン専門家の知識は機能追加でなく「何を作らないか」の確定に使うと最も効く。

2. **可変部だけを DB へ出し、ガードレールはコードに残す** — 運用で頻繁に変わるもの（文言・画像・on/off）と、変えてはいけないもの（表示制約・トリガー挙動）を分け、前者だけを管理画面化する。全部を設定化すると抑制の設計自体が運用で崩せてしまう。

3. **外部リソース未接続でも「degrade の正しさ」まで検証して残務を手順化する** — 依存先が揃うのを待たず、未設定時に安全側へ倒れることを検証項目にすれば実装は先に完成させられる。残る実データ E2E は所要時間つきの手順書にして引き渡すと、待ち時間が作業停止にならない。
