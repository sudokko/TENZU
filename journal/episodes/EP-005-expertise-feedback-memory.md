# 「このユーザーはプロ」の記録機構 — feedback_email_marketing_expertise.md の発明

## 何が起きたか（要約）

C-3 サービスブループリントのメール運用設計の場面で、Claude が「個人運営だから軽量でよい」として「リスト保管のみ」「シナリオ 1 本だけ復活させる B 案」を提案した。しかし CRM ベンダー営業 12 年のメールマーケ専門家であるユーザーが即座に訂正し、フル Automation 採用に切り替えた（→ EP-031）。この訂正を受けて、以降のセッションでも同じ訂正を繰り返さないよう、専門領域を記録した `feedback_email_marketing_expertise.md` を memory に新設した。

## 状況・背景

ユーザーのキャリアはグローバル CLAUDE.md に「CRM ベンダー営業 12 年」として記録されていた。しかし汎用プロフィール情報は「参考情報」として扱われがちで、具体的な設計提案の場面で「このユーザーはメールマーケのプロだから、素人向け説明は不要」という動作には結びついていなかった。

その結果、MailerLite の運用設計という専門性が直撃する論点で、Claude は「個人運営は配信運用に時間が取れない」「Automation は重いから後回し」という汎用の初心者向け推奨を出してしまった。ユーザーにとっては、自分の専門領域で的外れなアドバイスを受けた形になった。

## やり取りの中身

### 訂正の内容

Claude が MailerLite の位置付けとして提案したのは以下の軽量案だった。

- MailerLite はメールアドレスの保管庫として使う
- 定期メルマガ・ステップメールはしない
- F2 転換メールを 1 本だけ組む B 案を推奨

ユーザーの返答は「俺、実はメールマーケはプロ。F2 転換もシナリオ一本っていうほど甘くはない。どうせならフルシナリオやる。初期重いだけで運用は自動化される」だった。

この一言で MailerLite の方針はフル Automation 運用（ウェルカム・F2/F3 転換・非アクティブ復活・カート放棄リカバリ・レビュー収集連動）に転換した。

### memory ファイルの設計

訂正された直後、将来のセッションでも同じ状況が繰り返されないよう、専用の memory ファイルを新設することにした。

ファイルパス: `memory/feedback_email_marketing_expertise.md`

記録した内容の骨子：

- ユーザーはメールマーケ・CRM 運用のプロフェッショナル（CRM ベンダー営業 12 年）
- メルマガ・MA 運用・F2/F3 転換・カート放棄リカバリ等の話題では初心者向け説明や「やめとけ」提案は不要
- 「初期設定の重さ」と「運用の軽さ」を分けて評価する
- メール周りの設計タスクはユーザーが主担当。Claude は判断材料を整える補助役
- 専門用語（オープンレート・CTR・SPF/DKIM/DMARC 等）は説明せずに使ってよい

### なぜ汎用プロフィールに追記せず専用ファイルにしたか

グローバル CLAUDE.md のユーザープロフィールに「メールマーケのプロ」を一行追記する方法もあった。しかし汎用プロフィールは全ての会話に適用され、情報密度が高くなると個別の判断ルールが埋もれる。

専用ファイル `feedback_email_marketing_expertise.md` として切り出すことで、メール設計が話題になった時に「このファイルを読め」と参照できる。また `type: feedback`・`originSessionId` というフロントマターにより、「いつ・どの文脈で記録されたか」が明示される。

## なぜそう判断したか

AI の汎用提案は「平均的な初心者」を前提に組み立てられる。「個人運営だから軽量に」という一般論は多くのケースで妥当だが、専門家には的外れになる。毎セッション同じ訂正が発生するなら、記録による前提更新が唯一の解決策だ。

専門領域が明確に定義された memory ファイルを持つことで、Claude はその領域について「初心者向けの配慮を外して設計相手をする」モードに切り替えられる。これは「ユーザーが主担当・Claude が補助役」という分業を具体的に実装する機構でもある。

プロジェクトが長期化するほど、専門性の記録は価値を持つ。TENZU のように設計フェーズが複数にわたる場合、各フェーズで同じ訂正を繰り返す非効率を避けるために、専門性の記録は早い段階で行うべきだ。

## 学び（一般化できるノウハウ）

1. **AI 提案レベルを引き上げたい領域は専用 memory ファイルに切り出す** — 汎用プロフィールに埋め込むと個別の行動規則が機能しにくい。`type: feedback` の専用ファイルとして管理すると参照しやすくなる。

2. **「ユーザーが主担当」を明示すると AI は補助役に回る** — 「この領域はユーザーが判断・AI は材料整備」と明記することで、AI の過剰な提案を抑制できる。設計タスクの責任分担を memory に書くのは実用的な運用テクニックだ。

3. **訂正された瞬間が記録のチャンス** — 訂正が発生した直後に memory に書き留めると、その文脈がそのまま「why」になる。後から追記しようとすると文脈が薄れる。
