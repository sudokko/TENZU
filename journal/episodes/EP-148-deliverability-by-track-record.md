# 認証は全部通っているのに Outlook だけ弾く（到達率を「時間で解く」と決める）

## 何が起きたか（要約）

購入確認メールが Gmail では受信トレイに入るのに、**Outlook（hotmail）では迷惑メール**に入った。SPF/DKIM/DMARC は通っている（通っていなければ Gmail も弾く）ため、**認証不備ではなく送信ドメインの実績ゼロ**が主因と判断した。`send.tenzu.jp` は 2 日前に作ったばかりである。Reply-To を実在の窓口に設定し、本文の生 URL をアンカーで包み、サンクスページに「迷惑メールも確認を／届かなくてもこのページから何度でも DL できる」旨を追記した。そのうえで**開店には完全解が間に合わないと認め、時間で解く**と決めた（decisions §3.113）。

## 状況・背景

EP-145 で Resend へ移行し、送れるようにはなった。しかし「送れる」と「届く」は別問題で、新規の送信ドメインは受信側に実績が無いぶん厳しく判定される。開店 2 日前で、これを数日で覆す手段は存在しない。

## やり取りの中身

**Reply-To を実在の窓口に設定した**。送信元 `no-reply@send.tenzu.jp` は **MX を持たない送信専用サブドメイン**なので、そのままでは顧客の返信が宛先不明で消える。「返信できる差出人」にすることは**顧客体験と迷惑メール判定の両方**に効く。

**本文の生 URL をアンカーで包んだ**。表示文字列と href を一致させる形で。**表示を短縮して href だけ長くするのは避けた**——リンク偽装の典型パターンで、かえって減点される。ボタン＋フォールバックリンクの二重掲載はトランザクションメールの通例で問題ない。

**URL むき出しは主因ではないと評価した**。長いセッション ID は消せないし、Gmail が通して Outlook だけ弾いた事実は「新規ドメイン × 実績ゼロ」の典型的な症状である。

**設計で受け止めた**。サンクスページに一文を足した——メールが見当たらないときは迷惑メールフォルダも見る旨、**届かなくてもこのページから何度でも DL できる**旨。そもそも受け取りは webhook に依存しない設計なので、**メール不達は取りこぼしにならない**。

**人手の施策も並べた**。①Outlook で「迷惑メールではない」指定＋信頼できる差出人へ追加（SmartScreen は学習する）②Microsoft SNDS / JMRP への登録。ただし後日、**SNDS も JMRP も送信 IP の所有者向けプログラム**であり、共有 IP の ESP 経由では登録資格が無いことが判明して、この項目は取り下げている。

## なぜそう判断したか

**主因の切り分けを「誰が通して誰が弾いたか」で行った**。認証（SPF/DKIM/DMARC）が壊れているなら Gmail も弾く。Gmail が通した以上、認証は生きている。残る差は受信側の評価ロジックと送信ドメインの実績で、実績はゼロ以外にありようがない。**症状の分布から原因の層を絞る**やり方である。

**「時間で解く」を明示的に決めた理由**。新規ドメインの Outlook 突破は数週間かかる。開店に間に合わないことを認めたうえで、**間に合わなくても事業が壊れない設計になっているか**を確認する方向へ切り替えた。実際、受け取り経路がメールに依存していなかったため、これは受容できるリスクだった。**解けない問題は、解けないと認めたうえで被害を測る**。

**DMARC の `p=none` を昇格させなかった**。`quarantine` への昇格も実績が付いてからで、いま強めると自分の首を絞める。

## 学び（一般化できるノウハウ）

1. **「送れる」と「届く」を別の問題として扱う** — 送信基盤の構築が終わっても、到達率は別軸の課題として残る。新規ドメインには実績ゼロという構造的なハンデがあり、設定では埋まらない。

2. **症状の分布から原因の層を絞る** — 「A は通して B は弾いた」という差は、両者が共通で見ている層（認証）が原因ではないことを示す。全滅か部分かで、疑うべきレイヤが変わる。

3. **解けない問題は、被害の測定へ切り替える** — 期限内に解けないと分かったら、解こうとし続けるより「解けなくても壊れないか」を確認する。壊れないなら、それは受容できるリスクである。
