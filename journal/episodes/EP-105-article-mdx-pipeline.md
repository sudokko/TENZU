# 記事基盤を MDX 公開パイプラインへ（ブラウザ執筆移行・マルチ出力・専用ブランチ）

## 何が起きたか（要約）

記事執筆の作業場を PC の Claude Code CLI から claude.ai/code（ブラウザ）へ移し、その受け皿として MDX 公開パイプラインを Phase 0〜5 で実装した（2026-07-01〜02・commit 2ffaa08／11ea8a0／8a6e492／39cbdc5 ほか）。記事は書き始めに出力先を tenzu（サイト本体）／note／ameba の 3 分岐で宣言し、craft・ペルソナ・ガードレールは共通、最終整形と掲載先だけを分ける。TENZU 向けは LLMO（meta／JSON-LD／OG）を frontmatter から自動生成し、note／ameba へは貼り付け用テキストを生成する（投稿は手動）。ツールは判断系スキルと機械検査スクリプトに二分した。07-12 には記事ドラフト 20 本をスマホ確認・修正用の専用ブランチ content/article-drafts へ切り出し（commit 567d4f7）、「書く場所」と「出す場所」を分離した記事工場が完成した。

## 状況・背景

執筆体制そのものは 06-11 に確定していた。オーナーの書き散らし（dump）→AI の構成提案→オーナー確定→本文化→推敲→レビューという 6 段フローと craft 3 冊が SSOT としてある。問題は作業場所で、記事が PC のローカルにしか無く「いつでもどの端末でも」書けない。2026-07-01 にオーナーが承認した移行方針は、claude.ai/code を GitHub の該当リポジトリへ接続して回すこと。通常の claude.ai チャットの GitHub コネクタは読み取り専用で書き戻せず、PAT clone はサンドボックスが使い捨てで毎回トークンを要する。GitHub App 連携で commit／PR まで一気通貫できる claude.ai/code が実質唯一の解だった。

## やり取りの中身

**MDX パイプラインの実装（Phase 1〜2）**。@next/mdx で web/content/articles/*.mdx をビルド時 SSG する構成にし、frontmatter は remark プラグインで export 化、独自ブロック（LeadGraf・Diagram・Quote 等）は mdx-components で供給する。Phase 2 で LLMO/OG 基盤を敷いた。絶対 URL の基点を site.ts の `SITE_URL` env 一本に集約し、sitemap・robots・JSON-LD・動的 OG 画像を frontmatter から自動生成する。OG の日本語グリフは Google Fonts をテキストサブセットで取得し、失敗時はラテン表示へ退避してビルドを壊さない。ホスティング固有機能には依存せず、将来のホスト差し替えが「向き先・env・CI 設定」の 3 点で済む標準 Next.js 構成に留めた。

**専用ツールのハイブリッド設計（Phase 3〜4）**。頻出作業を、判断が要るもの＝スキル（/llmo・/article-decorate・/article-image）、決定的に検査できるもの＝スクリプト（llmo-check.mjs・img-optimize.mjs）に振り分けた。途中でオーナー指摘により /llmo をスリム化し、構造層（JSON-LD／meta の自動生成に食わせる frontmatter と faq_schema）を整える仕事へ純化した（commit 39cbdc5）。アイキャッチはオーナーが Gemini で手動生成し、Claude は配置・検査・alt 付与のみ。note／ameba 向けは整形規約を external-output.md に SSOT 化し、変換は 100% 判断のためスキルのみとした。

**専用ブランチへの一本化（07-12）**。記事ドラフト 20 本は作業ブランチ上で未コミットのままローカルにしか無く、スマホから見えなかった。作業ブランチは他に 167 件の未コミット変更を抱えていたため、記事だけを専用ブランチ content/article-drafts に隔離して push し、スマホの claude.ai/code から開けるようにした。以後、記事編集はこのブランチを真実のソースとし、PC 作業時はまず checkout する運用に統一した。

## なぜそう判断したか

**保存先を GitHub に置いた理由**。ブラウザ実行環境は毎回まっさらで、ローカル状態に頼る運用は成立しない。逆に「状態は全部 GitHub」と割り切れば、端末もサンドボックスも使い捨てで構わない。gitignore を調整してスキルやレビューエージェントの定義まで追跡し、執筆の道具一式をブラウザ側へ届けたのも同じ理屈だ。「書く場所」と「出す場所」の分離はこの割り切りの帰結で、専用ブランチ化も同じ原理の延長にある。

**LLMO ツールを構造層に純化した理由**。当初は「LLMO 8 原則」の本文チェックまで持たせていたが、その名前が誤解の元だった。原則の大半は良い構造化ライティング一般の話で、本文品質を見るレビューエージェントの領分と 4 重に重複していた。同じチェックを複数箇所に持てば基準改訂のたびに全部を直す羽目になる。固有価値を「構造化データに正しく食わせる入力を整えること」だけと定義し直し、本文品質はレビュー側へ一本化した。

**検査をスクリプトに切り出した理由**。frontmatter の必須キーや画像寸法のような決定的検査を AI の判断に混ぜると、結果が揺らぐうえに毎回コストがかかる。機械で白黒つくものはスクリプト、文脈判断が要るものだけスキルという線引きで検査結果が安定し、スクリプト側は exit code で機械的に運用できる。

## 学び（一般化できるノウハウ）

1. **実行環境が使い捨てなら、状態をリポジトリへ全部寄せる** — ブラウザ・サンドボックス系の作業環境は「毎回まっさら」を欠点でなく前提にする。成果物だけでなくスキルや検査ツールまで Git 追跡に載せれば、どの端末からでも同じ工場が立ち上がり、環境の寿命と作業の寿命を切り離せる。

2. **ツールの責務は「判断」と「決定的検査」で二分する** — AI スキルに機械検査を混ぜない。決定的に判定できるものはスクリプトにして機械的に回し、判断系スキルはルールを複製せず SSOT を参照するだけの薄い層に保つ。基準の改訂が 1 箇所で済み、検査結果も安定する。

3. **チェックの重複は「ツールの固有価値の再定義」で解消する** — 同じ観点のチェックが複数ツールに生えたら、まず各ツールにしかできない仕事を一言で定義し直す。固有価値以外を削ぎ落とせば残りは自然に本来の持ち場へ寄り、重複が構造的に再発しなくなる。
